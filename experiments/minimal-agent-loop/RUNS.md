# 真实模型运行记录

M0 最小回路的消融实验：从 Cary 的 `experiment/M0`（`62966c1`）出发，每一步只改一处，用同一道题、同一个模型重复运行，比较成功率、成本和审查质量。分支 `M0/ContextEngine`，2026-10-01。

## 实验设置

- 模型：`deepseek-flash`，费用按 mini-agent 同一套价格（缓存命中 $0.003 / 未命中 $0.15 / 输出 $0.6，每百万 token，非高峰）
- 题目：`fixtures/c-review`（4 个文件、200 行），prompt 为“检查这个 C 仓库中可能导致崩溃、内存错误或错误结果的问题。”
- 评分：`evals/c-review-answer-key.json` 中人工核实的 18 个缺陷，分为 core 9 个（看一个函数即可发现）和 subtle 9 个（需要跟踪数据流或理解库函数语义）。每个缺陷有一组正则，命中任意一个算找到；正则已用真实报告校准，共用的行号不单独计分
- 重复读取：某次 `file_read` 的范围已被更早一轮完整读过
- 复现：`pnpm exec tsx experiments/minimal-agent-loop/scripts/baseline.ts 10 <label> c-review`，原始记录写入 `runs/`（本地，不提交）

## 基线：0/3

Planner 的 handoff 都成功了，失败全部发生在 ReviewAgent 读文件那一步，错误码都是 `INVALID_MODEL_ACTION`，但模型的实际输出有三种：

1. 一句英文开场白，加上 4 个 JSON 动作（协议要求只输出一个 JSON 对象）；
2. DeepSeek 原生工具调用的内部格式 `<｜｜DSML｜｜ invoke name="file_read">` 泄漏到正文；
3. 前几次按单个 JSON 读文件，最后又冒出 DSML 格式。

模型想一次并行读 4 个文件，而且训练出来的原生工具调用格式会自己冒出来。让它用文本输出 JSON 是在逆着它的习惯走。

## C1：原生工具调用（0/3 → 10/10）

- AgentToolPool 按 Agent 定义工具（Planner：`handoff`；ReviewAgent：`file_read`、`submit_review`），请求带 `tools`、`tool_choice: auto`，显式关闭思考模式
- 一次回复中的多个 `file_read` 在 Workflow 中排队执行，全部完成后才调用下一次模型
- 典型路径：handoff → 并行读 4 个文件 → submit_review，3 次调用

新问题：**10 次中有 8 次反复重读已读内容**。模型每次都说“I have all four files... let me verify”，然后重读，最多的一次重复 12 次、共 16 次读取，正好等于 `MAX_FILE_READS`，再多一轮就会失败。重读的运行质量并不更高（无重读的 subtle 为 7，重读 12 次的也是 7），只是输入 token 从 6k 涨到 47–51k。

推测原因：每次调用都是 `[system, 一大段 JSON]`，模型看不到自己之前发过哪些 tool_call，于是不确定自己是否已经核实过。

## C3：只追加的消息列表（重读 8/10 → 2/10）

- `ContextPack` 改为消息列表：`system → 固定的任务消息 → assistant(tool_calls) → tool × N → ...`，Workflow 在 AgentRun 中保存每一轮回复
- 预算改为在任务消息中写一次总上限，不再每次更新剩余次数，保证前缀不变
- 工具结果仍是原来的 JSON，以便单独衡量消息列表的效果

结果：调用 5.4 → 3.2，输入 token −68%，core 10 次全部满分。剩下 2 次“重读”性质也变了：只针对性复查一小段（如 `main.c:8-24`）就提交，不再成轮重读整个文件。上面关于原因的推测得到支持。

缓存按前缀命中：第 4 次调用的命中数约等于第 3 次调用的全部输入。3 次调用的运行命中率只有约 40%，是因为第 3 次调用里 4 个文件的内容第一次出现，这是结构上的下限，不是缺陷。

费用没有下降：输入省下的钱被更长的报告抵掉了（输出 +19%）。

## C4：工具结果改为纯文本（UAF 10/10）

工具消息从 JSON 字符串（换行被转义成 `\n`）改为 mini-agent 同样的格式：

```text
src/parser.c (lines 1-93 of 93)
   1 | #include "parser.h"
   2 | #include <errno.h>
```

- 输入 token 再降 18%（7.3k → 6.0k），费用降到 $0.0035
- subtle 7.4 → 7.6；`parse_integer` use-after-free（第 15 行 `free(copy)` 后第 16 行读 `*end`）C1、C3 各漏 2 次，C4 一次没漏。**但见下文 C5：这两项都在批次间的随机波动范围内，不能算作 C4 的效果**

## C5：错误处理（不属于消融，作为回归检查）

把可纠正的错误交还给模型、Kernel 重试暂时性失败、最后一次调用强制 `submit_review`、纯文本回复不再被当作结论。这些都只在出错时生效，正常路径上发给模型的内容和 C4 完全相同：第 1 次调用的输入在两批中都是 613 token，10 次运行也没有任何错误被交还给模型。

成功率、调用次数、token、费用都和 C4 一致，回归检查通过。

但 subtle 从 7.6 降到 6.7。人工核对了被判漏掉的报告，确实没有提到（例如 `parser.c:32` 只作为 `duplicate_slice` 溢出的调用点出现，没有指出返回值未检查），不是评分规则的问题。也就是说：**输入完全相同的两批各 10 次运行，subtle 平均分相差 0.9**。漏得最多的两项在两批之间变化很大：`append-name-unchecked` 2 → 7 次，`parse-error-ignored` 1 → 5 次。

这改变了对前面 subtle 数字的解读：

- C3 → C4 的 +0.2 和“UAF 全部找到”都在这个波动范围内，不能归功于纯文本格式
- C1 → C3 的 +0.7 也不足以单独下结论
- 站得住的是不受这种波动影响的指标：成功率、重复读取、调用次数、输入 token，以及 core（C3 起每批都是 8.9–9.0）

以后比较 subtle，需要更多次运行（例如每批 30 次），或者对同一配置先跑两批，把批次间差异当作噪声的下限。

## 结论

| 讨论点           | 作用                 | 依据                                      |
| ---------------- | -------------------- | ----------------------------------------- |
| 原生工具调用     | **决定能不能跑通**   | 0/3 → 10/10                               |
| 只追加的消息列表 | **决定效率和稳定性** | 重读 8/10 → 2/10，输入 −68%，远离读取上限 |
| 纯文本工具结果   | 小幅提升效率         | 输入再 −18%；质量差异在噪声范围内         |

现在 80% 以上的费用和大部分耗时来自最终报告（约 5k 输出 token）。继续降低成本要靠控制报告长度，属于 prompt 问题，不再是上下文架构问题。

## 尚未解决

- “空值被解析为 0”（`strtol` 没有检查 `end == copy`）：C1 漏 10/10、C3 漏 6/10、C4 漏 9/10。报告往往写“`strtol` 检查完整”。属于模型能力或 prompt 问题
- “空值被解析为 0”在 C5 也漏了 9/10
- 评分只判断报告有没有提到某个缺陷，不判断说得对不对，也查不出编造的问题；每批 10 次时，subtle 的批次间波动约为 0.9（见 C5）
- 最后一次调用强制 `submit_review`：已用单次请求确认 DeepSeek 支持按名称指定 `tool_choice`（2026-10-02），但完整的“额度用完”路径在真实运行中还没有触发过
