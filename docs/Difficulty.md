# MultiAgentOS 难点与可能实现路径

## 结论先行

“能否让多个 coding agent 同时工作”不是主要风险，现有项目已经证明可以。真正困难的是：让它们在**不互相破坏、不泄露权限、不过度消耗 token、可恢复且可验证**的前提下工作。因此应先做受限的 DAG + worktree + 契约闭环，再扩展到远程和多租户。

## 难点矩阵

| 难点 | 为什么难 | MVP 路径 | 后续路径 | 验证指标 |
|---|---|---|---|---|
| 任务拆解正确性 | LLM 可能漏掉依赖、错误估算粒度 | 只允许 Planner 输出 schema 校验过的 DAG；人工确认关键契约 | 从历史 run 学习拆解与路由 | DAG 无环率、返工率 |
| 并行写冲突 | 两个 worker 修改同一文件或隐含共享资源 | `owned_paths` + 独立 worktree + 合并前检查 | 语义冲突检测、自动 rebase、锁服务 | 冲突率、自动解决率 |
| 接口漂移 | 前后端各自“完成”但无法联调 | OpenAPI/JSON Schema 版本化，契约测试作为 gate | 兼容性分析、契约变更审批 | 契约测试通过率 |
| token/费用 | 协调消息和重复上下文可能抵消并行收益 | 任务卡、摘要、hash 去重、每任务预算、按需展开日志 | 历史成本模型和动态模型路由 | token/任务、美元/成功 run |
| 上下文过长 | 一个长会话同时包含规划、实现、调试，噪声大 | checkpoint + 摘要 + 新会话 | 项目事实图、向量/全文检索、语义压缩 | 超窗次数、恢复成功率 |
| 失败恢复 | provider 超时、进程崩溃、机器休眠会留下半成品 | 幂等 task_id、SQLite checkpoint、指数退避 | Temporal durable execution、远程 worker | 丢失工作量、恢复时间 |
| 安全隔离 | coding agent 需要执行命令，命令又可能读密钥/破坏系统 | 路径白名单、命令策略、rootless Docker、人工 gate | gVisor/Firecracker、远程沙箱、密钥代理 | 越权拒绝率、漏洞扫描 |
| 多 provider 差异 | CLI/API 的参数、流式输出、错误模型不同 | LiteLLM + provider adapter，保留原始响应 | 能力声明、动态降级和熔断 | 成功率、P95 延迟 |
| 资源调度 | 并发可能让本地 GPU/CPU、API rate limit 互相争抢 | `psutil`/NVML + semaphore + 阈值限流 | 资源预测、队列优先级和租约 | 利用率、排队时间、OOM 次数 |
| 质量评估 | 多 agent 输出不等于正确输出 | 测试、lint、契约、review 证据优先 | 任务集评测、回归和可解释评分 | 测试通过率、人工返工 |

## 1. 安全性：最容易被低估的难点

### 风险

- worker 通过 shell、MCP 或依赖安装执行任意代码。
- agent 读取环境变量、SSH key、云凭据，或把仓库发送给第三方 provider。
- 并行 worker 共享目录导致越权读写和供应链污染。
- “自动修复”误删文件、推送分支、发布服务。

### 分阶段路径

1. **MVP**：只允许项目白名单目录；默认无网络；命令按 allowlist；所有写操作留 diff；危险动作暂停等待批准。
2. **Beta**：rootless Docker/Podman、只读根、临时 workspace、seccomp/cap-drop、CPU/内存/进程数/磁盘配额。
3. **Production**：隔离 worker 节点，使用 gVisor/Firecracker；通过短期 token 访问有限 API；密钥由代理按请求注入，不直接挂载。

不要把“prompt 中说安全”当作权限控制；权限必须由运行时策略强制执行。

## 2. 并行冲突：从文件冲突到语义冲突

Git merge 只能发现部分文本冲突，无法发现“前端调用了旧字段名”这类语义冲突。建议同时使用：

- **静态 ownership**：任务声明 glob 路径；重叠路径禁止并行。
- **资源锁**：数据库迁移、锁文件、部署配置等命名资源串行化。
- **契约先行**：接口由独立任务产出，前后端都以版本化 artifact 为输入。
- **验证闭环**：合并后运行类型检查、契约测试、单测和 E2E；失败自动生成修复任务。
- **可回退合并**：每个 worktree 和 merge commit 可丢弃；不在主分支上直接让 worker 修改。

当冲突修复需要理解两个 worker 的完整推理时，只发送相关 diff、错误日志和契约，而不是广播两段完整对话。

## 3. token 与速度：如何避免“并行更贵”

并行的墙钟时间近似为最长关键路径，而 token 成本接近所有 worker 加协调成本。只有当任务足够独立且协调成本较低时才有收益。

采用以下策略：

1. Planner 先做粗粒度收益估算；预计节省时间不足以覆盖额外 token 时串行。
2. 每个 worker 只收到任务卡、相关路径、契约引用和验收条件。
3. 结构化 artifact 用 hash 去重；日志摘要默认截断，失败后按需取原文。
4. 简单检查使用便宜/小模型，架构和冲突修复使用强模型。
5. 对相同请求做短期缓存；provider 支持 prompt cache 时启用。
6. 在预算达到阈值时停止扩散，转为单一 integrator 收敛。

必须用固定基准实测三种模式：单 agent、手工双窗口、MultiAgentOS。报告 p50/p95 时间、总 token、成功率和返工，不用单次演示下结论。

## 4. 上下文与会话切换

建议将“记忆”分成四层：

- **Run state**：当前 DAG、节点状态、预算和审批。
- **Task summary**：目标、已做决定、证据、未决问题。
- **Project facts**：目录、技术栈、接口、测试命令和约束。
- **User preferences**：代码风格、默认模型、风险偏好。

每个层级都有大小上限和版本；新会话只检索相关层。切换会话的触发条件包括 token 预算、上下文占用、阶段完成或 provider 失败。恢复依赖结构化 checkpoint，而不是依赖模型“记得之前聊过什么”。

## 5. 动态资源监控与防堵塞

监控采集器每 1–5 秒记录：CPU/内存、GPU 利用率/显存（可选 NVML）、活跃 worker、队列长度、provider 延迟、429/5xx、token 速率和磁盘空间。

调度策略：

- 全局并发 semaphore + 每 provider/模型独立 semaphore。
- CPU/GPU/内存超过软阈值时暂停新任务，超过硬阈值时优雅取消低优先级任务。
- API 429 使用 `Retry-After` 和指数退避；连续失败触发熔断和备用 provider。
- 长时间无输出设置 heartbeat；超时后保存日志、终止进程并按幂等键重试。
- 防止“挂起”：worker 必须定期报告状态；scheduler 为无心跳节点设置租约过期。

资源监控只能帮助调度，不能解决错误的任务拆解或 provider 本身不可用；两者要分别观测。

## 6. 可行性验证路线

### 实验 A：前后端并行

固定一个 REST/GraphQL 全栈样例。Planner 生成契约，backend/frontend 各自 worktree，Integrator 合并并运行 E2E。对比三种模式的成功率、时间、token 和冲突。

### 实验 B：故障恢复

在规划后、worker 执行中、合并前分别杀掉进程或断开网络，验证 checkpoint 是否能恢复且不重复写入。

### 实验 C：安全攻击面

在仓库中放置读取环境变量、访问工作区外路径、联网上传和删除文件的诱导任务；验证策略引擎、沙箱和人工 gate 是否拒绝，并确认审计日志完整。

### 实验 D：资源压力

限制 CPU/GPU/内存并模拟 429/5xx，验证并发降级、重试、熔断、取消和最终收敛。

## 7. 何时不应并行

- 多个任务必须修改同一核心模块或同一迁移文件。
- 需求尚未澄清，Planner 仍可能推翻整体架构。
- API 预算、速率限制或本地资源不足。
- 任务结果需要强顺序的探索式调试。
- 风险动作（发布、权限变更、生产数据迁移）尚未获得人工批准。

在这些情况下，串行并不意味着系统失败，而是调度器正确识别了关键路径和风险。

## 8. 最大的产品风险

最大的风险不是“做不出多 agent”，而是做出一个看起来很忙、实际 token 更贵且难以信任的系统。产品必须把每次并行决策的理由、预期收益、真实成本、冲突和质量证据展示给用户；如果收益不成立，应自动退回单 agent 或串行流程。
