# ContextEngine 学习笔记

## 2026-09-22：上下文稳定性、KV Cache 与历史裁剪

来源：`references/ai-agent-book` 第 2 章实验 2-3 的“常见错误上下文管理模式”。这是学习结论，不是最终架构决定。

### 结论

1. **稳定前缀是性能契约。** 同一 Agent Run 中，系统提示、Agent 定义、工具目录与其顺序应尽可能固定。只要前缀发生变化，后续的 prompt cache/KV cache 命中会从变化处失效。
2. **动态状态不要改写稳定前缀。** 时间、余额、配额、运行状态等应作为末尾的运行时消息、结构化状态引用，或按需工具查询，而非每轮重建 system prompt。
3. **不要用简单滑动窗口作为主要历史策略。** 它既破坏前缀稳定性，也可能删掉关键的工具结果，导致模型重复调用或基于缺失证据猜测。
4. **保留提供商原生的结构化消息。** role、tool call 与 tool result 应以模型 API 的标准结构传递；不要为了统一格式而粗暴拼成 `USER:` / `ASSISTANT:` 文本。

### 对 ContextEngine 的初步启发

- 可把 ContextPack 区分为：稳定基础层（指令、工具定义、长期不变策略）与运行时增量层（当前任务、检索证据、工具观察、临时状态）。
- 工具清单应有稳定版本和确定排序；权限变化时应传递可调用工具集合或 capability reference，但避免无意义地重排完整工具描述。
- 历史压缩需要保留证据可追溯性：摘要应链接/引用原始 Artifact 或 tool result，而不是让摘要成为唯一事实来源。
- KV cache 是优化而不是正确性基础：缓存是否命中还取决于模型提供商、模型版本、请求参数和缓存生命周期；即使未命中，上述结构仍有利于可靠性与可调试性。

### 待带回主架构对话的问题

- ContextPack 的稳定层与增量层是否要在协议中显式区分？
- 工具权限变化时，如何在“最小权限”与“工具定义稳定”之间设计请求格式？
- 对于长任务，采用何种“追加历史 + 有证据的摘要 + 按需检索”的替代策略，取代滑动窗口？

## 2026-09-22：Agent 状态栏（2.3.4）

### 概念与问题

状态栏不是完整记忆，也不是用户输入；它是框架从真实运行记录中**确定性地提炼**出的、放在当前上下文末尾的运行时摘要，例如任务目标、TODO、已调用工具次数、预算/上限、当前工作目录和最近错误。它解决长轨迹中模型需要反复从零散记录统计“已经做了什么、下一步还缺什么”，进而遗忘约束或重复调用的问题。

### 初步边界

- 状态的事实来源不应是 LLM：Workflow、Kernel、工具执行器或持久化记录各自维护权威状态；ContextEngine 只选择、格式化并投影其中允许暴露的字段。
- Agent 可以提出计划或 TODO 更新，但不应单方面宣告诸如“已执行 3 次”“有某权限”这类可影响安全/调度的事实。
- 状态栏是当前决策的高密度投影，而不是原始证据的替代品。重要结论需要能回链到原始 tool result / Artifact / 事件记录。
- 为保持上下文前缀稳定，状态应作为末尾的、带来源标记的结构化运行时消息。具体使用 `user`、`developer` 或厂商特定消息槽位，必须按目标模型 API 的语义决定，不能在审计上把框架状态伪装为真实用户输入。

### 对 ContextEngine 的可能关系

ContextEngine 未来可负责将经授权的状态快照渲染到 ContextPack，但不应拥有或篡改该快照的业务真相。一个概念性输入可包括 `task progress`、`capability limits`、`workspace state`、`recent failures` 与每项的来源、版本、生成时间；是否采用此协议留待主架构对话决定。

### 可验证的 V1 候选（待会议确认）

先实现只读、确定性维护的最小状态栏：`当前 Task/阶段`、`已授权工具与调用次数/上限`、`最近一次执行结果或错误`、`工作区/Artifact revision`。Workflow、Kernel 和执行器分别提供权威字段；ContextEngine 在 token 预算内把快照渲染为末尾的结构化消息。暂不让 LLM 自行改写关键计数，也暂不把所有环境信息、长期记忆和复杂 TODO 管理都塞入其中。

最小验收可用同一任务作 A/B：没有状态栏时与有状态栏时，比较是否重复调用、是否违反调用上限、是否遗漏已失败步骤和 token/延迟。状态栏每个字段应有 `source`、`version`、`observed_at`，并避免携带原始外部文本或秘密。

## 学习重点：上下文压缩（2.7）

上下文压缩不是把消息“变短”，也不等于长期 Memory。它是在 token 预算内，为**当前任务**构造高密度、可回溯的工作集。后续学习和原型应围绕六个问题展开：

1. **何时触发**：token 阈值、任务阶段与上下文腐化信号；避免每轮压缩。
2. **压什么**：优先大型、低复用的 tool result；稳定指令、工具定义与近期关键交互尽量保留。
3. **如何选择动作**：保留、截断预览、直接删除噪声、结构化摘要、归档摘要、外部 Artifact 引用，并非只有“让 LLM 总结”。
4. **如何保真**：压缩必须任务感知，并保留来源/原始 Artifact 引用、输入范围与版本；摘要不可成为无法验证的唯一事实。
5. **如何兼顾缓存**：批量、阈值式改写投影，接受压缩点后的缓存失效，但保护静态前缀。
6. **如何评估**：除 token/延迟外，要测任务成功率、关键事实召回、重复工具调用、错误决策和可回溯性。

## 2026-09-22：2.4.1 压缩与 KV Cache 的取舍

### 必须区分的两份“历史”

- **持久记录 / 证据层**：完整 transcript、tool result、Artifact、事件与状态变更。用于审计、恢复和按需回查，不应因 prompt 压缩而被删除。
- **模型上下文投影层**：当前一次 LLM 调用实际接收的消息列表。它是有 token 预算的工作集，可以用摘要或引用替代部分旧内容。

### 结论

压缩发生在两次模型调用之间，是对投影层的有意识重写；静态系统指令和工具定义保持不变。压缩/替换某段旧工具结果会使该位置之后的缓存失效，但比上下文溢出而导致任务失败更可接受。因此不应每轮压缩，而应基于 token 阈值、任务阶段或明显的上下文腐化信号进行批量压缩。

### 对 ContextEngine 的可能关系

未来的压缩结果需要带有输入范围、任务目标、来源 Artifact 引用、压缩器版本和时间，才能被审计和必要时重新生成。DBOS 一类 workflow checkpoint 应保存/引用这种上下文投影的版本，而不是被误当成“永久保存全部 prompt”的唯一机制。具体责任归属和数据结构仍待主架构讨论。

## 2026-09-22：提示注入（2.4.7）——带回 Kernel 的分层安全议题

### 威胁

网页、文档、邮件、检索结果、图片/元数据、第三方 Skill，甚至被污染的记忆或状态摘要，都可能把“像指令的文本”带入 Agent 上下文。模型若将其误当成可信指令，可能进一步触发写文件、网络外发、删除或泄露等实际行动。

### 初步职责切分（讨论草案，不是最终决定）

- **ContextEngine**：为外部内容保存来源、信任等级和内容类型；用原生结构化消息与明确数据边界注入；不得将不可信文本拼入 system/developer 指令或高可信状态栏；清洗可疑内容只能作为辅助，不能当安全保证。
- **Kernel**：作为不可绕过的执行边界，签发并在执行时强制校验 capability；用沙盒/文件系统/网络外发限制约束工具；对删除、写入、发送、提权等高风险动作施加独立策略、确认或拒绝，并记录审计事件。
- **Workflow / AgentToolPool**：定义何时需要人工确认与审批门；对第三方 Skill、工具与模板建立来源审核、版本和信任策略。

### 建议与 Kernel 同学讨论的问题

1. capability 在何处、以什么身份在**每次工具执行时**校验，确保模型文本不能绕过？
2. V1 哪些能力默认禁止：网络外发、任意 shell、删除、跨工作区读取、写入仓库等？
3. 高风险操作的确认/审批是 Workflow 触发、Kernel 执行，还是两者如何配合？
4. ContextEngine 应向 Kernel 传递哪些 provenance / trust 标签，供策略或审计使用？
5. 第三方 Skill 与检索文档如何进入信任链；被发现可疑时如何隔离、回溯和撤销？

### 原则

模型不是安全边界。来源标记和提示词是“帮助模型正确判断”的软防线；最小权限、沙盒、出口控制和执行时鉴权才是“即使模型判断错也无法造成越权后果”的硬防线。

## 第 3 章预读：V1 与“用户记忆 / 知识库”的范围

依据当前 `docs/mvp-scope.md` 与 `docs/InitialPlan.md`，V1 必须具备的是**一次 Run 内、围绕当前项目的受控上下文**：TaskCard/Contract、相关文件片段、Artifact 引用、diff、测试报告、任务摘要与已知事实。它不以跨会话用户画像、通用 RAG 知识库或多项目共享长期记忆为验收条件。

- **V1 需要**：可追溯的项目事实/任务摘要和按需读取当前工作区、契约、Artifact 的最小检索；起步可为显式引用、路径白名单与 `rg` 等确定性方法。
- **V1 可预留接口、不急于实现**：带 provenance、scope、revision、TTL/retention 的 `ContextItem` / `ArtifactRef`，使未来能接入代码索引或向量检索。
- **V1 不应实现**：自动从用户历史抽取偏好、跨 Session 的个人记忆、自动写入长期记忆、面向任意资料的共享向量库。它们带来身份隔离、删除/过期、投毒、隐私与评估问题。

## 第 3 章实验 3-1：用户记忆的评测闭环

实验由两个相邻项目组成：`chapter3/user-memory-evaluation/` 提供三层测试用例、评分与报告；`chapter3/user-memory/` 才提供被测记忆系统（对话 Agent 只读取记忆，后台处理器分析已结束对话并经 MemoryManager 写入）。

评测协议的关键不是“最后答案是否像摘要”，而是：将多段历史会话依次提供给记忆写入过程；最终回答阶段不再提供原始历史，只能使用已保存的记忆。Layer 1 测直接事实，Layer 2 测多个候选实体下的检索和澄清，Layer 3 测跨会话综合与主动发现关联。

注意：`python main.py --mode compare --metric keyword-recall` 是无需 API 的教学对照，但它对 `fixtures/system_responses.example.json` 中的预置回答计算关键词召回，**不实际运行四个记忆实现**。真实比较需要把各实现产出的回答交给 batch / LLM judge，并检查精确性、召回、推理、主动性和幻觉。

对 MultiAgentOS V1 的可借鉴点是评测方法，而非用户记忆功能：为“只给 TaskCard、Contract、Artifact 摘要而不给完整历史”的场景建立用例，检验 Agent 是否取回正确证据、能否识别歧义并拒绝臆测。
