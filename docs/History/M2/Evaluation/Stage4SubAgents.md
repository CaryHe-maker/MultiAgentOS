# 阶段 4 SubAgent 的真实模型评测

> **历史数据（旧阶段的实测记录）。** 本文写于 M2 第一轮实现期间，记录当时的实验与结论，不再修改。
> 数据来自单个模型与少量运行，是当时的事实，不是统计结论。当前的设计依据是 [M2Design](../../../M2/M2Design.md)，文中的"阶段 N"是旧编号，见 [History/M2](../README.md)。

> 2026-11-06。模型 `deepseek-flash`，运行环境 Ubuntu 24.04（WSL），代码为 M2Design v1.26。数据是单个模型、每格 3 次运行的事实，不是统计结论。

## 1. 要回答的问题

1. SubAgent 的结果是否**确定**：同一个任务多次运行，最终的文件状态能否由模型之外的脚本逐项判定对错。
2. 任务有依赖时，模型是否会用 `dependsOn` 表达，依赖的任务是否真的在前一个任务之后开始，互不依赖的任务是否真的同时运行。
3. **没有提示时**，模型是否会主动调用 `run_subagents`。

## 2. 测试集

目录 `apps/control-plane/test/acceptance/subagent-suite/`（`cases.ts` 定义任务，`harness.ts` 是它们共用的部分，`run-suite.ts` 是运行器）。同一种任务的两个规模（C1 与 L1、C3 与 L3、C5 与 L5）由同一个构造函数生成，只有规模不同（实验之后把手写的小夹具改为生成，形状不变：端点 10 个、库 5 个、目录 6 个）。每个任务有夹具（仓库内容）、检查脚本（在模型之外判定最终状态）和参考解（检查脚本必须在夹具上判失败、在参考解上判通过，由 `selfcheck.test.ts` 保证）。

| 任务 | 内容 | 依赖的由来 |
|---|---|---|
| C1 endpoints | 按 README 把遗留服务器**实际注册**的 10 个端点迁移成适配器、索引和文档；另有未被加载的 2 个死路由 | 要先读 `server.js` 才知道有多少端点，再分头建文件，最后汇总索引与文档 |
| C2 invoice | 给发票格式加两个字段：schema、四个格式的序列化器、测试、变更日志 | schema 先于序列化器，测试与日志最后 |
| C3 survey | 为 5 个库写报告表，数值只在各库文件里 | 5 项互相独立，再汇总 |
| C4 features | 三个功能共用一个配置文件 | 共享文件，写入范围会冲突 |
| C5 rename | 跨 6 个目录重命名一个函数（代码、测试、文档） | 按目录并行，再验证 |
| L1、L3、L5 | C1、C3、C5 放大到 40 个端点、24 个库、30 个目录 | 同上，规模使单个上下文做起来更慢 |
| K1–K3 | 对照：修一个小 bug、回答一个问题、一句问候 | 不需要派生 |

检查是**具体的**：逐个适配器文件的内容、索引顺序、文档行、序列化器对样例的输出、表格每一格的值、全仓库不再出现旧名字、`node --test` 通过。

四种提示：`natural`（只给任务）、`hint`（加"可以用子任务"）、`explicit`（要求用 `run_subagents`，有依赖的部分设为依赖）、`alone`（要求自己做）。

运行器 `run-suite.ts` 记录：检查结果、`run_subagents` 的参数（任务、`dependsOn`、写入范围）、各任务的汇合状态、真实并行度（各任务模型请求的时间区间重叠数）、被拒绝的调用、用时和请求数、main 每一轮的调用、会话日志里的收尾原因。

## 3. 结果

### 3.1 没有提示时是否主动派生（`natural`，最终版本，每格 3 次）

| 任务 | 正确 | 派生 | 平均用时 |
|---|---|---|---|
| C1、C2、C3、C4、C5 | 15/15 | 0/15 | 12–42 秒 |
| L1、L3 | 6/6 | 0/6 | 26–54 秒 |
| L5（30 个目录的重命名） | 3/3 | **2/3** | 78 秒、51 次请求 |
| K1–K3（对照） | 9/9 | 0/9 | 1–8 秒 |

两个更早版本的运行（共 21 + 9 次）结果相同：只有 L5 偶尔派生。`hint`（"可以用子任务"）12 次**全部没有派生**。

结论：**DeepSeek flash 不会主动调用 `run_subagents`**，除非任务大到一个上下文做起来明显吃力（本组里只有 30 个目录的重命名偶尔如此）；一句软提示不起作用。它自己做这些任务全部做对，且更快。

### 3.2 要求派生时是否正确（`explicit`，最终版本，每格 3 次）

| 任务 | 正确 | 用依赖 | 任务数 | 实测并行度 | 平均用时 / 请求 |
|---|---|---|---|---|---|
| C1 endpoints | 3/3 | 3/3 | 6/4/6 | 2/2/1 | 104 秒 / 43 |
| C2 invoice | 3/3 | 3/3 | 4/8/8 | 2/2/2 | 76 秒 / 36 |
| C3 survey | 3/3 | 3/3 | 6/6/7 | 2/5/5 | 50 秒 / 25 |
| C4 features | 3/3 | 3/3 | 4/3/2 | 3/2/1 | 54 秒 / 32 |
| C5 rename | 3/3 | 3/3 | 8/4/5 | 3/3/3 | 60 秒 / 40 |
| L1 endpoints | 3/3 | 3/3 | 8/6/5 | 4/4/4 | 134 秒 / 70 |
| L3 survey | 3/3 | 3/3 | 3/4/5 | 2/3/4 | 84 秒 / 42 |
| L5 rename | 3/3 | 3/3 | 5/5/4 | 4/4/2 | 102 秒 / 59 |

24/24 的最终状态通过检查，每次都用了 `dependsOn`（探查或写文件先于汇总、索引、文档），互不依赖的任务真的同时运行（最多 5 个）。写入范围冲突的 C4 没有出现越界。

### 3.3 代价

同一任务，派生比自己做慢：例如 L3 自己做约 26 秒、10 次请求，派生约 84 秒、42 次请求；L1 自己做约 51 秒，派生约 134 秒。本组任务一个上下文都装得下，并行没有赚回协调的开销。**没有量出"完工时间接近关键路径"（验收 P3）**；那需要单个 Agent 明显做不完或做不快的任务。

## 4. 评测发现并已修正的设计问题

第一轮 `explicit` 只有 9 次里 0 次完成。原因不是模型，而是规则：

1. 参数被校验拒绝的 `run_subagents` 算作"没有进展"的一轮；连续两轮就强制收尾，而收尾时不能再派生。
2. `update_todos` 单独成轮同样算没有进展；模型先写计划再派生是正常做法，却被强制收尾。参数写错的 `update_todos`（`completed` 而不是 `done`，或同时标了几个 `in_progress`）让这条路径更常触发。
3. 一次最多 4 个任务，而"先并行、再汇总、再写文档"的图常需要 5–6 个，第一次调用就被拒。
4. 参数被拒绝时，回复只说"不合要求"，不说哪里不合。

已改（M2Design v1.26）：被拒的 `run_subagents` 不判进展；只调用 `update_todos` 的一轮不判进展，连续第二个才计入，参数不合要求的那一轮始终不判；`maxSubagentsPerCall` 缺省 8，拒绝文字说明可分批；参数不合要求的回复写明哪里不合；`update_todos` 的状态值改为 `completed`，不再限制 `in_progress` 的数量。改后 `explicit` 从 0/9 变为 24/24。

## 5. 局限

- 单个模型、每格 3 次；n 太小，不能给出概率。
- 任务都在一个上下文放得下，所以没有显示出并行的收益。
- `natural` 的"不派生"取决于提示词与模型：把 main 的派生准则写得更强，或换更大的任务，结果会不同。这里测的是当前提示词。
- 检查只看最终状态与轨迹，不评价代码质量。

## 6. 复现

```bash
# 检查脚本的自检（不调用模型）
pnpm exec vitest run apps/control-plane/test/acceptance/subagent-suite
# 真实模型：--modes natural,hint,explicit,alone；--runs N；可以指定任务编号
MAO_ENV_FILE=.env pnpm exec tsx apps/control-plane/test/acceptance/subagent-suite/run-suite.ts \
  --yes --out results.jsonl --modes natural --runs 3 C1-endpoints L5-rename
```

结果按"任务|模式|序号"追加到 `--out`，已有的运行会被跳过，被时间限制中断后可以重新启动。WSL 中同时运行的进程不要超过 3 个。
