# 阶段 6 抓取顺序：本地优先还是 DeepSeek 优先

> **历史数据（旧阶段的实测记录）。** 本文写于 M2 第一轮实现期间，记录当时的实验与结论，不再修改。
> 数据来自单个模型与少量运行，是当时的事实，不是统计结论。当前的设计依据是 [M2Design](../../../M2/M2Design.md)，文中的"阶段 N"是旧编号，见 [History/M2](../README.md)。

> 2026-11-07。61 个真实地址，每个用三种方式各读一次：只用本地抓取、只用 DeepSeek 抓取、产品用的组合（本地优先，做不到时用 DeepSeek）。运行环境 Windows 本机，网络出口在新西兰。数据是一次运行的事实，不是统计结论；站点的反爬行为每次可能不同（`medium` 在两次运行里一次失败、一次成功）。

## 1. 要回答的问题

Cary 的两个顾虑：DeepSeek 的抓取要付费（约 0.75 美元每千次），自己做能不能省下来；以及自己做的质量够不够。上一份评测（[Stage6WebProviders](Stage6WebProviders.md)）里本地抓取只是"最小实现"，现在的本地抓取有完整的 HTML 转 Markdown（保留链接与代码围栏）、固定地址的连接与逐跳重定向检查。要看的是：在真实地址上，本地优先的组合是否不比 DeepSeek 优先差，失败时回退到 DeepSeek 能挽回多少。

## 2. 方法

脚本 `apps/control-plane/test/acceptance/web-eval/run-fetch-compare.ts`（`--yes --budget N --out <文件>`，已有的地址会跳过，`--budget` 限制整个运行对 DeepSeek 的请求数，密钥不写入记录）。地址分九类：官方文档（20）、维基百科（4）、GitHub（6）、问答与博客（9）、论文与规范（4）、难抓的站点（10：reddit、x.com、npm、BBC、Medium、Cloudflare、知乎、PyPI、crates.io、LinkedIn）、脚本应用（2）、数据接口（1）、边界情形（5：不存在的页面、http 到 https、跨主机重定向两个、同主机重定向）。

一个地址"好"的判据：完成；含只有真实页面才有的词；正文（不计工具加在前面的来源框架）不少于 400 字符（难抓与脚本应用类 1500，数据接口 50）。不存在的页面与 PDF 以"拒绝或失败"为好；会跳到另一个主机的地址，以"结果说明了目标主机"为好。DeepSeek 一栏是直接调它的接口，组合一栏走产品的 Executor（含全部地址检查）。

## 3. 结果

| 方式 | 好 | 备注 |
|---|---|---|
| 只用本地 | 51 / 61 | |
| 只用 DeepSeek | 47 / 61 | 其中边界类 2 项"差"是设计差异：DeepSeek 自己跟随了跨主机重定向，本地按设计只说明目标主机 |
| 组合（本地优先） | **52 / 61** | 只有 2 个地址用到了 DeepSeek：`crates-serde`（本地得到空壳页，DeepSeek 读出 1.7 KB 正文）与 `todomvc-react` 的空壳页 |

按类（地址数 / 本地 / DeepSeek / 组合）：官方文档 20/20/20/20，维基 4/4/3/4，GitHub 6/6/5/6，问答与博客 9/7/7/7，论文与规范 4/4/4/4，难抓 10/4/4/5，脚本应用 2/0/0/0，数据接口 1/1/1/1，边界 5/5/3/5。

**内容质量**（两边都成功的 44 个页面）：本地共 5767 个保留下来的链接与 950 个代码围栏，DeepSeek 是 24 个与 3 个。长列表与动态页差别最大：维基"编程语言列表" 51.7 KB 对 1.4 KB，GitHub releases 12.2 KB 对 266 字节，BBC 新闻首页 9.5 KB 对 294 字节，dev.to 17.9 KB 对 705 字节。

**时延**：本地中位数约 0.4 秒（p90 约 1.5 秒），个别大页面（Node 文档 428 KB）5 秒；DeepSeek 一般 3–5 秒，GitHub 与长页面常超过 10 秒，个别 30–45 秒。组合因为多数地址只走本地，中位数 0.15 秒。

**费用**：整次评测对 DeepSeek 共约 135 个请求（含两次试跑），约 0.1 美元；组合方式在这 61 个地址上只花了 2 个请求。

## 4. 评测发现的问题（已修）

1. 本地抓取在页面只剩空壳时（`crates.io`、`todomvc`）返回 0 字节的**成功**结果。现在：没有任何文字、或页面在 1500 字节以上而文字少于 300 字符，标为 `thin`，交给提供方，只有提供方给出更多文字才采用；最后内容仍为空时以 `PAGE_UNAVAILABLE` 回答，不把空页面交给模型。
2. 小而空的页面原先不触发回退（只看 1500 字节的大小条件），已改为没有任何文字就触发。

## 5. 两边都不行的情况

- `stackoverflow`、`npm`、`reddit`、`openai-docs`（平台文档，脚本应用）：本地得到 403 或空壳，DeepSeek 同样失败（常在 12–13 秒后超时）。这类站点需要真实浏览器或登录，评测没有试代理。
- `x.com`、`知乎`：本地只拿到登录墙；DeepSeek 读到的 x.com 推文文字反而是真实内容。本地的页面不是空的，所以不触发回退。这是已知的缺口：要识别"登录墙"需要站点特例，没有做。
- `medium`：两次运行一次被拒、一次读到 1.3 KB，随机性来自站点。
- 本评测的判据对 `lobsters`（本地读到 16 KB 的真实首页，只因标记词"Lobsters"没出现在正文里）有误判；记录里按判据算作"差"，没有手工改。

## 6. 结论

1. **本地优先是对的**：在 61 个真实地址上本地抓取不比 DeepSeek 差（51 对 47），保留了 DeepSeek 丢掉的链接与代码围栏，大页面与动态页上多得多，更快，且成功的抓取不把地址交给任何第三方。
2. **DeepSeek 作为回退有价值但是小价值**：挽回了脚本应用类里 2 个本地读不到的地址（`crates.io` 完整、`todomvc` 勉强）。费用几乎为零，因为它只在本地做不到时才被问。
3. 难抓的站点（Cloudflare 验证、登录墙、纯脚本应用）两边都做不好，这是抓取的天花板，不是顺序的问题。真正解决需要真实浏览器渲染，不在 M2 范围。
4. 顺序与回退条件已按此实现（ExecutorSet 第 5d 节）：REJECTED 与 404、410 永不回退，空内容与脚本生成页面回退，提供方做不到时给出本地抓取自己的失败。
