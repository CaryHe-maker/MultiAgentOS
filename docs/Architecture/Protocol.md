# MultiAgentOS 协议架构

## 1. 协作边界

协议约定 Module、Kernel 组件与基础设施之间的协作语义。
SharedContracts 提供公共契约；各 Owner 负责解释并维护自己的领域状态。
通信成功不等于请求获准，执行结束不等于结果被接受，结果被接受不等于业务验收完成。

外部系统调用统一进入 Gateway，由 Kernel 分发至相应职责。
内部系统调用用于 Kernel 内部受控协作，其组织方式保留演进空间。
可信事实通道可以向 Monitor 或对应 Owner 报告事实，不能借此发起受保护操作。

## 2. 消息与调用语义

| 类别 | 含义 |
|---|---|
| Command | 请求 Owner 改变状态；可以被拒绝，受理与完成分开表达 |
| Query | 查询允许公开的状态，不隐式触发执行或授权 |
| Event | 报告已经发生的领域事实，不替代新的决策 |
| Signal | 请求暂停、中止等控制动作；收到信号不代表效果已停止 |
| Result | 表达执行产物、失败或未确定效果，交由对应 Owner 接受 |
| Stream | 提供增量展示或观测，不单独构成完成和结算依据 |

长操作允许先返回受理结论，后续独立报告进度与终态。
调用双方必须能区分尚未受理、已受理未完成、已完成以及状态未知。
重复交接不得重复产生业务效果；相同请求标识对应不同意图时应视为冲突。

## 3. 身份与因果

请求、业务运行、任务尝试、Unit 尝试和 Executor 执行实例保持可追踪关系，
以区分业务重试、同一次请求重传与内部步骤推进。
结果必须能归属于其发起意图、作用范围及实际执行尝试，过期结果不能覆盖当前状态。

调用身份来自可信运行边界，不能只相信请求自报的身份。
公共关联信息只用于识别和追踪，不自动授予资源访问权。

## 4. 定义、权限与 Lease

运行采用确定的模板与行为版本，后续定义变化不应悄然改变已受理意图。
AgentToolPool 定义模板组合，ExecutorSet 提供行为代码，Execution 管理实际执行。

Tool 是可选权限封装。经过 Tool 的操作由 Core 按授权与 Lease 作出权限判断；
未封装 Tool 的行为依赖开发者授予的权限，调用者不能通过省略 Tool 改变权限来源。
两条路径都受运行范围、资源和数据安全约束。

Lease 内容仅存在于 Core。权限判断由系统调用触发，其他组件获得判断结论与操作关联，
不接收 Lease 实体、快照或可供独立判断的副本。
合法权限查询不等于直接访问 Lease；绕过边界直接读写 Lease 必须拒绝并触发 panic。

授权结论不应被解释为无限期、任意目标的执行许可。
授权条件变化、撤销与执行交接之间的关系由 Core 与 Execution 协作维持，
无法确认仍然获准时不得假定继续有效。

## 5. 作用范围与产物

MissionScope 表达业务边界、资源与数据范围。派生任务不能自行扩大范围。
输入、上下文与结果的引用需要保留来源、适用范围及版本关联，
引用可解析不意味着调用者有权读取内容。

不可变大对象存放在 ArtifactStore，协作消息可以携带必要摘要或结构化结果。
是否读取完整对象由消费语义决定；不能要求所有小型结果都间接读取，
也不能把未经持久保存的流式输出当作正式产物。

## 6. 结果、资源与控制

Execution 报告执行事实、产物和效果状态；Core 维护控制结论，
Workflow 决定业务接受、验收与下一步行动。Monitor 汇集资源与运行事实。
资源预留、实际消耗、结算和未知消耗应可区分，展示采样不能代替权威账目。

暂停、中止和超时是控制请求或观测事实，不自动撤销外部效果。
无法判断操作是否发生时，先保留未知状态并核对，不盲目重试。
补偿是新的业务行动，同样受准入和权限约束。

## 7. 人类参与

用户可以提供信息、作出业务选择、回答授权申请或验收产物。
不同交互应保留各自的决策主体和适用上下文。
UserInteraction 收集并展示决定，Core 判断授权有效性，Workflow 判断业务决策是否仍适用。

回答必须关联待处理事项。请求失效、范围变化或运行已结束时，
旧回答不能直接作用于新操作。展示完成不代表请求已经生效。

## 8. 保存与恢复

业务检查点记录可继续的业务语义，运行时恢复记录支持核对执行与控制状态，
SessionCheckpoint 组合会话所需的业务状态和产物关联，三者不能相互替代。

恢复先确认定义、数据、权限和外部效果是否仍满足继续条件。
旧授权和 Lease 不因保存而自动永久有效；恢复不得复活已撤销权限。
缺失产物、版本不兼容和未知效果必须显式处理，不能伪装为完整恢复。

## 9. 异常与安全

异常需要表达失败归属、影响范围、是否可重试及是否存在未知效果，
使控制逻辑不依赖解析面向人的错误文本。
局部执行失败通常形成结果；权限边界、状态权威或安全不变量遭到破坏时升级处理，
必要时进入 panic 和安全关闭。

诊断、审计与流式展示应保留必要因果，同时避免暴露凭据、私有 Lease 和无权访问的内容。
可靠领域事实与可丢弃观测分开处理。

## 10. 兼容与完成

协议演进需要明确生产者与消费者的兼容关系。
无法识别的操作或无法解释的关键语义应被拒绝，不能静默降级为另一种行为。

完成包含执行终态、结果接受、业务验收和用户可见交付。
每一步都有明确 Owner；重复或迟到交接不能重复结算、覆盖新状态或再次触发交付。
