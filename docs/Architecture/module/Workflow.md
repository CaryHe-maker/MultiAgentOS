# MultiAgentOS Workflow

## 1. 定位

Workflow 是业务推进与验收的权威，负责目标分解、任务依赖、Agent 行为、
人工等待、集成、恢复和补偿。它决定下一步应该做什么，Kernel 决定并管理实际执行。

Workflow 使用 AgentToolPool 模板创建运行，向 Gateway 提交 UnitIntent。
它不直接调用 ExecutorSet，不管理 Lease，也不选择执行进程。

## 2. 业务结构

| 概念 | 责任 |
|---|---|
| WorkflowRun | 一次目标运行及其业务结论 |
| TaskGraph | 任务依赖、输入输出关系和汇合条件 |
| GraphRevision | 业务图的不可变版本 |
| MissionScope | 目标谱系、业务监督、能力与预算上限、工作范围 |
| TaskRun / TaskAttempt | 逻辑任务与某次业务尝试 |
| AgentRun | 基于固定模板的一次智能行为过程 |
| AgentStep | 上下文、模型、动作与观察的业务推进边界 |
| IntegrationAttempt | 对变更产物进行集成和质量验收的业务尝试 |

TaskGraph 决定业务是否就绪，MissionScope 限定工作边界，
UserInteraction 的 SessionTree 决定用户如何组织运行。三者不能互相替代。
Kernel.Execution 拥有 UnitAttempt，与 Workflow 的 TaskAttempt 分开。

## 3. 模板与动作

Workflow 从 AgentToolPool 选用明确版本的模板，固定本次运行的能力组合，
不能随模板更新静默改变已有运行。

Unit 的执行链可以有 Tool 权限封装，也可以使用可信开发者授予权限的行为。
Workflow 检查模型动作是否存在、是否属于固定组合及是否满足业务输入要求，
但不通过检查动作合法性替代 Core 的权限审核。
无 Tool 路径由可信模板决定，模型不能自行省略审核封装。

## 4. Agent 行为闭环

```text
确定当前目标与已有证据
  → 请求所需上下文操作
  → 请求模型推理
  → 解释动作提案或结果
  → 提交合法 UnitIntent / 请求业务决策
  → 接收 Kernel 确认事实并形成观察
  → 继续、等待或提交业务结果
```

上下文构建和模型调用均由 Kernel 执行，具体行为来自 ExecutorSet。
架构不要求每个 Agent 固定包含同样数量或顺序的 Unit。
无进展、非法输出和预算不足需要有明确结束或修正路径，不能无限循环。

## 5. 依赖、并行与重规划

任务就绪由输入、上游结果、范围约束和汇合条件共同决定。
汇合可以要求全部、部分或满足特定验收条件的结果，但选中输入必须可解释，
迟到分支不能悄悄改变已采用的依据。

业务图变化形成新版本。Workflow 明确影响范围并通知 Kernel 限制旧工作继续推进。
未受影响分支只有在输入、产物、权限与修改范围仍独立时才可继续。
并行由业务依赖和执行资源共同约束，不以消息到达顺序决定集成结果。

## 6. 结果与集成

Workflow 消费 Kernel 的确认结果，核对业务尝试、输入、来源和验收条件。
执行成功或模型声明完成不直接构成业务成功。

代码或其他修改以可核验变更产物交付。Workflow 决定集成顺序和质量要求，
Kernel 执行物化、应用、检查等操作。单个 Executor 的自测不能替代整体集成验收。
发布和其他外部影响仍是独立获准的工作。

## 7. 人工参与

权限审批由 Core 管理，UserInteraction 收集用户响应，Workflow 保存业务等待。
信息补充、方案选择和结果验收同样可以触发交互，不限定在权限审核节点。

用户响应必须适用于当前目标和决策上下文；条件变化后不能复用旧批准。
批准后仍须回到适用的 Kernel 检查，超时不自动批准。

## 8. 控制、重试与补偿

暂停在一致边界停止业务推进，恢复延续适用的运行。
取消先停止新意图并请求 Kernel 收敛执行，物理终止不等于业务取消完成。
重试创建新的尝试并保留历史，重新运行和从保存点派生则形成新的业务运行关系。

未知效果先核对；已经发生的外部影响不能通过回退业务状态抹除。
补偿是新的受控工作，无法补偿或核对时交由明确处置，不能标记为正常成功。

## 9. Checkpoint 与恢复

区分控制流恢复点、同一运行的 WorkflowCheckpoint、用户可见的长期 SessionCheckpoint。
长期保存点具有独立内容与保留关系，不是可随时丢弃的内部状态别名。

Workflow 协调业务状态和依赖产物的一致保存，Kernel 提供执行、资源与效果事实。
保存点只引用其他 Owner 的事实或可重建依据，不接管其状态。
恢复需重新确认依赖、访问范围和执行条件，不复制有效 Lease、凭据或活执行会话。

从保存点派生运行与普通重试、重规划、控制流恢复分开。
必需依赖缺失或效果未明时，不得部分启动并宣称恢复成功。
持久控制流机制不能成为任务图的第二个权威，也不能在重放时重复产生副作用。

## 10. 完成与可观测性

最终完成须同时满足任务与汇合验收、必要审核、产物完整性、
Kernel 执行范围收敛及外部效果处理。终态不能由迟到结果重新打开。

Workflow 提供版本化业务视图，记录推进原因、等待、失败与证据。
它解释错误对业务的影响，不覆盖 Kernel 的实际执行、消耗或权限事实。
