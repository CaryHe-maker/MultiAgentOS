### 2. 同轮多个工具调用：串行还是并行

- **Cary**：一轮读 5 个文件，就是 5 个工具调用、5 个 Unit，现在按顺序串行执行，M0 已验证串行一定能跑通。M1 要不要尝试并行？问 field 的想法
- **field**：现在先不做并行
- **Cary**：既然没有并行调度，Scheduler 可以先做成空实现，或者只预留位置；API 已经写好了
- **field**：Scheduler 现在就是一个很简单的串行调度
- **结论：M1 串行执行。** Scheduler 保持现在的简单串行调度，为以后的并行预留位置；已经写好的 API 不动

> **点评**：支持。M0 里模型调用以外的执行合计只占 0.05% 的时间，并行几乎没有收益。要守住的是另一半：**协议上仍然允许模型一轮发多个调用**，每个调用各自得到结果，全部有结果后才组装下一次上下文（#14 Cary 的结论）。Scheduler 保持 field 现在的“串行调度”比 Cary 说的“空实现”更好：空实现容易被理解成可以绕过 Scheduler，以后加并行时就得补调用路径。

### 3. 程序退出与意外终止（对应 #19）

- **Cary** 提问：运行中途被强行取消、非法退出时，要不要保存状态？下次启动时如果有上次意外终止留下的东西，要不要专门写处理机制？
- 已有共识：M1 不支持继续之前没跑完的运行
- **field**：要做两种退出。正常退出要做，退出时卸载各模块；异常崩溃 M1 做不了
- **Cary**：那 M1 一旦异常崩溃，程序就“死”了吗？第二次启动至少要做一次清空，否则中途退出一次，下次就没法正常开始
- **field**：启动跟这个有关系吗？启动后直接跑新的不就行了
- **Cary**：比如 ContextEngine 要保存运行数据、Artifacts 里有之前的结果，意外终止后这些东西怎么删？是不是重新启动就默认删除？要不要专门写意外终止的处理办法，每次启动先检查有没有上次的残留？
- **field**：为了让意外退出后下次能正常启动、正常使用，每次启动都必须清空；M1 不管正常退出还是意外退出都清空，否则想不到方便的实现办法
- **Cary**：同意，就这样实现
- **结论：M1 不支持继续未完成的运行；正常退出时卸载模块；每次启动时清空上次运行留下的数据。**

> **点评**
>
> 支持“启动时不恢复任何状态”。field 一开始的说法（“启动后直接跑新的”）其实是对的：只要新运行不读旧数据，残留就不会妨碍启动。Cary 担心的“第二次起不来”，只在多次运行共用状态时才会发生。“清空”这一步有三个代价，建议实现前确认：
>
> 1. **和 #19 的落盘表冲突。** #19 建议步骤记录、权限申请与回答、用量记录“落盘、只追加”，用途是事后查看、审计。启动即清空，这些记录只能活到下次启动。
> 2. **影响评测和排查。** 评测（`scripts/grade.ts` 这类）和排查问题都要在运行结束后读运行记录；#6 的安全测试还要检查“假 key 不出现在审计记录中”。一跑完、重启一次，证据就没了。
> 3. **删除是有风险的操作。** 清空代码一旦路径算错，删掉的可能是别的目录；如果同时开了两个实例，后启动的会删掉正在运行的那个的数据。
>
> 一个同样简单的替代：**每次运行写进自己的目录（`runs/<runId>/`），启动时不读任何旧目录。** “不读”和“删除”一样容易实现，同样保证意外退出后能正常启动，但记录还在。磁盘占用可以用“只保留最近 N 次”控制，或者以后统一回收。
>
> 如果坚持清空，至少：只删 MultiAgentOS 自己的数据目录（写死根目录，删除前校验路径），并把运行记录（步骤记录、审计、用量）排除在外。

### 4. 运行轮次上限与额度限制（对应备忘 2.4、2.5）

- **Cary** 提问：如果两个 Agent 反复互相调用、一直不结束，Workflow 需要限制最高轮次；以后还会有 API 额度限制。第一版要不要实现？Cary 的预想是都不需要实现（已发到群里）
- **field**：Monitor 只维护额度，终止原因只有一个：额度不足立即终止，其他都不做
- **Cary**（推断）解释：实际产品一般不会在额度用完时直接终止，否则用户拿不到任何输出；通常是到额度时追加一条 prompt，让 Agent 立即生成报告。明确说不是要求 M1 实现
- **Cary**：要实现真实功能，不是只留一个壳。直接中断就没有输出，所以设**两个阈值**：
  - **软阈值**：到了以后让 Agent 生成报告，然后结束
  - **硬阈值**：到了以后立即终止
- **field** 问：是 Monitor 监控用量，还是实时监控 API 运行？
- **Cary**：用量超过阈值，Gateway（门禁）就不放行任何请求
- **field**：理解为 Monitor 向 Gateway 报告异常，Gateway 驳回请求，Workflow 根据驳回信息做相应处理
- **Cary** 补充：除了 Monitor 这一层，还需要**单次 API 调用的限制**。现在的逻辑是到额度后下一个 Unit 进不来，但如果一次调用思考了十万 token、跑了四十分钟，也要能截断。由 Execution / Executor 自己判断，还是由 field 的 Monitor 判断？
- **field**：目前的想法是直接终止本次调用、丢弃结果，简单处理；再考虑一下
- **Cary** 总结：M1 会有 API 额度上限和循环（轮次）上限
- **结论：M1 实现 API 额度上限（软、硬两个阈值）和轮次上限。硬阈值由 Monitor 发现、Gateway 驳回。单次调用限制的归属待定（field 考虑）。**

> **点评**
>
> 1. **Cary 最初“都不需要实现”的预想和他自己在 #15 的评论矛盾。** #15 写的是：没有轮次上限，模型原地打转时运行不会结束；#6 的安全测试“死循环在上限处停下，并给出停止原因”也靠它。轮次上限不是功能，是“运行一定会结束”的保证，实现成本只是 Workflow 里一个计数器。最后的结论保留了轮次上限，这一点没问题。
> 2. **“两个 Agent 互相调用”不会出现，真正的风险在单个 Agent 内部。** 按 #15 的单向移交，只有 Planner → CodeViewer。会打转的是 CodeViewer 自己反复读文件：M0 每次调用只给 JSON 状态时，10 次中 8 次重复读取，有一次一直读到 16 次上限。
> 3. **field 的“额度不足立即终止”只适合作为硬阈值。** 直接终止意味着前面所有调用的费用都白花了，用户什么也拿不到。Cary 提出的两个阈值解决了这个问题。
> 4. **软、硬阈值之间的距离至少要够一次完整的报告调用。** M0 里最终报告约 5k 输出 token，输入是整个上下文；如果两者挨得太近，软阈值触发后的那次报告调用会直接撞上硬阈值，又回到什么都拿不到。建议把软阈值定义成“剩余额度不够再走一轮工具调用加一次报告”，或者干脆按调用次数触发（倒数第二次调用后进入收尾）。
> 5. **软阈值由 Workflow 判断，硬阈值由 Monitor / Gateway 执行。** 软阈值要求的是“再发一次调用、只许交报告”，这是业务决定，只能由 Workflow 做；Workflow 从每个 Unit 结果带回的用量就能算出来（Cary 在 #15 已定“用量结构化上报”）。实现上就是 #18 第 4 节的 `finalCall`：最后一次调用把 `tool_choice` 指定为提交报告的工具，末尾加一句提示，报告照常走结构检查。硬阈值是兜底拒绝，用的是 Cary 在 #15 预留的“额度不足”拒绝原因。
> 6. **单次调用的限制不需要实时监控，应该写进请求本身。** 这回答了 field 的问题“是不是实时监控 API 运行”：M1 不做流式输出（#15），调用进行中根本看不到用了多少 token，Monitor 也就无从判断。可行的只有两件事，都由 ModelExecutor 在发请求时设置：`max_tokens`（输出上限，由模型服务端截断）和超时（时间上限）。两个数值放在 MODEL Unit 的输入或模型定义里，Executor 只负责执行。所以这个问题的答案倾向于 Execution。需要确认：DeepSeek 的 `max_tokens` 是否包含思考部分。
> 7. **field 说的“丢弃结果”可以，但用量不能丢。** 被截断的调用已经计费，必须照常上报用量（field 自己在 #17 也说了：结果被拒绝也不能抹去已经发生的消耗）。另外，如果被截断的恰好是最后那次报告调用，又会没有输出；兜底可以是把已读文件和已有的中间结论作为“未完成报告”展示，并注明原因。
> 8. **需要同步文档**：Cary 在 #15 写的“M1 对资源额度只记录，不限制”被本次结论推翻，#15 那条评论要更新。

> **点评**
>
> 1. **“判定和 M0 一样”要先说清楚指什么。** 如果指最终报告的验收（只能通过收尾工具提交、引用必须落在已读范围内），同意，Cary 在 #15 的验收评论已经采纳。如果指错误分类，M0 的三类有两处已被后续讨论改掉：技术重试改由 Execution 负责（#14 Cary）；工具名不存在、参数不是合法 JSON 不再直接让运行失败，而是交还模型一次（#14 meti）。
> 2. **Cary 问的“写文件给工具还是交给 Kernel”不是二选一，两者都要。** 工具是模型表达意图的方式，Kernel 是授权方：模型调用 `write_file`，Gateway 按 Lease 检查路径和“写”操作，必要时请用户 Y/N。
> 3. **通用 EXEC 工具本质上就是 bash。** field 说的“命令行也要封装成工具”是对的，但包了一层工具，并不会让命令变安全：`exec("rm -rf …")` 和直接给 bash 没有区别，而且 Gateway 看不出一条命令会读写哪些路径，Lease 的路径检查就失效了。建议：没有沙盒之前，只给**用途单一的工具**（读、搜索、列目录，以后加写文件 / 打补丁），每个工具的参数里能看出操作对象，Kernel 才能检查；EXEC / bash 等有了沙盒再给（与 #4 中 meti、Cary 的意见一致）。
> 4. **field 说“bash 怎么用靠提示词”，但安全不能靠提示词。** 提示词决定模型“用得好不好”，安全必须由 Kernel 和沙盒保证，这部分仍然是 Kernel 的职责。#6 的“README 里的注入指令”测试就是在检验这一点：模型看到注入后完全可能照做，只有 Gateway 拒绝才算守住。
> 5. **模型偏好命令行不是问题。** M0 只给 `file_read` 一个工具，模型 10/10 跑通；工具描述写清楚，模型会适应给定的工具集。

### 6. M1 用户流程与人类在环（对应 #15、#13、备忘 2.7）

**Cary** 概述 M1 的用户流程：

- 程序初始化后提示用户输入 prompt
- 用户输入 prompt 之后，只能做两件事：**终止**，或者**授予权限**；没有其他操作
- **不支持二次输入**：中途改方向不行，拿到报告后再追问也不行
- 最后给用户一份报告或结果，结束后不能继续提问
- **人类在环**：用户一开始给出仓库地址，系统询问这个地址能否访问、是否安全，用户回答 Y 或 N
  - Y：继续
  - N：怎么处理还没想好，应该不难
- Cary 问大家：对 M1 的任务规划有没有问题

**结论：M1 单次输入、单次输出；运行中用户只能终止或授权；访问仓库前问一次 Y/N。N 的处理待定。**

> **点评**
>
> 1. **支持，这和备忘 2.7 一致**（开始时问一次 Y/N），也和 Cary 在 #13 的评论（“先问用户能否信任这个仓库”）、field 在 #17 的范围一致。
> 2. **这段话实际上把暂停 / 恢复移出了 M1。** “只能终止或授权”意味着没有暂停和恢复，而 #15 正文和 #19 都还写着暂停、恢复。这样 #19 问题 1–6 大部分可以关掉，Workflow 也不用实现“暂停中”的状态。需要在 #15、#19 写明。
> 3. **“授予权限”只在开始时，还是运行中也会有？** 如果只在开始时问一次，运行开始后用户就只剩终止，Workflow 不需要“等待授权”的挂起状态，实现最简单。建议 M1 明确只在开始时问。
> 4. **N 的处理建议：直接结束运行，状态写明“用户拒绝访问仓库”。** 前提是 **Y/N 在第一次模型调用之前问**，这样拒绝不花一分钱。“没有仓库访问也给一个有限回答”（#15 问题 6）留到有 Planner 的阶段再说。
> 5. **问 Y/N 之前，系统先检查路径。** 路径是否存在、是不是目录、解析符号链接后的真实路径；Lease 绑定真实路径，否则用户同意的是 A，实际读的可能是链接指向的 B。
> 6. **Y/N 提示要写清楚“代码会发给模型服务”。** #15 已经要求说明仓库路径、允许的操作、范围，以及代码片段是否发送到配置的模型服务（M1 是 DeepSeek）。这是用户真正需要知道的信息，不能只问“是否安全”。
> 7. **用户回答 Y 也不等于所有文件都能读。** #6 要求假 `.env`、写死的假 key 不出现在上下文里；如果 FileReadExecutor 没有排除规则，用户一答 Y，`.env` 就可能被读进去发给模型。建议 M1 的只读 Lease 默认排除 `.env`、密钥文件这类路径。

### 7. 模型回复如何变成 Unit，以及格式错误的处理（#14）

- **meti**：今天回复了 #18 和 #14
- **Cary** 讲解 #14 的 Unit 与队列机制：
  1. 用户输入 prompt 后，Workflow 初始化，创建第一个 AgentRun，**默认第一个永远是 Planner**
  2. Workflow 在 Unit 等待队列里先放两个 Unit：**① ContextEngine 组装上下文；② 模型调用（MODEL CALL）**
  3. 模型回复有三种：调用工具、handoff（移交给其他 Agent）、直接结束并提交结果。ModelExecutor 把回复包装成 ModelTurnOutput（名字可以再考虑），交回 Workflow
  4. Workflow 先检查格式。不合法的情况：回复不符合规则、调用了不存在的工具、其他格式错误。不合法时，Workflow 再排一组“组装上下文 + 模型调用”，把错误信息放进上下文，让模型重新生成
  5. **重新生成最多 3 次**；3 次都失败，就当作这个 Agent 失败，把错误返回给用户，WorkflowRun 结束（一个 prompt 进、一个结果出，整个过程是一个 WorkflowRun）
  6. 合法的工具调用由 Workflow 转换成 Unit
  7. **handoff 用最简单的方式**：A 交给 B 之后，A 就结束了，不等待 B 的结果；B 如果要再交出去，就交给一个新的 AgentRun。这样整个过程是严格串行的
  8. **错误归属**：
     - 纯技术错误（例如 404、连接超时）：Execution 直接重试，**最多 3 次**；都失败就把失败结果交给 Workflow
     - 模型给出了回复的：Execution 不做任何处理，直接交给 Workflow；由 Workflow 判断格式是否正确、历史是否满足要求、工具是否合法
  9. **同一轮的工具调用全部完成后才调用模型**：例如两次模型调用之间有 A、B、C 三个工具调用，A 成功、B 失败、C 成功，也要等这一轮全部结束，再把所有结果（包括 B 的错误）交给模型，由模型决定要不要重试、怎么用这些信息；不会 B 一失败就立刻调用模型
  10. 工具格式错误、某个工具没有权限这类问题，由 ContextEngine（meti）在组装上下文时加进去，交还给模型重新调用一次
- Cary 问大家对这部分有没有问题，没有人提出
- **结论：采纳 #14 的流程；技术错误由 Execution 重试（最多 3 次），其余交给 Workflow 判断；同一轮的调用全部有结果后再调用模型；错误由 ContextEngine 放进上下文交还模型。**

> **点评**
>
> 整体流程和 #14 正文一致，也和 meti 在 #18 的 StepRecord、#14 的纠错回复对得上。有四处需要在会上说清楚：
>
> 1. **“格式错误就整条回复重来”和 Cary 自己在 #14 的结论冲突。** Cary 在 #14 评论里定了“同一轮的调用各自独立，每个都有自己的结果”。如果模型一轮发 4 个调用，其中 1 个工具名不存在，按会上的说法是整条回复作废、重新生成；按 #14 的结论，应该是另外 3 个照常执行，只有出错的那个得到一条错误结果。建议分两层：
>    - **单个调用的错误**（工具不存在、参数不是合法 JSON、路径不合法）：这个调用记为 `REJECTED`，结果写 `Error <CODE>: <说明>`，其他调用照常执行（meti 在 #18 的 `ToolCallOutcome`）
>    - **整条回复的错误**（没有调用任何工具、直接用纯文本作答；提交结果和其他调用混在同一轮）：用一条反馈消息（StepRecord 的 `notice`）交还模型
> 2. **出错的那条回复要留在历史里，不能丢掉重来。** Cary 在 #18 定了历史“只追加”。错误回复保留下来，模型才看得到自己刚才做了什么；而且协议要求每个 `tool_call` 后面都有对应的 tool 消息，所以出错的调用也要有一条结果——这正好就是第 1 点的错误结果。
> 3. **“3 次”要说清楚怎么数。** 是连续 3 次不合法，还是整个运行累计 3 次？Cary 在 #15 写过“纠错次数与重新提交次数共用预算”。建议：**连续** 3 次不合法才失败（中间有一次合法就清零），每次重新生成也计入轮次上限。另外 M0 加了错误处理后的 70 次真实运行里一次都没触发过，这个数值不用纠结。
> 4. **“第一个 AgentRun 永远是 Planner”和议题 1 的分阶段有关。** 如果采纳分阶段，第一阶段的第一个（也是唯一一个）AgentRun 是 CodeViewer。建议写成“第一个 AgentRun 由 WorkflowDefinition 决定”，两种阶段都不用改代码。

> 补充一个小点：队列里的模型调用 Unit 依赖前一个组装 Unit 的输出（ContextPack 引用），入队时输入还不完整。#14 正文“队首条目的输入准备好后再提交”已经覆盖了这一点，实现时注意即可。

> **对第 7–9 点的点评：**

> 5. **第 9 点同意**，和 #14 Cary 的评论、meti 在 #18 的 StepRecord 一致。它覆盖的是“执行失败”（B 执行了但失败）。第 1 点说的是“检查不通过”（B 的工具名不存在、根本没执行）——建议同样处理：B 记为 `REJECTED`，A、C 照常执行，一起交给模型。这样两种失败走同一条路，Workflow 也更简单。
> 6. **404 不是技术错误，不应该重试。** 404 表示请求的地址或资源不存在，重试 3 次结果一样，只是白等。meti 在 #14 的回复给过区分：连接失败（请求没发出去）、429、5xx 可以重试；**请求已发出后超时**最多重试 1 次，用量记为“未知”；其他 4xx 不重试。超时尤其要小心：如果单次调用超时设成 10 分钟，重试 3 次就是 40 分钟，而且因为思考太长导致的超时，重试大概率还是超时（和议题 4 的单次调用限制直接相关）。
> 7. **文件读取的“文件不存在”也不是技术错误。** Execution 判断“技术错误”时，要把 `FILE_NOT_FOUND`、行号越界这类排除在外，它们应该作为 `ERROR` 结果交给模型，而不是重试。
> 8. **重试产生的用量要上报。** 重试的模型调用同样计费，要计入 Monitor 的用量（Cary 在 #14 列的待定项 3），否则硬阈值会漏算。
> 9. **handoff 链要有限制。** 第 7 点允许 B 再交给新的 AgentRun，比 #15 的结论更宽（#15：只有 Planner → CodeViewer，CodeViewer 不能再移交）。M1 只有两个 Agent，建议仍按 #15 限制；以后放开时，要给 handoff 次数设上限，否则 A → B → C → … 也是一种不会结束的循环。另外，轮次上限和额度应该按整个 WorkflowRun 累计，不能每次 handoff 后重新计数。
> 10. **“A 交出去就结束”同意。** B 拿到的是“任务 + 移交说明”（#18 Cary 的评论），移交说明应该作为 handoff 工具的参数，由 Workflow 检查后放进 B 的 `task.handoffNote`。

### 8. Unit 结果怎样返回 Workflow（对应 #17 field 的第 3 点）

- 起因：讨论到模型提交结果（Show_Result）怎样返回
- **field**（昨天已和 Cary 讨论过）：结果存在 Artifact Store，这点同意；但不要发给 Kernel、再由 Kernel 转交。返回只能是：Execution 先做一次“系统调用”，把句柄（`outputRef`）交给 Gateway，进入 Kernel 判断；Kernel 判断接收后，由 **Execution 直接返回给 Workflow**，结果本身不经过 Kernel 转交
- **Cary**：Workflow 需要的也只是这个句柄。为什么不是 Execution 把句柄交给 Gateway，Gateway 判断后**直接把句柄交给 Workflow**？两边要的是同样的数据
- **field**：系统调用是一去一回，不是去了不返回；再想一下
- **Cary**：field 的方案会让一部分数据链条跳过 Kernel，按自己原来的架构设想这很危险；但也能理解 field 的说法
- **field**：没有跳过。Execution 申请了鉴权，鉴权失败结果就不会返回。Gateway 在逻辑上**不承担转交职责**，只做“弹射”（重定向）。外界与 Kernel 的交互分三种：
  1. **可信信息传递**：例如 Execution 上报运行信息，不经过 Gateway，走可信信道直接传给 Kernel
  2. **系统调用**：请求发给 Gateway，Gateway 鉴权后陷入内核
  3. **持有 Lease 的调用**：Gateway 检查 Lease 后，直接弹射（重定向）到 Execution
- **Cary**：第 3 种里，Workflow 把请求交给 Gateway，Gateway 判断后交给 Execution；那为什么 Execution 把句柄交给 Gateway 后，Gateway 不能直接交给 Workflow？这不对称
- **field**：第 3 种里没有句柄，只是一个请求：要执行工具，必须把 Lease 交给 Gateway 检查，再由 Gateway 重定向。如果这样也觉得不对称，可以改成：Workflow 先申请 Lease、Gateway 判断，然后 **Workflow 直接交给 Execution**。总之 Gateway 不承担中转职责
- **Cary**：改成这样完全没意见。但这样它就不该叫 Gateway，而是“系统调用”了：两个组件各自去做系统调用，它不再是一个门口
- **field**：它仍然是门禁：要么放进、要么放出、要么拒绝，为什么不能叫 Gateway？
- **Cary** 总结：Gateway 不做任何中转，Workflow 也不中转。**Workflow 把请求直接交给 Execution 之前，先找 Gateway 判断一次；Execution 把结果交还 Workflow 之前，也先找 Gateway 判断一次。** 暂定这样
- 关于对称：**field** 认为没必要对称，很多设计都不对称，例如 Linux 的 fork；**Cary** 认为这两件事很像，应该一样处理
- **Cary**：两种方案差别不大，关键是 Gateway 有没有“过门而不入”（只判断、不转交）的职责。Kernel 是 field 的部分，请 field 直接定一个，Cary 照着做
- **field**：**不中转**
- **Cary** 复述：Workflow 交给 Execution 之前调用一次 Gateway，通过后传递；Execution 返回时也调用一次 Gateway，通过后传递
- **Cary** 问：需不需要 Fabric 参与？
- **field**：用信道传输，肯定要经过某种信道（Fabric）。问题是：如果所有跨模块调用都当作 Port，是**先通过检查再上信道**，还是先上信道再检查？——倾向先通过检查再上信道
- **结论：Gateway 不中转（field 拍板）。请求和结果都是“发送方先调用 Gateway 检查，通过后经 Fabric 信道直接交给接收方”。**

**接着讨论 Gateway 和 Core 的分工：**

- **field**：使用内核受保护的服务，必须先发消息给 Gateway。返回有两种：
  1. Gateway 拦截，Gateway 直接返回
  2. 陷入内核，内核直接返回，**不再经过 Gateway**
- **Cary**：这样接口太多了吧？（不是效率问题，是要设计很多接口）
- **field**：内核已经做出的决定，不同意再经过一次 Gateway，太麻烦，直接由内核返回。Gateway 是通往内核的单向通道，内核再通过单向通道发给其他模块；可以写一个消息缓存池统一分发
- **Cary** 问：Gateway 会拒绝哪些消息？
- **field**：目前最明显的是租约（Lease）不满足，其他的以后再说
- **Cary** 问：Lease 不满足被 Gateway 拒绝了，那 Core 要处理什么？
- **field**：Core 只负责签发 Lease，到期时向 Gateway 发请求更新快照。**Gateway 持有所有 Lease 的快照**
- **Cary**：既然 Gateway 有快照，为什么不由 Gateway 直接判断，通过、不通过都直接返回给 Workflow，不再经过 Core？
- **field**：对，**Unit 带着 Lease 时，Gateway 按快照检查，有没有都直接返回，不经过 Core**。没有 Lease 时陷入内核，内核把签发的 Lease 直接返回，接收方是两个：Gateway（更新快照）和 Workflow（拿到 Lease）
- **Cary** 问：提交 Unit 给 Gateway 审核，和提交权限申请，是两件事吗？不可能只有工具调用才需要审核
- **field** 讲原则：**Gateway 是替内核分担职责的。Gateway 能做出安全、权威的判断时，就不进内核；Gateway 无法判断时才陷入内核。内核的返回不经过 Gateway，最多通知 Gateway 一声**
- **Cary**：没有意见
- **结论：模块之间可以建立直接传递消息的信道，但每次传递之前，必须先向 Gateway 确认权限。**
  - **提交 Unit**（带 Lease）：Gateway 按 Lease 快照检查，通过或拒绝都直接返回，不进内核
  - **申请权限**（没有 Lease）：Gateway 判断不了，陷入内核；Core 签发 Lease 后直接返回给 Workflow，并更新 Gateway 的快照
  - Core 负责签发 Lease；Lease 到期时更新 Gateway 的快照

> **点评**
>
> 两个方案传的都只是句柄，正文都在 Artifact Store，区别只在“谁把句柄交给 Workflow”。我倾向 **Cary 的方案（Gateway 直接交给 Workflow）**，理由：
>
> 1. **用 field 自己的“一去一回”也能推出 Cary 的方案。** 这里其实有两次系统调用：Workflow 提交 Unit（Workflow → Gateway），以及 Execution 请求确认结果（Execution → Gateway）。按“一去一回”，Execution 那次的“回”是接收决定，回给 Execution；Workflow 那次的“回”是执行结果，应该从 Gateway 回给 Workflow。Cary 的方案两次都是一去一回；field 的方案里，Workflow 提交的请求最后是从 Execution 那里“回”来的。
> 2. **省掉一次核验。** field 在 #17 写了：Workflow 不能信任 Execution 自报的 accepted，要拿接收决定再去 Gateway 核验一次。如果句柄和决定直接由 Gateway 交给 Workflow，来源本身就是可信的，不需要再核验。field 的方案是 Execution → Gateway → Execution → Workflow → Gateway，Cary 的方案是 Execution → Gateway → Workflow。
> 3. **Kernel 转交的只是句柄和决定，不是正文。** field 担心的“Kernel 中转执行输出”在这里不成立，转交的数据量和 field 方案里 Execution 交给 Workflow 的一样。
> 4. **和 Cary 在 #17 的第 5 条一致**：Workflow 提交 Unit 后先得到受理回执，结果由 Kernel 另行投递，改成 IPC 后也成立。
>
> 对 ContextEngine 没有影响：无论哪种方案，Workflow 拿到的都是 `outputRef`，写进 StepRecord，ContextEngine 再从 Artifact Store 读正文（#18）。
>
> **对后续讨论的点评：**
>
> 5. **分歧的根源是：现在的方案一半“经过 Gateway”、一半“直接交付”。** 请求经 Gateway 重定向到 Execution，结果却由 Execution 直接交给 Workflow。Cary 说的“不对称”指的就是这个，这个质疑是成立的：“重定向”本身就是转发一条消息，把结果重定向回最初的请求方，是同一种操作的反方向。
> 6. **其实有两种都说得通的模型，选一种做到底即可：**
>
>    | | A：经 Gateway 中转（Cary） | B：凭证直连（field 最后提的替代） |
>    |---|---|---|
>    | 请求 | Workflow → Gateway → Execution | Workflow 向 Gateway 申请凭证，再直接交给 Execution |
>    | 结果 | Execution → Gateway → Workflow | Execution 向 Core 申请接收决定，再直接交给 Workflow |
>    | 怎样防伪造 | 接收方只信 Gateway 这条通道，按真实来源判断 | 凭证和接收决定要能被接收方**独立校验**（签名或向 Gateway 核验） |
>    | M1 工作量 | 小：单进程里通道来源天然可信 | 大：要实现凭证签发和校验 |
>
>    不好的是两者混用：请求按 A、结果按 B，接收方既要信通道又要校验凭证。
> 7. **M1 建议选 A。** field 在 #17 自己写过“判定必须由可信边界根据真实调用来源作出，不能由外部消息自行宣称”，A 正好做到这一点；B 是更彻底的能力模型，适合以后多进程时再做。
> 8. **field 的第 1 种交互和 #17 不一致。** #17 写的是“Execution 的调度请求、结果确认、用量与故障上报……均须经过 Gateway”，今天说运行信息走可信信道、不经过 Gateway。需要在 #17 更新为准。
> 9. 建议会后由 field 在 #17 画一张三种交互的时序图（请求、结果、用量各走哪条路），比口头讨论更容易收敛。
>
> **对暂定结论的点评：**
>
> 10. **暂定结论就是上表的 B，而且是两个方向一致的 B，不再混用，这比之前好。** 我原来建议 M1 选 A 是因为工作量小；既然选了 B，就要补上 B 的前提：**接收方必须能独立确认“发送方确实找 Gateway 判断过”。** 否则某个组件有 bug、跳过了 Gateway，接收方完全察觉不到，Gateway 就形同虚设。field 自己在 #17 也写过“不能信任 Execution 自报的 accepted”。
>     - 最简单的做法：Gateway 每次判断都返回一个决定 ID，绑定 Unit、Attempt 和输出 hash；发送方把决定 ID 随消息一起交出去，接收方拿它向 Gateway 核验一次
>     - 这个决定 ID 要写进 contracts 的消息结构里
> 11. **名字之争不影响设计。** 在 B 里，Gateway 是“做授权决定的地方”，真正执行检查的是接收方（核验决定 ID）。叫 Gateway 也可以，只要文档写明它“只判断、不转发”。
> 12. **对称之争：两人说的都有道理，但这里 Cary 更对。** 对称本身不是目标，field 说得对；但这两个方向面对的是同一个问题——“一个组件把数据交给另一个组件，需要 Kernel 背书”——同一个问题用同一套机制处理，实现和审计都更简单。fork 的不对称是因为两边的语义不同，这里两边语义相同。
> 13. **需要同步 #17。** Cary 在 #17 的边界第 1 条写的是“Workflow 不直接调用 Execution”，暂定结论改成了 Workflow 判断后直接交给 Execution，那条要改。
> 14. 对 ContextEngine 仍然没有影响：CONTEXT Unit 由 Execution 调用 ContextEngine，ContextPack 的引用按同样的方式交回 Workflow。
>
> **对 Fabric 讨论的点评：**
>
> 15. **“先检查再上信道”顺序对，但谁来保证发送方真的检查过？** 如果只靠发送方自觉，就回到第 10 点的问题。Fabric 正好可以解决：field 在 #17 写过 Fabric 是 Kernel 管辖的通信基础设施，它本身是可信的。建议让 **Fabric 在投递前核验决定 ID**——没有有效决定 ID 的消息，Fabric 不投递。这样：
>     - “先检查再上信道”由信道强制执行，不依赖发送方守规矩
>     - 接收方不用再单独找 Gateway 核验，少一次调用
>     - Gateway 仍然只判断、不转发，业务逻辑上没有中转，field 的原则不变
>     - M1 单进程里，Fabric 就是进程内 Adapter，核验只是一次查表
> 16. **检查和投递之间有时间差。** Gateway 判断通过后、消息送达前，Lease 可能刚好过期或被撤销。M1 的 Lease 按整次运行签发，这个窗口可以接受；以后有中途撤销时，要么在 Fabric 投递时再查一次，要么规定“以判断时刻为准”。
> **对 Gateway / Core 分工的点评：**
>
> 17. **“Gateway 能判断就不进内核”是好原则**，相当于快速路径和慢速路径：日常的 Unit 检查只查快照，只有签发 Lease 这类少见的事才进内核。Cary 担心的“接口太多”，实际数下来大约 5 个：Gateway 检查 Unit；申请 Lease（陷入内核）；Core 把 Lease 交给 Workflow；Core 更新 Gateway 快照；Monitor 告诉 Gateway 额度已用完（见第 20 条）。可以接受。
> 18. **Lease 到期不需要 Core 推送。** 快照里存了到期时间，Gateway 检查时自己比较即可；需要 Core 主动通知的只有“提前撤销”。M1 的 Lease 按整次运行签发、不中途撤销，所以 M1 里 Core 到 Gateway 的更新只在签发时发生一次，实现更简单。
> 19. **结果方向还没说清楚。** 今天讨论的全是请求方向（Unit 能不能交给 Execution）。结果方向上，Execution 交还 Workflow 之前“找 Gateway 确认”的是什么？Lease 管的是“能不能做”，管不到结果。field 在 #17 写过“Core 保留结果接收权、接收决定绑定 Attempt 和输出 hash”——按今天的原则，结果接收是 Gateway 能判断，还是每次都要陷入内核？如果每次都进内核，结果方向就是每个 Unit 都走慢速路径。需要 field 明确。
> 20. **额度检查也可以按同样的原则放进 Gateway。** 议题 4 定了“超过硬阈值时 Gateway 驳回后续请求”。按今天的原则，Monitor 在用量超过硬阈值时更新 Gateway 的快照（和 Core 更新 Lease 快照一样），Gateway 检查 Unit 时一并检查额度，不需要每次问 Monitor。
> 21. **回答 Cary 的“不可能只有工具才需要审核”：对，模型调用也需要 Lease。** 模型调用会把仓库代码发给 DeepSeek，议题 6 的 Y/N 提示要说明这一点，所以用户回答 Y 时签发的 Lease 应该同时覆盖“读仓库”和“把代码发给模型服务”两项，CONTEXT、MODEL、工具调用三类 Unit 都按它检查。
> 22. **Gateway 通过之后，Execution 仍要自己守住路径。** Gateway 检查的是 Unit 里声明的参数（例如路径在仓库内）；Execution 实际读文件时，还要解析符号链接、确认真实路径仍在仓库内。否则 `repo/link -> /etc` 这样的路径可以通过 Gateway 的检查。
> 23. **第 15 条（Fabric 核验决定 ID）还没有讨论到。** 现在的方案仍然是“Workflow 问过 Gateway 后，自己把 Unit 交给 Execution”，Execution 无法确认 Workflow 真的问过。
>
> 24. **按今天的结论，Scheduler 在 #14 的路径上没有位置。** 长期架构（`feature/M1/kernel-docs` 的 Overall.md、Protocol.md）里 Scheduler 负责：为就绪步骤选择 Executor 实例、在 API 池里分配容量、管理调度代次、中断时阻止新推进。M1 里这些都退化了：每类 Executor 只有一个实例；Workflow 的等待队列已经保证一次只交出一个 Unit；中止时由 Gateway 拒绝或 Workflow 停队列即可。而今天定的路径是“Workflow 问过 Gateway 后直接交给 Execution”，Scheduler 根本不在路上。建议在 #14 / #17 写明：**M1 的执行顺序由 Workflow 的等待队列决定，Scheduler 不参与**，这与议题 2 的“串行调度”是一回事；以后需要容量控制时，Scheduler 放在 Gateway 判断之后、Execution 之前。注意不要出现两个队列（Workflow 一个、Scheduler 一个）各管一套顺序。
> 25. **内核处理是毫秒级，所以“多一步”“快速路径”都不是性能问题**（M0 里模型调用以外的执行合计只有 12 毫秒）。今天几处争论（Gateway 要不要多走一步、Kernel 返回要不要经过 Gateway）应该按接口数量和信任关系来定，而不是按快慢。
>
> 26. **和 ContextEngine 有关的问题：ContextEngine 读 Artifact Store、AgentToolPool 这两个只读 Port，要不要经过 Gateway 检查？** field 在 #17 写的是“非 Kernel 主体之间的合法通信不要求统一由 Gateway 中转”，#18 写的是“在授权范围内只读访问”。授权范围由谁检查（Artifact Store 自己、Fabric，还是 Gateway），需要明确；这决定 ContextEngine 读 Artifact 的接口要不要带决定 ID 或运行身份。

> **点评**

### 10. Kernel 与 Execution 是否解耦，Scheduler 调度的是什么

> **点评**
>
> 1. **两人说的确实不是一个层面。** field 说的是操作系统层面的并发（进程、fork/exec），Cary 说的是 Unit 层面的排队（有限资源下谁先开始）。**Cary 的定义和长期架构一致**：Overall.md 写的是“Scheduler / Monitor 为就绪步骤选择 Executor、分配资源”，Instance.md 写的是“多个就绪模型步骤由 Scheduler 在 API 池中安排容量”。
> 2. **field 的新理解是对的，而且正好说明 Scheduler 该管什么。** API 不是 CPU，紧缺的不是计算能力，而是**可计数的配额**：同时允许几个请求（并发数）、每分钟多少次（限流）、还剩多少额度（Monitor）。这种资源用“信号量”管理就够了，不需要进程调度。用 Python 类比：`async with api_slots: await call_model()`，`api_slots = asyncio.Semaphore(1)`。
> 3. **在我们的实现里，API 调用不会 fork 进程。** MultiAgentOS 是 Node（TypeScript），模型调用是同一个进程里的异步 `fetch`，就像 Python 的 asyncio + aiohttp：一个进程里同时等待多个请求，由事件循环负责并发。所以“面向所有进程还是只面向 API 进程”这个问题在 M1 里不存在。fork/exec 的模型以后适用于沙盒里执行命令的工具（bash 之类），那时由 Supervisor 管，不是 Scheduler。
> 4. **这样“跨两层”的问题就解开了，不需要两层都调度：**
>
>    | 层 | 决定什么 | 例子 |
>    |---|---|---|
>    | Workflow | 哪些 Unit 已就绪（业务依赖） | 组装上下文完成后才能调用模型 |
>    | Kernel 的 Scheduler | 已就绪、已通过 Gateway 的 Unit **什么时候可以开始**（按资源类别限并发） | 模型调用最多同时 1 个；文件读取不限 |
>    | Execution | **怎样执行一次**（重试、超时、`max_tokens`） | 连接失败重试最多 3 次 |
>
>    Scheduler 和 Monitor 都在做资源记账（一个管并发槽位，一个管用量额度），放在 Kernel 里合理；Execution 只管执行，不做调度。
> 5. **M1 里仍然不需要实现。** 已定串行、只有一个 API，Workflow 的等待队列就等于一个容量为 1 的信号量。和议题 9 的点评一致：M1 不实现 Scheduler，保留接口位置；以后要并行时，按第 4 条的位置加一个按资源类别的信号量即可。
> 6. **field 最早的设想（Executor 是无状态元件、状态都在 Kernel）和现在的文档不一致。** #15 正文写的是“Execution 创建并维护 UnitAttempt”，也就是 Attempt 状态在 Execution。解耦后状态归谁，需要写进 #17。
> 7. **SessionCheckpoint 还原旧会话不是“调度”**，而是恢复。而且议题 3 已定 M1 每次启动清空、不支持继续旧运行，这部分和 M1 无关，建议会上不要展开。
> 8. 建议会后请 Cary 和 field 在 #17 各用一句话写下“Scheduler 决定什么”，先对齐定义再讨论放哪一层。
>
> **对 field 澄清后的点评：**
>
> 9. **到这里两人的意思已经一致了**：Scheduler 只管占用有限资源（API）的 Unit，其他 Unit 依赖满足就直接执行。可以当场确认，作为这个议题的结论。
> 10. **建议把“API”推广成“资源类别”。** 每个 Unit 声明自己占用哪类资源（模型 API、以后的联网搜索 API 等），每类资源有自己的槽位数；不占用任何资源的 Unit 不经过 Scheduler。这样以后加新的有限资源，不用改 Scheduler 的逻辑。
> 11. **“每个 Unit 起子进程”在我们的实现里不需要。** Node 里读文件、发请求都是异步 I/O，同一个进程里就能同时进行；为每次文件读取起一个子进程，开销反而比读文件本身大得多（M0 里模型调用以外的执行合计只有 12 毫秒）。子进程留给以后需要隔离的工具（沙盒里执行命令）。这是实现细节，不影响上面的结论。
> 12. **“不涉及 API 的 Unit 全部可以并行”只对只读操作成立。** 以后有写文件的工具，两个写同一文件的 Unit 即使不占 API 也不能同时执行——这正是 Cary 在 #10 Q2 说的“并行的难点在写操作”。到那时需要按资源（文件路径）加锁，可以用同一套“资源类别”机制表达。
> 13. **以上都是长期设计，M1 仍按议题 2 串行执行**，不要因为这段讨论把同轮并行带回 M1。
>
> **对“合进去还是摘出来”的点评：**
>
> 14. **建议摘出来，Scheduler 放在 Kernel，Execution 在 Kernel 之外。** Scheduler 不必“横跨两个模块”：它的输出是一个决定——“这个 Unit 现在可以开始”，和 Gateway 的检查是同一种东西。Execution 在执行占用 API 的 Unit 之前申请槽位、执行完释放，就是一个客户端调用：
>
>     ```text
>     Execution → Scheduler.acquire(资源类别, unitId) → 获得槽位
>     Execution 执行 Unit
>     Execution → Scheduler.release(槽位)
>     ```
>
>     这和议题 8 刚定的原则一致：“发送方先问 Kernel，再自己执行”。解耦的代价就是这一对接口，加上一条规则：Execution 崩溃时槽位按超时自动回收（和 Lease 到期是同一套逻辑，Kernel 已经要做）。
> 15. **field 喜欢的操作系统类比，正好支持这个方案。** Linux 的调度器在内核里，被调度的进程在内核外；进程通过系统调用和阻塞与调度器交互，调度器不需要“跨两层”。反过来，“合进去”相当于把用户进程放进内核。
> 16. **“合进去”会扩大可信范围。** Executor 处理的是模型输出和外部工具结果，以后还有沙盒里的命令，都是不可信的输入；放进 Kernel，Kernel 要信任的代码就变多了。field 在 #17 坚持“外部主体必须经过 Gateway”，就是为了让 Kernel 小而可信，合进去和这个方向相反。
> 17. **Scheduler 放 Kernel，还因为它和 Monitor 是一对。** Monitor 管用量额度（议题 4 的软、硬阈值），Scheduler 管并发槽位，两者都在给有限的 API 资源记账，放在一起最自然。如果 Scheduler 放进 Execution，以后有多个 Execution 实例时，就没有一个地方统一分配同一个 API 的槽位。
> 18. **区块链的比喻不太贴切。** 区块链的安全来自互不信任的多方达成共识；我们的模块是同一个团队写的同一套代码，安全来自权限最小化和清晰的边界。解耦的价值在于让 Kernel 小、边界清楚，而不是“分布式”本身。
> **对后续讨论的点评：**
>
> 19. **field 的矛盾来自把“API 资源”和“执行”当成一个东西。** Kernel 要管的是**配额**（还剩几个槽位、还剩多少额度），这是一个计数；Execution 做的是**用掉配额去执行**。计数和执行本来就是两件事：数据库连接池和执行查询、令牌桶限流和真正的请求，在任何系统里都是分开的。所以不是“一个东西拆成两半”，而是“一个分配者 + 一个使用者”，粘合只需要 acquire / release 两个调用。
> 20. **field 想要的“分布式、非管家式”，现成的例子是 Kubernetes。** 调度器在控制平面，只决定“这个任务去哪、什么时候跑”；kubelet 在各个节点上真正执行；配额由 API Server 统一管理。控制平面不执行任何任务，这正是 field 说的“Kernel 不管执行”。对应到我们：Kernel = Gateway + Core + Monitor + Scheduler（只做决定和记账），Execution 在外面执行。
> 21. **Cary 担心的“除了 Workflow 都归内核”，只在 Execution 放进 Kernel 时才成立。** 写 Artifact、调用 ContextEngine、执行工具都是 Execution 的事；Execution 在 Kernel 外，Kernel 就只剩权威状态和权限，不会变成管家。所以“Execution 解耦”恰好解决了 field 的顾虑；一个只做计数的 Scheduler 留在 Kernel，并不会让 Kernel 变成管家。
> 22. **Cary 提的“先做 M1 再看”，field 说得对：M1 不做并发调度，什么也看不出来。** 但也不需要为了验证而把复杂的并发调度带进 M1（违背议题 2，M0 数据也显示没有收益）。
> 23. **M1 其实不用现在拍板，只要守住接口边界。** 无论以后选哪种，M1 的做法都一样：Execution 单独一个包，Kernel 只通过 `ExecutionAdapter` 这个接口调用它（`feat/M1` 现在就是这样），不实现 Scheduler。以后选“合进去”，把这个包部署在 Kernel 里即可；选“摘出来”，在 Kernel 加 acquire / release。**唯一要避免的是 Execution 的代码直接读写 Kernel 的内部状态**，那样两条路都会被堵死。
> 24. **避免再次“不了了之”：写一条带触发条件的决定。** 例如在 #17 记下：“M1：Execution 独立成包、经接口调用；Scheduler 不实现。**出现第二种需要限流的资源，或要做同轮并行时**，再决定 Scheduler 放在哪里。”有了触发条件，这件事就有明确的重新讨论时间点。
>
> **对 Monitor 收集用量的点评：**
>
> 25. **其实并不“频繁”。** M1 不做流式输出，用量只有在一次调用结束时才知道（模型服务在响应里返回 token 数）。一次运行大约 10–20 次模型调用，平均二十秒左右才有一条用量。M1 是单进程，Fabric 是进程内调用，耗时是微秒级。专用高速信道解决的是一个不存在的性能问题。
> 26. **不需要新信道：用量跟着结果一起报。** 议题 8 已定：Execution 交还结果之前要先找 Gateway 确认。用量直接放在这次确认请求里，Gateway 收到后更新 Monitor，每个 Unit 一次，不用 Monitor 主动去收集。好处：
>     - 不增加任何接口，也不需要专用信道
>     - 失败、被拒绝的调用照样经过这一步，用量不会漏（field 在 #17 说的“结果被拒绝也不能抹去已经发生的消耗”）
>     - Execution 重试 3 次的用量可以一并报上来（议题 7）
>     - Monitor 更新后如果超过硬阈值，直接更新 Gateway 的快照，下一个 Unit 就会被拒绝（议题 4、议题 8 点评第 20 条），整条链路都在 Kernel 内部
> 27. **真正的问题是信任，不是速度。** Execution 在 Kernel 外，Monitor 只能相信 Execution 报上来的数字（用量来自模型服务的响应，Kernel 没法自己核对）。这就是 field 说的第 1 种交互“可信信息传递”。field 想要的“专用信道”，本质上应该是“这条信道上的数据被 Kernel 当作可信”的约定，而不是一条更快的信道。M1 接受这个信任即可，在文档里写明。
> 28. **调用进行中的用量不需要监控。** 单次调用的上限靠请求里的 `max_tokens` 和超时（议题 4 点评第 6 条），所以 Monitor 不需要在调用过程中收集任何东西。唯一会丢用量的情况是 Execution 在调用中途崩溃，M1 每次启动都清空（议题 3），可以接受。
>
> **对“M1 把 Execution 放进内核”的点评：**
>
> 29. **作为 M1 的决定可以接受**，它能让卡住的讨论往前走，而且 Cary 自己也说了到 M4、M5 影响都很小。但要附两个条件，否则以后就拆不出来了。
> 30. **条件一：区分 Execution 层和 Executor。** field 最早的设想其实是两层：**Execution 层**（管 UnitAttempt、重试、写 Artifacts、上报用量，有状态）放进内核；**各个 Executor**（ModelExecutor、FileReadExecutor 等，无状态，只负责“执行一次”）留在内核外，通过接口调用。这个划分是自洽的：
>     - Scheduler 和 Execution 层都在内核里，“横跨两层”的问题消失，Monitor 收集用量也是内核内部的事
>     - 处理不可信输入的部分（模型输出、文件内容、以后沙盒里的命令）仍在内核外，Kernel 不用信任它们
>     - Cary 担心的“除了 Workflow 都归内核”只成立一半：内核管“执行的记账”，不管“执行本身”
> 31. **条件二：“内部权限隔离”要落到代码上，不能只靠约定。** 建议 Execution 层在 Kernel 里仍是单独的目录或包，只通过接口和 Core / Monitor 交互，不直接读写它们的状态；用 pnpm workspace 的包边界（或依赖检查工具）让越界的 import 直接编译失败。这和第 23 条一样：守住接口，以后想拆出去只需改部署位置。
> 32. **和议题 8 的结论不冲突，反而更简单。** Execution 在内核里，Workflow 交给 Execution 就是“经 Gateway 进入内核”；Execution 把结果交还 Workflow 就是 field 说的“内核返回不经过 Gateway”。第 26 条的“用量跟着结果确认一起报”也变成内核内部调用。
> 33. **对 ContextEngine 的影响：** #17 写的“ContextEngine 的调用方是 Execution”不变，只是 Execution 现在在内核里。ContextEngine 的接口不用改，但议题 8 点评第 26 条的问题（ContextEngine 读 Artifact Store 要不要检查、由谁检查）变得更好回答：由内核里的 Execution 层在调用 ContextEngine 时把允许读的范围一起传进来。
>
> 34. **M1 只需要决定代码放在哪个包里。** `feat/M1` 现在没有单独的 Execution 包，Kernel 通过 `ExecutionAdapter` 接口调用执行（`packages/kernel/src/index.ts`），这已经是“摘出来”的结构。建议 M1 就保持接口分离：Execution 单独一个包，Scheduler 不实现（议题 9），以后加 Scheduler 只需在 Kernel 里加 `acquire / release` 两个接口。
