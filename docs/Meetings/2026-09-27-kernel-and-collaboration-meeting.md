## 议题 1：Kernel 的可信划分与角色（field 汇报）

**field：**
- 按操作系统的思路区分可信与不可信：我们自己的模块可信；执行器、用户工具、模型输出不可信。
- Kernel 内部划分 Gateway、Kernel Core、Supervisor、Resource Broker 等角色；Resource Broker 必须可信，可信计算基（TCB）要尽量小。
- 草案中还有 ExecutionPermit、bootEpoch、fail-closed（出错时默认拒绝）等机制。

**讨论要点：**
- 这些角色在 M1 是**逻辑分层**，不是独立进程；Executor、Tool、Broker 是角色，M1 里可以合在一起。
- 原“权限态”的说法更接近操作系统里的“保护域 + 能力（capability）”，建议改用后者的概念。
- M1 里真正的风险不是“不可信进程”，而是：提示注入导致越界读取、把 `.env` 等敏感内容发给模型服务商、危险动作、成本失控。
- **Cary：** Agent 在 M5 之前不会运行程序。【待确认：与 M2 计划运行测试的说法冲突，见第 8 节待决事项】

**会后说明：** M1 建议的 Kernel 子集是：单进程、逻辑分层、准入检查、审计记录、错误分类、模型密钥只由模型适配器持有、预算的预留与结算账本。第一个真正不可信的进程出现在“运行用户仓库的测试”时，届时再引入容器隔离。

## 议题 2：身份伪造、预算与模型适配器

- **身份伪造：** 解决办法是身份和权限字段从不取自模型输出。现实中更要防的是“绕路”：路径技巧、借 shell 绕过限制、修改测试让它通过、诱导用户批准。
- **预算与配额：** Kernel 负责记账（执行前预留、执行后结算，按运行和按天设上限）；Workflow 负责业务上的步数控制和预算快用完时的收尾；另外 API 账户只预充小额余额，作为最后一道保险。
- **模型适配器：** 放在模型执行器里，负责对接各模型服务商的 API。建议命名为 **ModelAdapter**，不叫“LLM Gateway”，避免和 Kernel 的 Gateway 混淆。
- **静态架构规则：** 只有 Kernel、执行器、ContextEngine 可以引入文件系统、子进程和模型 SDK，由 CI 自动检查。

## 议题 3：检查点、模块生命周期、只读访问与 Lease

- **检查点分三层：** Workflow 负责业务检查点；ContextEngine 不存状态，恢复时重建；从 M2 开始需要工作区的 git 快照。
- **模块生命周期：** M1 中五个模块常驻；只有不可信的执行实例按单次尝试创建。
- **只读访问：** 执行过程中读取 AgentToolPool 的定义、读取运行产生的档案，不算受保护资源，不需要每次经过 Kernel 审批；读取用户仓库文件仍由 Kernel 按单元准入。
- **Lease：** 有时限的独占 + 心跳 + fencing token，属于 M3 多 Agent 并行的议题，M1 不做。

## 议题 4：开发环境、跨平台与界面

- 统一版本：Node 24.19.0、pnpm 11.25.0、TypeScript 6.0.3。
- Cary 用 Windows（PowerShell），meti 用 macOS（arm64），field【待确认】。
- 支持 Windows 和 macOS 开发，CI 在 Linux 上跑；需要 Linux 专有能力时用容器或虚拟机（Windows 上的 Docker Desktop 依赖 WSL2）。
- 需要注意：文件名大小写不敏感、BSD 与 GNU 命令行工具差异、arm64 与 x64 差异。
- 只做 CLI。以后如需展示，只读的运行记录与评测查看页成本低，适合演示；实时交互界面难度大，暂不考虑。

## 议题 5：模型选型与缓存命中率

- 开发和测试默认使用 DeepSeek Flash；Pro 只用于对照实验。9 月 24 日官方价格：缓存命中输入与未命中输入的单价相差约 50 倍；工作日有高峰时段，高峰价是低峰的两倍。
- **field（以使用者身份分享）：** 缓存命中率非常关键。用 DeepSeek 时命中率只要下降 5%–10%，成本就可能涨到两三倍；DeepSeek 之所以便宜，是因为命中率可以做到 99% 左右。
- **结论：** 缓存命中率作为核心指标。ContextEngine 通过稳定前缀保证命中率，模型调用的用量记录中必须包含“命中缓存的 token 数”，评测报告单列这一项。

## 议题 6：Kernel 的开发节奏（field 汇报）

**field：**
- Kernel 内部逻辑复杂，涉及进程与框架，要基本做完才能开放使用，无法保证一周内完成。
- 提议：在 Kernel 完成前，其他模块可以先不经过 Kernel；Kernel 完成后删除这些旁路，或者用系统错误把它们堵上。
- 模块之间的通信可能要用 RPC，与 Kernel 设计相关，之后单独讨论。

**Cary：** 原本的设想也是所有交互（包括 Workflow 与 Kernel 之间）都经过 Kernel，先听 field 的完整设计。

**会后说明（meti 的提议，待决）：** 用“直通版 Kernel”代替旁路：先按 Kernel 的接口写一个只转发、不做检查的实现，所有模块从第一天起都通过 Kernel 的接口调用；完整版写好后直接替换实现，调用方一行不用改。旁路以后要逐个找出来删除，漏掉一个就是安全漏洞。

## 议题 7：Git 分支、issue、CI 与工作日志（由 Cary 写入 Style.md）

- **分支：** `feat/<版本>` 是受保护的集成分支，只有 Owner 能创建；`feature/<版本>/<部分>[-<主题>]` 是工作分支，例如 `feature/M1/context-engine-search`。除版本号外全部小写，部分与主题之间用连字符，不再用斜杠分层。合并后删除工作分支。
- **同步：** 可以直接把 `feat/M1` 合并进自己的工作分支，不需要为同步另开 PR。
- **issue：** issue 是工单，不只用于报告问题，也用于拆分开发任务（父 issue + 子 issue）。判断标准：不会马上做完、之后有人要跟进的事就建。会议待办、决策（decision）、评测失败案例都用 issue 记录。
- **CI：** GitHub Actions，每个 PR 运行 `pnpm run check`；设为必须通过的检查；CI 中不调用真实模型。
- **工作日志【提出人待确认】：** 只看 commit message 很难定位 bug，只能二分回滚查找。每天开发结束后让 AI 自动总结，写进共享文档。命名为 `docs/WorkLogs/YYYY-MM-DD-<成员短名>.md`，随当天的工作分支提交。重点记录“行为变化”和“疑点”，查 bug 时先看日志缩小范围，再用 `git bisect` 精确定位。
- **周报：** 每周一个周报 issue，每人周五前回复一条。

## 议题 9：协议怎么定义

**Cary：** 每个模块的第一个 PR 要保证接口完备，内部可以是半成品，只要有一条跑通的通路。文档里只写协议在哪个文件，不要在文档里把类抽象地写一遍。

**讨论（field【待确认】）：** 对象非常多（Agent 定义、AgentRun、Unit、UnitRun 等），要不要全部用文字写进 Interface 文档？还涉及进程间通信，需要等周三 Kernel 文档推上来后再研究。

**结论与建议：**
- **“接口完备”的检查标准：** (1) 类型定义进入 contracts 并导出；(2) Port 的每个操作都能调用，返回合法结果或结构化错误，不能直接抛异常，也不能假装成功；(3) 提供 fake 实现，供别人写测试；(4) 有 contract test。
- **代码是唯一权威：** 跨模块接口用 TypeBox 写在 contracts 中，按领域拆成多个文件。M1Interface 只做索引：名字、负责人、生产方与消费方、文件位置、一句话含义。文字只写类型表达不了的规则：谁生成 ID、调用顺序、幂等性、超时后谁重试。
- **只有跨模块传递的数据才进 contracts**，模块内部类型留在各自的包里。
- **草稿阶段**的接口讨论放在 PR 或 decision issue 中，定稿合并后文档只留指针。给人看的简报用一个真实的 JSON 例子代替抽象定义。
- **IPC：** M1 单进程直接调用函数。只要跨模块数据能转成 JSON（不传函数和类实例，时间用 ISO 字符串，大对象用 ArtifactRef），以后改成跨进程几乎不用改接口。

## 议题 10：模块之间怎么共享信息

**问题（Cary 或 field【待确认】）：** M1 没有 SQL，工具调用的结果怎么交给 ContextEngine 生成下一轮上下文？要不要读写权限？要不要加锁？

**meti 的方案：**
1. Kernel 执行完一个单元，把结果存入 Artifact Store，返回取件单（ArtifactRef）。
2. Workflow 把每一步记为 StepRecord：步骤序号、动作、结果的 ArtifactRef。
3. 下一轮 Workflow 发 ASSEMBLE 请求，带上全部 StepRecord（只有取件单，没有正文）。
4. ContextEngine 凭取件单从 Artifact Store 读取正文，决定原样放入、截断还是压缩，然后组装模型输入。

**为什么不需要锁：** Artifact Store 按内容哈希命名，只写一次、永不修改，多方同时读取是安全的。会变化的状态（运行状态、StepRecord 列表）只有它的负责人能修改，别人拿到的都是副本。

**权限：** 在组合根中只给 ContextEngine Artifact Store 的只读接口。以后换成 SQL，也只是改成“只读查询负责人的表”，“单一写入者、其他人只读”的原则不变。

**待定：** StepRecord 的具体格式（meti + Cary）。
