## 议题 1：Unit 的定义与 Agent 内部回退

**Cary：**
- 一个 Agent 由多个 Unit 组成，例如取上下文 → 生成 prompt → 调用 API → 根据返回调用工具，具体步骤由 Agent/Tool 模板规定。
- Unit 有两个作用：它是交给 Kernel 调度和执行的最小单位；也是保存状态和返回的基本单位，因为一次 API 调用无法中途暂停保存。
- Agent 内部可以回退到之前的 Unit。例如工具调用失败后，回到上上个 Unit 重新调用 API。

**会后技术评注：**
- Unit 作为“执行和状态保存最小单位”的理解是正确的，与 DBOS 的 step、Temporal 的 activity 是同一个概念。
- “出错就回退到之前的 Unit”与主流做法相反。主流 Agent 的做法是把工具错误作为工具结果追加进对话，由模型根据错误信息换一种做法。原因：(1) 错误本身是信息，回退会抹掉教训，模型可能重犯；(2) 回退内存状态撤不回已经发生的文件修改和命令副作用。
- 回退适合的场景是**用户主动撤销**，可以用“会话日志 + git 快照”实现，不需要 DBOS。

## 议题 2：Process Scope Tree（任务树）

**Cary：**
- 这是本项目相对主流工作流最大的区别。Planner 把任务拆给前端 Agent、后端 Agent 后，传统方式下它们互不知道对方存在，也不知道对方何时开始、何时结束。
- 任务树把任务结构传递下去：子节点能看到父节点目标（例如“实现一个分布式系统”）和兄弟节点（例如“实现后端”），从而知道自己的任务边界，避免多个 Agent 做重合的工作。
- 设想用任务树为 Agent 提供权限范围：Agent 负责任务的哪个部分，决定它需要什么权限，再向 Kernel 申请，Kernel 批准后才实际获得。

**会后技术评注：**
- 要解决的问题真实存在，是多 Agent 协作的核心难题。
- 但它不是原创。Anthropic 公开的多 Agent 研究系统经验里，子 Agent 也会重复劳动，解决办法正是由主 Agent 明确写出每个子 Agent 的目标、输出格式和任务边界；MetaGPT、CrewAI 也有类似的层级分解。建议对外表述为“借鉴并实现了”，而不是“主流没有”。
- 任务树只能传递**静态**信息（兄弟在做什么），无法传递**动态**决定（例如后端把某个字段改了名）。动态冲突要靠 Planner 事先定好接口约定，再加一块共享公告板。
- **用任务范围限定权限**是这一议题里最有价值的想法，实现也便宜：Planner 为每个子任务声明允许修改的路径和可用工具，由 Kernel 在每次工具调用时检查。建议在多 Agent 阶段实现。

## 议题 3：DBOS 与检查点回溯

**Cary：**
- Workflow 的 Durable Runtime Adapter 用 DBOS 实现。
- DBOS 保存每个 checkpoint 的全部状态，可以从 checkpoint 3 跳回 checkpoint 2 或 1。
- 这既可以用于崩溃恢复，也可以用于用户修改目标后回溯到某个状态重新开始。

**会后技术评注：**
- 这里对 DBOS 的理解有偏差。DBOS 主要做**向前恢复**：记录已完成 step 的结果，崩溃后从断点继续执行；它也支持从某一步分叉出新工作流，但只恢复它自己记录的程序状态，**撤不回**磁盘文件、git 状态和外部 API 调用。
- “用户改目标后回溯”需要同时回退对话和文件，这要靠 git 快照加会话日志。
- 对本地 CLI 来说，崩溃后重新运行并从会话日志继续，已经能满足绝大多数需求。

## 议题 4：TaskGraph 状态机

**Cary：**
- 状态包括 Pending、Ready、Running、Success、Failed、Skipped，具体在定义状态机时再确定。
- 依赖满足后从 Pending 进入 Ready；Ready 的任务交给 Kernel 调度，进入 Running；由 Kernel 判定 Success 或 Failed，失败则打回。
- 整个工作流通过状态机在图上向后推进。

**会后技术评注：**
- 这是 Airflow 等工作流系统的标准设计，正确且实现成本低。注意顺序应为 Pending → Ready → Running，转写中有一处顺序颠倒。
- 需要讨论的是“谁判定 Success”。按现有文档，Kernel 只判定执行层面的成败（命令是否执行成功），任务是否真正完成由 Workflow 验收（例如测试是否通过）。会上的说法与文档不一致，需要统一。

## 议题 5：Agent 如何向 Kernel 请求能力；Communication Fabric 放在哪里

**田园：**
- Agent 向 Kernel 请求能力的机制应该类比系统调用，作为请求内核服务的统一公共接口。
- Communication Fabric 应该放在 Kernel 里面，由 Kernel 维护。放在外面，Agent 容易操控它；放在 Kernel 里，权限更收缩，否则还得对它单独再做一套权限保护。
- （第 2 段开头）如果 Fabric 只是一个缓冲区信道，放在外面没有问题；但支撑这个信道的机制必须放在内核里。

**Cary：**
- 所有 Infrastructure 只代表“跨模块存在”，本身不负责维护业务。Fabric 连接的是所有模块之间的交互，不只是和 Kernel 的交互，所以应当独立于 Kernel 存在；Kernel 可以设二级组件来管理它们。
- 除 Kernel 外，没有任何东西能执行操作，Agent 也运行在 Kernel 提供的运行环境里；如果 Agent 能自行破解，放在哪里都一样。
- Module Host 只负责启动时初始化各模块和最后收尾，相当于 runtime 主线，不做管理。
- Kernel 有观察整个系统所有组件（四个 Module、五项 Infrastructure）的监测权限，具体监测哪些内容等写 Kernel 设计时再定。田园的想法和这个规划一致。

**会后技术评注：**
- 两人各对一半，实际上在讨论两种不同的“通信”：
  1. **模型 → 系统的请求（工具调用）**：内容由模型生成，不可信，必须经过 Kernel 检查。田园说的“系统调用”在这里完全正确：工具注册表就是系统调用表，每次工具调用就是一次系统调用。
  2. **模块 → 模块的调用**（如 Workflow 调 ContextEngine）：都是团队自己写的可信代码，单进程内就是普通函数调用。Router 放在 Kernel 内外，对安全没有影响。
- 模型只能输出文字和工具调用请求，碰不到任何模块的代码，因此不存在“Agent 操控 Fabric”的问题。Cary 的“除 Kernel 外没有东西能执行”是对的。
- 统一的类比：**五个模块都在“内核态”，只有模型输出在“用户态”。** 真正的安全边界在“模型输出”和“真实副作用”之间，而不在模块之间。
- 单进程的 M1 实际上不需要 Fabric。Module Host 在 M1 中就是一个 `main.ts`，相当于操作系统的 init 进程。

## 议题 6：异常处理

**田园：**
- 异常分两类。第一类是编程错误：用户不可能触发、预期上完全不可能发生的错误，应像 xv6 的 `panic` 或 C++ 的 `assert` 一样直接终止整个系统；不需要单独组件，用语言特性或一个函数即可。
- 第二类是运行时错误，可能由用户或 Agent 引起，需要一个“异常监测”组件。例如 Agent 使用内核资源，但检查权限令牌发现没有相应权限，即为越权，需要处理。
- 越权监测和权限签发不是同一件事，就像传统操作系统里进程创建和进程运行维护是两个部分。它是一个小但重要的模块，不需要成为一级 Module。

**Cary：**
- 目前只考虑过“中断”，没有考虑过“异常”。中断包括用户暂停或更换任务：用户提交给 Kernel，Kernel 传给 Workflow，Workflow 通过 DBOS 跳回需要修改的节点，重新生成 Prompt，再正向执行。Agent 内部认为做不下去、需要返回某一步重来，也属于正常中断，走同样的机制。
- 越权监测应放在 Kernel 权限管理器的二级组件里，因为签发权限和检查越权本应是同一个东西。如果另设 Kernel 以外的组件来管，就要给它访问这两类信息的权限，反而更危险。

**会后技术评注：**
- 田园的两类划分正确，且是业界通用做法（Rust 的 `panic` 与 `Result`、Erlang 的“让它崩溃”）。第一类用 assert 快速失败即可，但崩溃前应确保会话日志已写盘，以便重新运行后继续。
- 但遗漏了实践中**最常见**的两类错误，建议补充：
  - **外部依赖错误**：API 超时、429 限流、网络中断、模型返回的 JSON 格式非法。处理方式是有限次重试加退避。
  - **模型行为错误**：工具参数错误、编造不存在的文件、原地打转没有进展。这些**不应当作异常处理**，而是作为工具错误结果返回给模型，同时用步数上限和无进展检测兜底。
- 关于越权，操作系统本身就给了答案：进程 `open()` 一个没有权限的文件，内核返回 `EACCES` 错误码，**不会 panic**。对应到这里：Agent 越权时，Kernel 拒绝并向模型返回“权限不足”；多次越权再终止这个 Agent（类似内存越界时内核向进程发 `SIGSEGV`）。只有 Kernel 自身的不变量被破坏时才 panic。
- “签发与监测是否分开”之争，两人各对一半：
  - 田园的直觉对应操作系统经典原则“**策略与机制分离**”：规则（谁能做什么）是数据，检查是代码。
  - Cary 的直觉对应安全领域的“**完全仲裁**（reference monitor）”：每次访问都必须经过同一个检查点，这个检查点要小、要无法绕过。
  - 落到代码上：一份策略配置加一个在每次工具调用入口执行的检查函数，放在同一个包里。只要所有副作用都经过这个入口，就不需要事后监测越权；事后监测只在检查入口管不到的地方才需要，例如 bash 命令内部的行为，而那要靠沙箱来约束。
- Cary 所说的“中断 → DBOS 跳回 → 重新生成 Prompt”方案，见议题 8 的评注，存在更简单的做法。

## 议题 7：微内核还是混合内核

**田园：**
- 【待确认：开头一句“我的思想偏向于微内核”可能是田园或 Cary 所说】
- 主张混合内核：必要的部分放进同一个内核整体运行，通信高效；Workflow 这类运行频率高的模块，如果每次都要走模块间通信机制，会降低效率。
- 建议在现有“四个一级模块 + 五项基础设施”基础上再精简，想清楚哪些必须放在内核里、哪些放在外面，关键是判断必要性。目前只是一个意见，具体方案还没有想好。

**Cary：**
- 【待确认】表示自己想的是微内核。
- 前两天专门考虑过这个问题：AI 的建议是，Agent 系统和操作系统最大的区别是需要极大的动态性和可变性，宏内核会让项目死板，后续替换组件（例如把 DBOS 换成别的技术）很复杂。
- 希望 Kernel 的具体设计由田园负责，因为田园更熟悉操作系统，Kernel 以内还有很大的设计空间。

**会后技术评注：**
- 这场争论建立在一个不成立的前提上。微内核和宏内核的取舍，关乎地址空间隔离与跨进程通信的开销；而本项目所有模块都在同一个进程里，模块间通信就是函数调用，耗时在微秒级。一次模型调用要几秒到几十秒，模块通信的开销可以忽略不计，**性能不是需要考虑的因素**。
- “以后能替换 DBOS”这类灵活性，靠的是接口（端口与适配器），与内核风格无关。
- 结论：当前阶段就是“带清晰模块划分的单体”，这个问题可以暂时搁置。田园提出的“按必要性判断放不放进去”，是本议题最有价值的原则。

## 议题 8：用户体验与 Session

**田园：**
- 从软件工程角度，目前的用户端体验很差。系统可以是研究性质的，但最终要为用户服务。
- 缺少供后续扩展的接口，特别是没有 Session。主流 Agent 都依靠 Session，每个对话窗口就是一个 Session。没有它，上下文会无限膨胀；只能单 Session，新建会话就会清空原来的，同一时间只能有一个项目，管理能力太弱。
- Session 之上还应该有一层抽象（管理多个 Session），否则会混乱。这一点要在文档里写出来，因为后面用 AI 实现时，AI 不会主动考虑这个问题。

**Cary：**
- 目前处于框架阶段，完全没有考虑用户体验。
- Agent 系统不能给用户太大的权限，用户无法直接指定下一个依赖或下一个 Agent，最多通过 prompt 控制。用户可以通过 Kernel 查看正在运行的 process、Agent 和依赖图（可以可视化）；如果想改变，必须终止运行并重新输入提示词。
- 项目已经过于复杂，实现时甚至需要精简，不可能再设计复杂的用户系统，最多预留扩展范围。三个月内能否实现单 Session 都很难说，所以没有考虑多 Session。
- Session 很容易实现：DBOS 能回到任何 checkpoint，把 checkpoint 包装成 Session，下次调用时选择回到哪个 checkpoint 即可。Session 之上的一层抽象可以再想，但与底层架构不矛盾。
- 会后建群，请田园把意见整理后发出来。

**会后技术评注：**
- 田园的判断是对的：Session 是 Agent 产品的核心概念。后续版本文档中已加入 WorkSession、PromptRevision，说明这条意见已被采纳。
- 但 Session 比双方想的都简单。在主流 Agent 里，**一个 Session 就是一份对话记录**（消息列表加元数据），通常存成一个 JSONL 文件。恢复就是读回文件，新建就是新开文件，多项目就是按目录区分文件。例如 Claude Code 把会话记录按项目目录分别保存。不需要 DBOS。
- **Session 不等于 checkpoint。** 层级应为：项目（目录）→ Session（一份对话记录）→ 轮次 → 步骤。checkpoint 是 Session 内部的某个时间点，用于撤销。
- **“修改目标必须终止并重新输入”并不必要。** 在对话式 Agent 里，用户中途纠正就是往对话里追加一条消息，主循环读到后自然会调整方向。Claude Code 就是按 Esc 打断，再输入新的指示。这比“Kernel → Workflow → DBOS 跳回 → 重新生成 Prompt”简单得多，也更好用。

## 议题 10：用父子 Agent 缓解上下文膨胀

**田园：**
- 设想：一个长对话 Agent 注入系统提示词后，每遇到一个具体任务就派生一个子 Agent，子 Agent 继承父 Agent 的全部上下文，完成后返回一份摘要，注入父 Agent 的上下文。这样能“治标不治本”地维持持久性。
- 改进版：子 Agent 发现项目方向有偏移时返回一份小摘要，由父 Agent 再派生一个新的子 Agent 并给出新提示。
- 如果这个机制做好，Agent 会更像人，拥有“自我”。

**Cary：**
- 这个想法与工作流的关系更大，而不是与上下文。
- 父子来回传递，双方要花很长的上下文解释发生了什么、需要改什么。更好的做法是：子 Agent 完成后，根据自己了解到的信息和整体项目目标，直接生成下一个 Agent 继续任务。
- 这与现有工作流系统完全兼容，不需要改动 Workflow；只需要在 AgentToolPool 中定义具有这种功能的 Agent。

**会后技术评注：**
- 田园的设想正是 Claude Code 子 Agent（subagent）的做法，已被主流产品验证有效。有一处需要修正：子 Agent 通常**不继承**父 Agent 的全部上下文，而是只拿到一份任务说明、在一个干净的上下文里工作，这样才能起到隔离细节、为父 Agent 节省上下文的作用。
- Cary 提出的“子 Agent 完成后直接生成下一个 Agent”是接力式交接（handoff）。它的问题是没有一个始终掌握全局目标的协调者，链条越长越容易偏离目标。需要全局一致性的任务，主流做法仍是由父 Agent 协调、子 Agent 返回摘要，也就是田园的方案。
- 实现上，子 Agent 就是父 Agent 的一个工具：调用这个工具，就在里面跑一遍新的 Agent 主循环，返回摘要文本，大约几十行代码。**子 Agent 返回的摘要应该包含什么、多长、什么格式**，本身就是一个上下文工程问题，适合由 ContextEngine 负责，可以作为较早实现的功能。

## 议题 11：主体、工作对象与执行对象的分层（田园提出的新概念）

> 本段从“那天讨论完以后”开始，可能是会议后半段，也可能是会后的另一次讨论。【待确认】

**田园：**
- 要给每个“主体”合理的抽象层次。主体指用户和 Agent，两者都有思考能力：用户是人的思维，Agent 是大模型提供的概率性思考资源。
- 抽象出两类对象：
  - **工作对象**：项目、作业、任务、attempt、run 等，面向用户和 Agent，是他们唯一能直接操控的对象。
  - **执行对象**：process、Unit 等运行细节，对 Agent 遮盖，由系统通过映射和硬编码自动完成。Agent 确实需要时，再自己去查询执行对象的具体信息。
- 目的是不让 Agent 去思考它不需要思考的运行细节。

**Cary：**
- Unit 以及 Kernel 的调度几乎全是硬编码的，除权限授予可能需要 Agent 参与外，其余都不需要 Agent。Unit 的协议写在 Contract 里还是写在 AgentToolPool 的 Agent 定义里，还没有确定，但一定是确定的协议；每种协议经过 Kernel 的哪些设施、交给哪个执行器，都是硬编码的。
- Agent 能知道什么，完全由我们自己定义：Agent 只知道 prompt。AgentToolPool 规定某个 Agent 需要哪些部分的信息，ContextEngine 负责把这些信息整理出来。例如 Planning Agent 需要知道整体意图、已有任务和后续计划，这些信息经 ContextEngine 整理后交回 Kernel，再交给 Workflow，最后发给 API。
- 这个概念在理论上有指导意义，但与现有实现不矛盾，不需要修改。

**会后技术评注：**
- 田园的分层思想是正确的，而且非常重要。它不算全新：软件工程里有“信息隐藏”原则（Parnas，1972）；针对 Agent，SWE-agent 论文提出了 **Agent-Computer Interface（ACI）**，核心观点就是要专门为模型设计交互界面，隐藏它不需要的细节。这个研究表明，界面设计本身就能显著影响 Agent 的成功率。对外可以表述为“基于 ACI 思想的分层”。
- Cary 说“Agent 只知道 prompt”，这一点正确，两人实际上是一致的。但这个原则最有用的地方，是指导**工具设计**：暴露给 Agent 的工具应当是“工作对象”层级的动作，例如“读取文件”“创建子任务”“提交结果”，而不应该让 Agent 去“提交一个 UnitIntent”。它同样适用于用户界面：给用户看任务和进度，不给用户看 Lease 和 UnitAttempt。
- 建议把“Agent 需要时自己查询执行细节”限定为**只读的诊断信息**（例如错误原因），不开放执行层的控制能力。
- Agent 能看到什么，由 AgentToolPool 声明需要什么、ContextEngine 负责组装，这个分工合理。决定 Agent 看到什么抽象层次，本身就是上下文工程的一部分。

## 议题 12：项目—作业（Session）层级与多 Session 之间的信息共享

**田园：**
- 用自己的概念对照 Workflow 文档：WorkflowRun 相当于一个 Session，也就是一个“作业”（job）；作业之上还应该有“项目”。
- 例子：一个酒店管理系统项目，下分三个作业，分别是后台、PC 端前端、安卓端前端。
- 参照 Codex：新建项目，先开一个只包含初始信息的 Session，再明确从它 fork 出三个子工作 Session，Codex 可以做到。
- 希望设计一种让这些 Session 共享信息的通信机制，但这取决于有没有办法实现。

**Cary：**
- 如果三个 Session 分别用三段不同的提示词、各自从零开始，结果一定互相矛盾，例如数据结构不通用。即使在 Codex 里这么做，三部分也会完全无关。
- 可以在提示词里说明要做前端、后端、API 三部分，但必须从同一个起点开始，在任务树里作为三个平行分支。在他的概念里，抽象就是从 job 开始的。
- 即使从同一个对话 fork 出三个，它们之间的信息也完全不共享，没有实际价值。设计 Session 之间的信息共享机制极其困难。
- 他的解决方案是 Process Scope Tree。

**会后技术评注：**
- 两人各对一半：
  - Cary 说得对：三个互相独立、没有共同设计的 Session，拼起来的结果一定会冲突。
  - 但田园提出的“项目”这一层在主流产品里真实存在，而且 Session 之间的信息共享**并不难**。**共享的介质就是仓库本身**：同一个代码仓库、同一份项目记忆文件（AGENTS.md / CLAUDE.md）、同一份接口约定文件（例如 API 规格）。Claude Code 的“项目”就是一个目录，这个目录下所有 Session 共享同一个代码库和同一份 CLAUDE.md。现实中三个开发团队也是这样协作的：共享一个仓库和一份接口文档，而不是共享大脑。
  - Cary 说“fork 出来的对话信息绝对不共享”，只对了一半：对话上下文确实不共享，但工作区是共享的。这既是协作的基础，也是冲突的来源，所以并行时需要 worktree 隔离加最后合并。
- Cary 说“必须从同一个起点开始”，对从零开始的新项目成立。对一个已经存在的项目，**仓库当前状态加上项目记忆文件本身就是共同起点**，后续新开的 Session 都从这里出发。
- 建议统一层级：**项目**（共享仓库、项目记忆、接口约定）→ **Session / WorkflowRun**（一个目标的一次运行）→ **任务树**（运行内部的任务分解）。Cary 的任务树管一次运行的内部，田园的项目层管多次运行之间，两者不冲突，应当同时存在。

## 议题 13：任务树的重新命名与“派遣公司”类比

**Cary：**

**会后技术评注：**

  - 接口约定 = 施工图纸：让兄弟任务在交界处对得上，避免冲突。
  - 共享公告板 = 现场协调会：记录施工过程中临时做出的决定。

## 议题 15：权限态与鉴权隔离

**田园：**
- 目前的设计里没有“权限态”这个概念，可以考虑加上。权限必须由内核鉴权。
- 传统操作系统之所以安全，是因为有硬件支持，例如 RISC-V 的 Machine、Supervisor、User 三种模式。我们的系统跑在普通操作系统之上，无法借用操作系统的权限门来做跨权限态的调用。
- 设想：把鉴权做成一个独立的服务器，类似 MCP 服务器，可以独立于程序，也可以是程序的一部分，绑定一个网络端口来通信。所有请求都必须经过这个鉴权服务器，它相当于门禁。
- 澄清：Kernel 保存所有权限相关的文本，鉴权服务器只是门禁，要从 Kernel 获取权限状态再做判断。独立出来的目的，是借用操作系统的**进程隔离**，获得类似机器级别的隔离。
- 区分：Cary 所说的权限是“对权限的文本化管理”，自己说的权限是“实现方式和隔离机制”。

**Cary：**
- 一开始没有听懂为什么要提 MCP：在本系统里，MCP 只是一种工具。
- 目前的设计是由 Kernel 里的权限管理器签发和收回权限。
- 自己所说的权限只是授予 Agent 的权限。询问田园是不是想把权限扩展到 Kernel、Module 和用户，以及独立出来是否意味着要管理 Kernel 的权限。
- 四个 Module 的二级组件大多与其他部分完全解耦，所以从实现上看，与完全独立于 Kernel 几乎没有区别。
- Agent 的所有权限都来自工具：运行前定义好 Agent 和 Tool，除此之外 Agent 没有任何权限。Agent 使用工具时属于“Agent 态”，Kernel 运行时属于“系统态”，还可以定义权限较少的“用户态”。这更像一条原则：实现时要确保三种态之间在逻辑上完全闭合。

**会后技术评注：**
- 这一段两人没有对上话。根本原因是两人说的“独立”不是一回事：
  - Cary 说的是**代码解耦**：模块之间互不依赖。
  - 田园说的是**运行时隔离**：由操作系统强制保证一段代码无法越过边界。
  **同一进程里的代码解耦不提供任何安全边界。**在一个 Node.js 进程里，任何代码（工具实现、第三方 npm 包、MCP 客户端）都可以绕过 Kernel 的检查，直接调用文件系统。所以 Cary 那句“解耦之后与独立几乎没有区别”，在安全意义上不成立。
- **田园的核心直觉是对的，而且与主流产品的做法一致：**我们没有硬件特权级，就借用操作系统的进程或容器隔离。例如：
  - OpenHands 把执行环境放在 Docker 容器里，通过 HTTP 端口接收要执行的动作，这与田园“用端口通信的独立服务”的设想非常接近。
  - Codex CLI 使用操作系统自带的沙箱机制（macOS 的 Seatbelt、Linux 的 Landlock/seccomp）限制命令能做什么。
- **需要修正的一点：应该隔离的是“执行器”，而不是“鉴权判断”。**实际的威胁来自模型生成的命令和代码被执行之后。模型的输出只能经过工具调用解析器进入系统，它无法在鉴权代码所在的进程里执行任何东西，所以鉴权判断留在 Kernel 进程内是安全的。真正危险的是 `bash` 执行的命令：它可以读写任何文件、访问网络，必须放进操作系统强制的隔离环境（沙箱或容器，只挂载工作区，默认禁网）。把鉴权单独做成一个服务器，会增加延迟和复杂度，却挡不住这个真正的威胁。
- **Cary 说“Agent 的权限全部来自工具”，这个思路正确，但有一个漏洞：**一旦给了 `bash` 工具，它就等于“万能权限”，工具级别的权限划分就失效了。所以工具级权限必须配合操作系统级隔离。
- 建议把两人的观点合并成一个方案，并用 RISC-V 三种模式来对应：

| RISC-V 模式 | 本系统对应 | 由谁强制保证 |
|---|---|---|
| User 模式 | 执行 Agent 命令的沙箱进程或容器 | 操作系统（容器、沙箱） |
| Supervisor 模式 | 我们的主程序：Kernel 与各模块 | 工具调用解析器、Kernel 的权限检查 |
| Machine 模式 | 宿主操作系统和用户本人 | 用户审批、操作系统用户权限 |

  **鉴权决策留在 Kernel（Cary 的方案），强制隔离交给操作系统（田园的方案）。**这样既有 Cary 要求的“三态逻辑闭合”，又有田园要求的“机器级隔离”。
- 时间安排：只读的 M1 不需要沙箱；一旦加入 `bash` 或写文件，就应该同时加入确认机制，并尽快把命令执行放进容器。

### 已达成的共识

1. 分工：Workflow 与总体架构由 Cary 负责；Kernel（含权限系统、中断、异常）由田园负责；ContextEngine 由 meti 负责，Cary 协助。
