# 实验记录

这里记录为选择技术路径而做的实验：问题是什么、比较了哪些选项、怎么做的、选了什么、什么情况下要重新考虑。
测试结果和技术测试数据不放在这里。

## tree-sitter：代码检索要不要用语法树

- **时间**：2026-11-04。
- **结论**：现在不引入，符号检索继续用正则。

### 问题

`search_repository` 的 `SYMBOL` 模式用正则逐行猜声明。它不懂注释、字符串和类结构，TypeScript 的类方法会漏掉。要不要换成 tree-sitter 解析出的语法树？

### 选项

| 选项 | 做法 |
|---|---|
| 现状正则 | 不变 |
| 改进正则 | 声明关键字要在语句开头，并增加一条匹配类方法的规则 |
| tree-sitter | 先按文本筛出候选文件，再解析语法树确认声明 |
| tree-sitter 加文件大纲 | 同上，另外提供一个列出文件全部声明的工具 |

### 实验

1. **静态比较**：在 6 个真实代码库（TypeScript 和 Python）上比较声明查找，标准答案来自编译器的 AST，与被比较的几方无关。
2. **真实模型对比**：现状正则、tree-sitter、tree-sitter 加大纲三组做定位任务。任务由 AST 随机抽样，避免人为挑选。

### 发现

- **tree-sitter 的静态准确率明显更高**，差距集中在 TypeScript，Python 上正则已经接近完美。
- **改进正则走不通**：召回率上去了，精确率却下降。只看一行分不清 `foo(` 是调用还是声明，也分不清多行 import 里的 `type X`。所以要提高准确率，只能靠语法树。
- **性能不是障碍**：解析很快，语法文件也不大。
- **Agent 没有因此受益**：三组的成功率和 token 用量没有可测的差别。正则漏掉类方法时，模型直接改用文本搜索就找到了。
- **模型很少走这条路**：写入任务和真实仓库任务的搜索以文本和自动模式为主，`SYMBOL` 占比很低。提供了文件大纲，模型也几乎不用。

### 决定

不引入。实验没有测到 Agent 层面的收益，而每种语言都要长期维护语法文件和查询规则。

### 局限

只用了一个模型；对比任务都是只读定位题，没有测对写入任务成败的影响；每组样本不大，小幅差异不能说明谁更好。

### 什么时候重新考虑

满足其一就再评估：

1. 真实仓库任务的失败或大量 token，明确来自找不到符号；
2. 要做文件大纲，并且能让模型真正用起来；
3. 需要跨语言的精确重命名。此时先看 LSP，因为 tree-sitter 不懂类型和跨文件引用。

`web-tree-sitter` 已经为解析 bash 引入，运行时已经在依赖里，到时增加的主要是语法文件和查询规则。

### 脚本

`experiments/tree-sitter/`。它们不属于产品，也没有包依赖它们。

## token 估算：用什么方法贴近 provider 的计数

- **时间**：2026-11-04。
- **结论**：按文本片段分类估算，再用同一 AgentRun 上一次的实测值校准；不引入 DeepSeek 的分词器。

### 问题

原来的估算直接取字节数，比 provider 的计数高出 3 倍左右，而且比例随内容变化。输入上限和额度都按它判断，模型的上下文窗口只用上了一小部分，真实大型仓库上的任务因此提前收尾。目标：与 provider 的计数相差不到 5%。

### 选项

| 选项 | 做法 |
|---|---|
| 字节除以固定系数 | 只改一个数 |
| 字符类别回归 | 统计字母、数字、标点、中文等的数量，按回归系数相加 |
| 片段分类 | 把文本切成类似 token 的片段（按单词长度、数字分组、中文字符等），每类一个权重，权重有下限 |
| 片段分类加校准 | 同上，再乘以同一 AgentRun 上一次"实测 ÷ 估算"的比值 |
| 官方分词器 | 用模型自带的 `tokenizer.json`（约 6 MB），精确计数 |

### 实验

1. **真实请求**：真实运行写入评测的题目（小仓库、困难题、本仓库），保存每次请求的正文和 provider 返回的 `prompt_tokens`。
2. **异常文本**：把中文文档、纯中文、TypeScript、锁文件、压缩后的 JS、base64、十六进制、数字表格、emoji 混合文本发给 provider（`max_tokens = 1`），覆盖真实请求里少见的文本。
3. **评估**：系数拟合时留出整道题目，评估只用留出的数据，避免自己验证自己。

### 发现

- **固定系数走不通**：不同文本每 token 的字节数相差 3 倍以上，一个系数不可能都准。
- **字符类别回归同样不够**：一遇到 base64、emoji 这类文本，误差就大到不可用。
- **片段分类接近目标，但不能保证**：真实请求上仍有一部分超过 5%，题目之间的差异消除不掉。
- **校准最有效**：一次请求的绝大部分是上一次请求，只有新增部分带估算误差，所以请求越大越准。接近上限时恰好最准，这正是需要判断的地方。
- **思考内容算进输入**：回传的 `reasoning_content` 计入 `prompt_tokens`，原来的估算没有算它。
- **权重需要下限**：不加下限的拟合结果里，某些长度的单词权重为 0，同一个单词重复很多次的文本会被算成几乎没有。

### 决定

片段分类加校准。不增加依赖，也不用加载 6 MB 词表，校准后已经达到目标。最后再用真实仓库任务验证了产品里的实现。

### 局限

只测了 `deepseek-flash`；样本以英文代码为主。校准之前的第一次请求和少数小请求仍可能超过 5%，但这些请求离上限很远。

### 什么时候重新考虑

满足其一就再评估：

1. 接入其他模型（权重只针对这个模型拟合）；
2. 真实运行中大请求的误差超过 5%，或因此触发了 provider 的上下文超限错误；
3. 需要逐字节精确的计数，此时改用官方分词器。

### 脚本

拟合脚本和数据都是一次性的，没有留在仓库中。权重在 `packages/libraries/contracts/src/context/token-estimate.ts`。
