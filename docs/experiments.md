# 实验记录

这里记录为选择技术路径而做的实验：问题是什么、比较了哪些选项、怎么做的、选了什么、什么情况下要重新考虑。
测试结果和技术测试数据不放在这里。

## tree-sitter：代码检索要不要用语法树

- **时间**：2026-11-04，阶段 2 结束时。
- **结论**：现在不引入，符号检索继续用正则。

### 问题

`search_repository` 的 `SYMBOL` 模式用正则逐行猜声明。它不懂注释、字符串和类结构，TypeScript 的类方法会漏掉。要不要换成 tree-sitter 解析出的语法树？

### 选项

| 选项 | 做法 |
|---|---|
| 现状正则 | 不变 |
| 改进正则 | 声明关键字要在语句开头，并增加一条匹配类方法的规则 |
| tree-sitter | 先按文本筛出候选文件，再解析语法树确认声明 |
| tree-sitter 加文件大纲 | 同上，另外提供一个列出文件全部声明的工具 |

### 实验

1. **静态比较**：在 6 个真实代码库（TypeScript 和 Python）上比较声明查找，标准答案来自编译器的 AST，与被比较的几方无关。
2. **真实模型对比**：现状正则、tree-sitter、tree-sitter 加大纲三组做定位任务。任务由 AST 随机抽样，避免人为挑选。

### 发现

- **tree-sitter 的静态准确率明显更高**，差距集中在 TypeScript，Python 上正则已经接近完美。
- **改进正则走不通**：召回率上去了，精确率却下降。只看一行分不清 `foo(` 是调用还是声明，也分不清多行 import 里的 `type X`。所以要提高准确率，只能靠语法树。
- **性能不是障碍**：解析很快，语法文件也不大。
- **Agent 没有因此受益**：三组的成功率和 token 用量没有可测的差别。正则漏掉类方法时，模型直接改用文本搜索就找到了。
- **模型很少走这条路**：写入任务和真实仓库任务的搜索以文本和自动模式为主，`SYMBOL` 占比很低。提供了文件大纲，模型也几乎不用。

### 决定

不引入。实验没有测到 Agent 层面的收益，而每种语言都要长期维护语法文件和查询规则。

### 局限

只用了一个模型；对比任务都是只读定位题，没有测对写入任务成败的影响；每组样本不大，小幅差异不能说明谁更好。

### 什么时候重新考虑

满足其一就再评估：

1. 真实仓库任务的失败或大量 token，明确来自找不到符号；
2. 要做文件大纲，并且能让模型真正用起来；
3. 需要跨语言的精确重命名。此时先看 LSP，因为 tree-sitter 不懂类型和跨文件引用。

阶段 3 引入 `web-tree-sitter` 解析 bash 之后，运行时已经在依赖里，到时增加的主要是语法文件和查询规则。
