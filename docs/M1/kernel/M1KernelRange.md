# MultiAgentOS M1 Kernel 设计范围

## 1. 目的与设计阶段

本文记录 M1 Kernel 已确认的设计范围，作为后续机制讨论、模块级设计和实现的边界。
范围遵循 [Kernel 架构](../../Architecture/module/Kernel.md) 的六组件宏内核组织，服务于
M1 只读仓库分析。既有 [M1 计划](../M1Plan.md) 的单 Agent、独立 ContextEngine 等旧口径
需同步调整，不作为本轮架构适配的依据。
本文作为第一阶段收敛后的范围基线，确定必要能力、职责边界及明确排除项。
除已确认的 FIFO 等范围约束外，具体接口、算法、存储结构和目录布局留待后续阶段设计。

设计工作分为五个阶段：

1. 确定 M1 Kernel 实现范围，以本文记录结论。
2. 讨论 Kernel 具体机制及单进程软件组织、数据通信机制。
3. 编写能够直接指导实现的模块级设计文档初稿。
4. 根据其他开发者意见完善设计。
5. 设计项目目录结构。

## 2. 目标与运行边界

M1 采用最小可行子集：Gateway、Core、Scheduler、Execution、Supervisor、Monitor 均承担真实职责，
共同完成一条受控的串行执行闭环，不以空接口代替核心行为。

| 维度 | M1 边界 |
|---|---|
| 运行组织 | 本地、单用户、单项目、单进程、单活动 Task；Planner 与 CodeViewer 通过单向 handoff 串行交接 |
| 业务目标 | 只读仓库分析，支持模型、仓库概览、搜索、文件读取和上下文组装所需的执行能力 |
| 执行顺序 | 同轮可提出多个工具调用，所有 Unit 不区分是否涉及 API，统一按 FIFO 串行执行；不引入并行 Agent 调度 |
| 信任边界 | 仅开放可信内置模块和 Executor，不加载任意不可信执行代码 |
| 只读约束 | 不修改被分析仓库，不执行项目命令或项目测试 |
| 必要系统操作 | 允许受控的系统状态、Artifact、审计写入，以及获准的模型 API 请求 |
| 控制能力 | 支持取消、停止和最终收敛；不提供暂停/恢复与崩溃续跑 |
| 用户交互 | 单次目标输入与最终输出；运行中支持终止和必要授权，访问仓库前收集一次 Y/N |

系统自身写入与被分析仓库写入必须明确区分；模型 API 访问不构成任意网络访问权限。
两个 Agent 均属于 M1 交付，Kernel 支持其执行归属与资源交接，业务 handoff 由 Workflow 管理。

## 3. 软件组织与通信边界

M1 设计必须覆盖单进程内的组件组织、模块装配、启动与关闭关系，以及数据通信机制。
各类状态仍只有一个权威写入 Owner，不因同处一个进程而开放内部状态的跨模块修改。

系统仅设 UserInteraction、Workflow、Kernel 三个 Module。Execution 纳入 Kernel；
上下文算法归 ExecutorSet，所需运行状态归 Execution，不再设置独立 ContextEngine。
AgentToolPool、ExecutorSet、SharedContracts 是静态库，不作为自主服务或独立生命周期主体。

ArtifactStore、ModuleHost、Fabric、Persistence 保持独立基础设施地位，由 Kernel 承担相应管理职责，
但不成为 Kernel 内部组件。管理关系与架构分类分别表达：

| 基础设施 | 独立职责 | 管理关系 |
|---|---|---|
| ArtifactStore | 不可变内容存储、完整性与保留原语 | Execution 承担管理与执行产物协调职责 |
| ModuleHost | 系统装配、就绪与生命周期机制 | Supervisor 承担监管与生命周期协调职责 |
| Fabric | 通信、路由与事实交接 | Core 承担管理职责，不因此中转全部消息 |
| Persistence | 状态存取与持久化机制 | ModuleHost 管理生命周期，各 Owner 保有数据权威 |

基础设施提供技术机制，领域 Owner 保留业务决定权与状态所有权。
独立地位不要求独立进程，M1 仍采用单进程部署。

通信接口必须保留以下约束，以支持后续替换为 IPC：

- 使用明确、可序列化的数据契约，并在模块边界执行运行时校验。
- 明确异步调用、请求关联、结构化错误、超时及接受与完成的区别。
- 模块协作不依赖共享可变对象、裸内部句柄或同步回调链。
- 大对象通过受控 Artifact 引用传递，必要的小型结构化结果可以直接交付。

外部模块与独立基础设施的受保护服务、执行及控制请求统一通过 Gateway 移交 Core；基础设施
受 Kernel 管理不等于拥有内部入口。Kernel 内部组件可直接向 Core 提交控制请求，无需绕回
Gateway，但仍须校验调用身份与职责权限，不能任意共享内部状态或绕过控制响应逻辑。
普通监控数据与可信事实可直接交给 Monitor 或对应 Owner，不要求经过 Gateway。

M1 不实现 IPC、多进程部署或分布式可靠投递。后续扩展以保留模块职责和请求/结果语义为目标，
不承诺传输层替换完全无需修改；具体引入阶段另行确定。

## 4. 六组件职责范围

### 4.1 Gateway：统一申请入口与控制分派

- 外部模块与独立基础设施申请受保护系统服务、执行能力或提交 Kernel 控制请求时，以 Gateway 为唯一申请入口。
- 确认可信调用身份，校验、规范化请求并建立请求关联，将请求信息移交 Core 的统一控制响应逻辑。
- Kernel 内部组件可直接向 Core 提交控制请求；Gateway 不实现或维护各类控制响应逻辑。
- 授权与 Lease 裁决交由 Core 负责；Gateway 不保存 Lease 实体、快照或验证缓存，不自行作租约裁决。
- 普通监控数据与可信事实可通过专用信道交接；外部 Exception 经 Gateway 移交 Core，内部 Exception 直接提交 Core。

M1 的额度处理采用一次性执行准入截断：Monitor 向 Core 提交指定 Agent 的额度 Exception，
Core 处理后通知 Gateway 设置截断。Gateway 拒绝该 Agent 下一次执行准入并返回明确原因；
拒绝后解除本次额度截断，由 Workflow 处理拒绝并提交收尾 UnitIntent。

该机制不阻断取消、异常上报或状态查询，不终止已经运行的调用，也不实现请求速率限制。
解除额度截断不解除取消、停止或 panic 等其他限制，后续仍执行正常权限与范围检查。
进入收尾由 Workflow 负责，不将一次性截断视为
持续的硬额度封锁或仅允许收尾请求的准入策略。

### 4.2 Core：授权、租约与控制裁决

- 实现并维护统一控制响应逻辑，处理 Syscall（AgentOS 系统调用，含内部与外部 syscall）、
  Interruption（中断信号）和 Exception（AgentOS 异常，可来自包括 Kernel 在内的整个系统）。
- 接收 Gateway 移交的外部请求及内部组件直接提交的请求，按可信来源与职责权限执行同一套
  控制响应逻辑；通过各组件职责接口落实处理，不递归提交同一控制请求，也不接管其权威状态。
- 明确授权依据及能力上限：本地用户或系统配置提供授权依据，MissionScope 与固定定义限定
  工作范围和能力上限；模型输出、工具注册和能力声明本身不产生授权。
- 将 Lease 作为 Core 私有运行时数据，维护其签发、检查、复用、失效与撤销。除 Core 内部
  受控维护逻辑外，任何主体只能通过 Core 处理的 Syscall 申请相关操作，不得通过其他接口访问。
- 不向其他模块、基础设施或组件开放 Lease 存储句柄，也不允许其保存、直接读取或修改 Lease 实体、快照或验证缓存。
- 对外只返回操作所需的裁决与执行关联，不传播可供独立授权判断的 Lease 副本。
- 区分可选 Tool 权限封装与可信开发者授权路径；Tool 的有无由固定模板和代码确定，调用者不能自行移除封装。
- 提供最小控制闭环，覆盖系统调用、取消/停止中断及故障异常的响应、处置协调和处理结果。
- 维护候选执行结果的接收决定，并向 Workflow 提供确认事实。

M1 支持只读分析所需的基础人工授权，由 UserInteraction 收集响应，Core 判断适用性并决定
是否签发 Lease；拒绝或超时不默认放行。无 Tool 行为仍受工作范围、数据和资源约束。
不引入任意能力扩权、复杂审批、委派与再委派或长期跨运行租约。
授权适用范围、拒绝后的业务收尾、续期需求及内部裁决方式在第二阶段细化。

### 4.3 Scheduler：串行调度与 API 调用机会

- 对涉及 API 的执行步骤管理调用机会，检查获准工作是否具备实际启动条件，不另设改变 Unit FIFO 顺序的调度策略。
- 非 API 步骤由 Execution 串行推进，无需申请 API 调用机会，不另建通用资源调度系统。
- 根据固定定义、调用约束和可用状态匹配 API 调用目标。
- 管理最小 API 池，包括调用目标、必要可用状态、容量及调用机会的分配和释放。
- 与 Monitor 协作确认额度、预留及消耗；停止或取消后阻止相应范围继续调度。

API 池归 Scheduler，Core 管调用资格，Monitor 管资源账本；实际 Provider 请求由
Supervisor 监管的模型执行任务发起，Execution 维护相应执行状态。
M1 不实现优先级、公平性、抢占、并行 Agent 调度、负载均衡或自适应并发。

### 4.4 Monitor：资源账本与额度控制

- 维护额度、预留、已消费、释放和待核对消耗，提供必要查询。
- 支持主动收集与被动接收两类数据获取能力，覆盖额度配置及控制决定、API 资源状态、执行用量与状态、生命周期与监管事实。
- 从配置来源及 Core、Scheduler、Execution、Supervisor 等对应 Owner 获取必要数据；保留资源账本权威，不接管其他 Owner 的状态或读取 Core 私有 Lease。
- 为执行前的额度核对提供权威资源事实，发现额度异常时向 Core 提交 Exception。
- 支持与调度、执行结果关联的结算，防止重复扣减或重复释放。
- 区分实际消耗与未知消耗；失败、超时或取消不能直接按零消耗处理。
- 检测 API 额度阈值并报告指定 Agent 的额度异常，由 Core 协调 Gateway 执行一次性准入截断，具体语义见 4.1 节。

Workflow 负责轮次上限与业务收尾，Monitor 负责实际资源事实和必要的额度异常报告。
账本依赖可核对的执行事实，不能用周期采样近似维护。主动与被动收集的数据划分、收集时机、
交接及核对方式留待机制设计。M1 不建设通用监控告警平台、CPU/GPU 周期采样、
异常预测或自适应反馈调节。

### 4.5 Supervisor：系统生命周期与执行任务监管

- 负责软件系统的启动与正常关闭，协调独立基础设施 ModuleHost 完成装配、依赖就绪与资源释放；ModuleHost 保留自身的生命周期机制职责。
- 接收 Execution 的执行任务请求，根据执行定义引用装配、创建并启动进程内 Executor 执行实例，维护受管执行任务范围。
- 监管任务生命周期、超时、取消与停止期限，向 Execution 交接完成、失败及终止事实，并释放执行资源。
- 不维护 Unit 执行队列，不接管 UnitAttempt、业务执行顺序或结果验收。

M1 的关闭限于停止新执行、尽力结束在途任务及程序资源释放，不实现崩溃恢复；无论正常关闭、
用户强制关闭还是崩溃，下次启动均建立全新的运行状态，不恢复上次任务。
Supervisor 是进程内监管组件，不能承诺强制终止任意失控任务，也不能在所在进程卡死或崩溃后
继续监管或保证清理完成。无法局部收敛时的整体退出边界仍需明确。

独立 OS 子进程、进程池及进程与线程组合的执行载体仅作为后续扩展方向，保留执行请求与结果
交接的职责边界。M1 不实现子进程监管、自动重启、强隔离或远程健康管理。

### 4.6 Execution：尝试、行为执行与上下文状态

- 幂等建立 UnitAttempt，维护步骤、执行进度、输入输出、已知与未知效果及新旧尝试关系。
- 维护唯一的 Unit FIFO 执行队列，按受理顺序串行推进 API 与非 API 工作；前一执行活动完成或确认停止后才启动下一项，不实现并发冲突判断。
- 读取 ExecutorSet 的固定执行定义，向 Supervisor 提交定义引用及必要执行参数，由其装配并监管模型、文件、搜索、概览和上下文执行任务，不自行扩大操作范围。
- 接收 Supervisor 返回的执行结果与生命周期事实，维护 UnitAttempt 及步骤状态，推进后续处理。
- 通过内部 Syscall 取得 Core 的授权与 Lease 裁决，并取得 Scheduler 的 API 机会和 Monitor 的资源确认，不持有 Lease。
- 管理本次分析所需的上下文构建记录、检索台账和来源关联；不建设完整长期记忆或共享索引系统。
- 对独立基础设施 ArtifactStore 承担管理与执行产物协调职责，使用其存储和完整性机制发布产物，向 Core、Monitor、Supervisor 交接相应事实；产物业务归属仍由对应 Owner 决定。
- 响应取消及单次 API 调用的时间、输出限制，保留已发生消耗；对外交付 Kernel 确认结果，不由原子 Executor 回调 Workflow。

单次调用的中断判定分工、局部技术重试与结果交付机制在第二阶段明确。
模型输出只是动作提案，由 Workflow 形成后续 UnitIntent；静态库不保存可变运行状态。
非 API 工作经冲突判断后并发执行仅作为后续演进方向，不纳入 M1。

## 5. 执行与控制闭环

### 5.1 授权、执行与结果确认

以下通路表达必要的控制分支与职责交接，不固定 Syscall 名称、调用次数或接口形式。

```text
Workflow 提交 UnitIntent
  -> Gateway 校验并移交 Core
  -> Core 通过 Syscall 处理授权与 Lease 检查
       -> 已具备执行资格：进入执行
       -> 需要且允许申请授权：必要时由 UserInteraction 收集授权
            -> 获准：Core 签发 Lease，进入执行
            -> 拒绝或超时：向 Workflow 返回拒绝事实
       -> 不允许执行：向 Workflow 返回拒绝事实

获准执行
  -> Execution 幂等创建 UnitAttempt，按 FIFO 串行推进
  -> 按需取得 Scheduler 的 API 调用机会及 Monitor 的资源确认与预留
  -> Execution 提交执行定义引用与参数，Supervisor 创建并监管进程内任务
  -> Supervisor 交回执行结果与结束事实，Execution 更新执行状态
  -> Execution 向 Core 提交内部结果检查 Syscall
  -> Core 处理候选结果或异常，向 Workflow 交付确认事实
  -> Workflow 作业务判断，结束或提交后续 UnitIntent
```

Lease 检查未通过不等于可以申请授权；明确禁止或超出能力范围的请求直接拒绝。
执行须关联对应请求的授权裁决，并满足执行时的有效性要求，不能将一次检查视为永久许可。
无 Tool 行为按可信开发者授权路径裁决，仍受工作范围、数据和资源约束。

Core 检查结果的执行归属与可接受性，Workflow 判断业务结果是否成功；实际执行完成、Core
接受结果和业务验收必须分别表达。Monitor 在执行收敛过程中核对与结算用量，执行失败或
结果被拒绝均不能免除已发生的消耗。
模型工具动作仍须由 Workflow 转换为 UnitIntent，不得绕过 Kernel 执行。
FIFO 约束执行请求的推进顺序，不阻塞取消、停止、Exception 和查询等控制处理。

重复请求、重复结果和迟到结果属于 M1 必须处理的输入：不得重复执行同一逻辑请求、重复结算，
或因取消后的迟到结果重新推进业务。具体幂等与失效识别机制在第二阶段确定。

### 5.2 取消、停止与最终收敛

取消/停止必须区分请求收到、接受与实际生效。正常完成和取消均需收敛本次范围的在途工作、
执行资格与资源持有，核对结果及消耗；未知效果不得被标记为成功或直接自动重跑。
主体在其他工作中仍有效的租约不阻止本次完成。

### 5.3 panic 与安全停机

panic 仅用于可信基础或关键安全不变量已无法维持的情况，普通工具失败、权限拒绝或 Provider
错误不直接触发全局 panic。设计必须明确 panic 判定边界与可信发起职责。
除 Core 内部受控维护逻辑外，绕过 Syscall 访问 Lease，或外部主体绕过 Gateway 的受保护入口
执行内核操作，均属于权限边界失守；经可信边界确认后立即拒绝并进入 panic 处置。
Lease 正常过期、撤销或权限不足仅返回拒绝，不触发 panic。合法的内部控制请求与可信事实
传递不属于越权，不能仅凭 Executor 自报触发停机。

安全停机范围包括：停止新准入和调度、尽力取消在途活动与清理资源、保存必要事实和诊断，
明确表达未完成工作、未知效果及清理失败，并尽力向 UserInteraction 通报致命异常与停机结果。
停机利用 Core 的控制请求与响应能力组织，具体通路、期限和失败兜底留待机制设计。
突然崩溃不保证这些步骤全部执行，不能依赖崩溃后的
Kernel 发出最终通知。M1 不提供自动故障恢复、透明续跑或高可用。
正常退出由 Supervisor 协调卸载和程序资源释放，不保存用于续跑的运行状态；再次启动从空白
运行状态开始，清理上次运行的临时状态，不恢复未完成运行。
清理范围必须限定为系统拥有的运行数据，不涉及被分析仓库、配置或凭据；最终报告与审计的
保留边界在第二阶段明确，不能将启动清理解释为任意删除用户产物。

### 5.4 最小审计与运行查询

保留足以说明“为何获准或被拒、执行到哪里、消耗多少、为何结束”的授权、控制、调度、结果
和消耗记录。运行视图组合各 Owner 的事实，不形成第二个可任意写入的权威状态。
普通日志不记录 Secret、完整 Prompt、源码或工具正文，必要内容使用受控 Artifact 引用。
具体保存粒度与持久化方式留待机制设计，不由此引入崩溃续跑承诺。

## 6. 后续机制设计事项

下列事项属于已确认范围内的实现选择，第二阶段讨论，不在本文提前冻结：

| 主题 | 需要明确的机制 |
|---|---|
| 组织与通信 | 三 Module、静态库与独立基础设施的装配，外部/内部 syscall、可信事实通道、基础设施管理关系与 IPC 演进边界 |
| 授权与租约 | 开发者授权与 Tool 封装、基础 Y/N 审核、Core 私有 Lease 生命周期、Syscall 访问约束、裁决与撤销 |
| 调度与账本 | FIFO 受理与推进边界、API 调用机会、额度阈值与一次性准入截断、收尾额度、用量交接与未知消耗处理 |
| 执行与控制 | Attempt 与上下文状态、结果接收、幂等、技术重试、单次调用限制、取消及最终收敛 |
| 生命周期与故障 | ModuleHost 装配、进程内执行任务的创建与监管、panic 判定与安全停机通路、用户通知、程序资源释放与启动清理边界 |
| 记录与验证 | Monitor 主动与被动收集的数据划分及交接核对、审计和运行视图、持久化粒度、验证场景及验收证据 |

本阶段不规定多进程与 IPC、并行调度、强隔离、暂停/恢复和崩溃续跑的后续交付排期，
也不开展模块级详细方案或项目目录结构设计。
