# MultiAgentOS M1 Kernel 设计范围

## 1. 目的与设计阶段

本文记录 M1 Kernel 已确认的设计范围，作为后续机制讨论、模块级设计和实现的边界。
范围遵循 [Kernel 架构](../../Architecture/module/Kernel.md) 的五组件组织，服务于
[M1 计划](../M1Plan.md) 定义的只读 Repository Analysis Agent。
本文确定“需要具备什么能力”，具体的接口字段、算法、存储结构或目录布局后续在其他 M1 Kernel 设计文档呈现。

设计工作分为五个阶段：

1. 确定 M1 Kernel 实现范围，以本文记录结论。
2. 讨论 Kernel 具体机制及单进程软件组织、数据通信机制。
3. 编写能够直接指导实现的模块级设计文档初稿。
4. 根据其他开发者意见完善设计。
5. 设计项目目录结构。

## 2. 目标与运行边界

M1 采用最小可行子集：Gateway、Core、Scheduler、Monitor、Supervisor 均承担真实职责，
共同完成一条受控的串行执行闭环，不以空接口代替核心行为。

| 维度 | M1 边界 |
|---|---|
| 运行组织 | 本地、单用户、单项目、单进程、单 Agent、单活动 Task |
| 业务目标 | 只读仓库分析，支持 CONTEXT、MODEL、FILE_READ 执行能力 |
| 信任边界 | 仅开放可信内置模块和 Executor，不加载任意不可信执行代码 |
| 只读约束 | 不修改被分析仓库，不执行项目命令或项目测试 |
| 必要系统操作 | 允许受控的系统状态、Artifact、审计写入，以及获准的模型 API 请求 |
| 控制能力 | 支持取消、停止和最终收敛；不提供暂停/恢复与崩溃续跑 |

系统自身写入与被分析仓库写入必须明确区分；模型 API 访问不构成任意网络访问权限。

## 3. 软件组织与通信边界

M1 设计必须覆盖单进程内的组件组织、模块装配、启动与关闭关系，以及数据通信机制。
各类状态仍只有一个权威写入 Owner，不因同处一个进程而开放内部状态的跨模块修改。

通信接口必须保留以下约束，以支持后续替换为 IPC：

- 使用明确、可序列化的数据契约，并在模块边界执行运行时校验。
- 明确异步调用、请求关联、结构化错误、超时及接受与完成的区别。
- 模块协作不依赖共享可变对象、裸内部句柄或同步回调链。
- 大对象通过受控 Artifact 引用传递，传输方式不改变状态所有权与授权边界。

M1 不实现 IPC、多进程部署或分布式可靠投递。后续扩展以保留模块职责和请求/结果语义为目标，
不承诺传输层替换完全无需修改；具体引入阶段另行确定。

## 4. 五组件职责范围

### 4.1 Gateway：统一入口与受控分派

- 统一接入受保护的系统服务与执行请求，确认可信调用身份并校验请求。
- 验证 Lease 的主体、范围与有效性；无适用资格时交由 Core 裁决。
- 将获准请求分派至对应服务或调度入口，支持停止准入。
- 有效 Lease 只省去重复授权裁决，不省去执行关联、资源约束和结果确认。

M1 暂不实现按用户或 API 的入口速率限制，但必须约束工作容量：单活动 Task 和停止期间的
新工作准入规则不能省略。容量约束与入口限流分别设计。

### 4.2 Core：授权、租约与控制裁决

- 明确授权依据及能力上限：本地用户或系统配置提供授权依据，MissionScope 与固定定义限定
  工作范围和能力上限；模型输出、工具注册和能力声明本身不产生授权。
- 管理 Lease 的签发、验证依据、复用、失效与撤销；Core 是租约权威，Gateway 使用其可信验证依据。
- 区分可复用 Lease 与本次执行的受限 Permit，保持执行资格与实际尝试的关联。
- 提供最小控制闭环，覆盖 AgentOS 系统调用、取消/停止中断及故障异常的分派、响应和处理结果。
- 维护候选执行结果的接收决定，并向 Workflow 提供确认事实。

M1 只开放预先许可的只读分析能力，超范围请求明确拒绝；不引入动态权限提升、复杂人工审批、
委派与再委派或长期跨运行租约。Lease 载体、续期需求及具体授权配置方式在第二阶段确定。

### 4.3 Scheduler：串行调度与 API 调用机会

- 提供单活动 Task 下的极简串行调度，检查获准工作是否具备实际启动条件。
- 区分 UnitAttempt 的开始/继续与就绪 Executor 步骤的资源分配；Tool 步骤依赖由 Execution 判断。
- 根据固定定义、能力、执行约束和可用状态匹配执行目标。
- 管理最小 API 池，包括调用目标、必要可用状态、容量及调用机会的分配和释放。
- 与 Monitor 协作确认额度、预留及消耗；停止或取消后阻止相应范围继续调度。

API 池归 Scheduler，Core 管调用资格，Monitor 管资源账本，Execution 的模型网关发起实际
Provider 请求。M1 不实现优先级、公平性、抢占、多 Agent 调度、负载均衡或自适应并发。

### 4.4 Monitor：权威数据与硬预算

- 维护额度、预留、已消费、释放和待核对消耗，提供必要查询。
- 为执行前的硬预算检查提供权威判断，预算不足时不得继续放行。
- 支持与调度、执行结果关联的结算，防止重复扣减或重复释放。
- 区分实际消耗与未知消耗；失败、超时或取消不能直接按零消耗处理。

Workflow 负责业务步数与收尾，Monitor 负责实际资源事实。M1 不实现周期资源采样、主动告警、
异常预测或反馈调节；暂缓主动异常触发不等于取消额度检查和失败返回。

### 4.5 Supervisor 与 ModuleHost：生命周期与执行监管

ModuleHost 归 Supervisor 管辖，负责模块装配、依赖、启动、readiness、启动失败清理和正常关闭。
Supervisor 负责执行活动监管、超时与取消跟踪、停止期限以及资源收敛，不接管业务调度或验收。

单进程下必须明确监管能力的边界：不能承诺独立强制终止某个失控模块，也不能在进程卡死或突然
终止后保证内部清理完成。无法局部收敛时的处置与整体退出边界纳入设计。
M1 不实现子进程监管、自动重启、强隔离或远程健康管理。

## 5. 执行与控制闭环

### 5.1 正常执行与结果确认

```text
Workflow 提交 UnitIntent
  -> Gateway 验证 / Core 必要裁决
  -> Execution 幂等创建 UnitAttempt 并准备 Tool 步骤
  -> Scheduler 分配机会，Monitor 确认与预留额度
  -> Supervisor 监管，Execution 推进执行
  -> 候选结果与用量交由 Kernel 确认、结算
  -> Workflow 消费确认事实并作业务验收
```

实际执行完成、Core 接受结果、Workflow 判定业务成功必须分别表达。
模型工具动作仍须由 Workflow 转换为 UnitIntent，不得绕过 Kernel 执行。

重复请求、重复结果和迟到结果属于 M1 必须处理的输入：不得重复执行同一逻辑请求、重复结算，
或因取消后的迟到结果重新推进业务。具体幂等与失效识别机制在第二阶段确定。

### 5.2 取消、停止与最终收敛

取消/停止必须区分请求收到、接受与实际生效。正常完成和取消均需收敛本次范围的在途工作、
执行凭证与资源持有，核对结果及消耗；未知效果不得被标记为成功或直接自动重跑。
主体在其他工作中仍有效的租约不阻止本次完成。

### 5.3 panic 与安全停机

panic 仅用于可信基础或关键安全不变量已无法维持的情况，普通工具失败、权限拒绝或 Provider
错误不直接触发全局 panic。设计必须明确 panic 判定边界与可信发起职责。

安全停机范围包括：停止新准入和调度、尽力取消在途活动与清理资源、保存必要事实和诊断，
明确表达未完成工作、未知效果及清理失败。突然崩溃不保证这些步骤全部执行，不能依赖崩溃后的
Kernel 发出最终通知。M1 不提供自动故障恢复、透明续跑或高可用。

### 5.4 最小审计与运行查询

保留足以说明“为何获准或被拒、执行到哪里、消耗多少、为何结束”的授权、控制、调度、结果
和消耗记录。运行视图组合各 Owner 的事实，不形成第二个可任意写入的权威状态。
普通日志不记录 Secret、完整 Prompt、源码或工具正文，必要内容使用受控 Artifact 引用。
具体保存粒度与持久化方式留待机制设计，不由此引入崩溃续跑承诺。

## 6. 后续机制设计事项

下列事项属于已确认范围内的实现选择，第二阶段讨论，不在本文提前冻结：

| 主题 | 需要明确的机制 |
|---|---|
| 组织与通信 | 单进程装配、引导顺序、接口形式、分派与异步交互、未来 IPC 替换边界 |
| 授权与租约 | 授权配置与身份建立、Lease 载体与生命周期、Permit 投影、验证与撤销 |
| 调度与账本 | 串行推进、API 池结构、容量分配、与 Monitor 的数据交接及一致性 |
| 执行与控制 | 结果接收、幂等、迟到处理、控制调用、取消与超时、最终收敛 |
| 生命周期与故障 | ModuleHost 具体设计、单进程监管、panic 条件、安全退出与清理边界 |
| 记录与验证 | 审计和运行视图、持久化粒度、验证场景及验收证据 |

本阶段不规定多进程与 IPC、并行调度、强隔离、暂停/恢复和崩溃续跑的后续交付排期，
也不开展模块级详细方案或项目目录结构设计。
