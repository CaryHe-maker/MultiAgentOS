# Phase 1 任务集设计：Turn-chat 的基线与对照

> 2026-11-11。本文是 [M2ReleasePlan](M2ReleasePlan.md) 任务 RP1-EV-0 的设计：为 Turn-chat 建立任务集，录基线 1，优化到基线 2（第 3a 节）。
> 评测系统本身（任务规格、度量、记录、对比）见 [Evaluation](Evaluation.md)，本文只回答"测什么任务、怎么比、怎么防过拟合"。
> 状态：设计已定；对照 harness 已在 WSL 里试跑通过；公开测试集的调研与数据核对已做，试跑（需要 Docker）待做（第 9 节）。标"待核实"或"未确认"的事项没有证据，不能当结论用。

## 1. 要回答的问题

Turn-chat 的基线 2 要证明：**在同一模型、同一预算下，我们的系统（harness）完成代码任务与并行任务的效果不明显差于对照 harness。**

三个考量点：

| 考量点 | 度量 |
|---|---|
| 任务完成的成功率 | 隐藏的验收测试全部通过，并且没有改动测试、没有越界写入 |
| token 消耗 | 未缓存输入、缓存命中、输出，按价格表折成美元；在模型接口处统一记录，两边口径一致 |
| 完成花费的时间 | 从发出第一条消息到最终回复；并行类另记关键路径比（P3 的 1.3 倍口径）与相对"关闭派生的同一系统"的加速 |

两类任务：**代码功能**（修缺陷、加功能、重构、迁移、构建、终端运维、读懂后回答）与**并行功能**（宽读、宽写、有依赖的先后、冲突、失败回收、不该并行的小任务）。

## 2. 选题的原则（按优先级）

1. **避免重复。** 任务之间考察的能力点不重叠：同一个仓库、同一类缺陷、同一种工具使用方式不出两次；开发集、留出集、公开最终集之间不得有相同或近似的题目（按仓库、按补丁内容、按任务文字三道去重，记录来源与哈希）。数量不是目的，覆盖不同的 harness 行为才是。
2. **测 harness，不测模型。** 一个任务只有在"同一个模型换一个 harness 结果会明显不同"时才有区分度。判据：
   - 任务的成败取决于 harness 的决定：选哪个工具、读多少、怎样并行、出错后怎样恢复、上下文满了怎样压缩、长任务怎样保持状态、命令怎样在沙盒里运行；
   - 不入选的：纯靠模型的算法功力或冷门知识的题（如竞赛题、要背 API 细节的题），单轮就能答完、不需要工具的题；
   - 入选前做**消融检验**：同一个模型，在我们的系统里关掉一项 harness 能力（并行派生、压缩、某个工具）再跑，分数有可见变化的任务才算"测 harness"；一个任务在所有配置下都是全对或全错，没有区分度，剔除。
3. **较难，足以暴露系统问题。** 目标是让系统的短板（工具缺口、上下文处理、并行协调、恢复）露出来，而不是让分数好看。试跑后，对照与我们都全对的题剔除。
4. **丰富。** 覆盖多语言（TypeScript、Python、Shell 为主）、多规模（单文件到数十个文件的仓库）、多任务形态。
5. **开源成熟优先。** 同等条件下，优先用有公开数据、有验收测试、有维护记录的公开测试集，不自己出题；自建只补公开集没有的部分（主要是并行类）。

## 3. 三层任务集

| 层 | 内容 | 来源 | 用途与规矩 |
|---|---|---|---|
| **开发集** | 优化时反复使用的题 | 公开集中划给"可分析"的部分，加上自建、按种子生成的题 | 可以逐题看失败原因，可以据此改提示词与工具 |
| **自建留出集** | 不参与优化，用来发现过拟合 | **由别的模型或人独立出题**，我们不看细节；同一生成器换种子也算，但出题时不得参考我们系统的行为 | 只在里程碑时运行，只看汇总数字 |
| **公开最终集** | 基线 2 结论的依据 | 公开测试集的一个固定子集，**提前抽样并封存**，我们没有调过它 | 只看总数字，不看逐题失败；一旦分析了封存部分的失败原因，这部分作废，换一批 |

- **公开集的切分**：用固定随机种子，把公开测试集切成"可分析部分"（进开发集）与"封存部分"（做最终集），记下种子与题目编号的哈希，写入仓库。
- **为什么结论以公开最终集为准**：我们调过的题上，我们的系统占便宜，对照 harness 吃亏；公开最终集上两边都是第一次见，比较才公平。公开题可能出现在模型的训练数据里，但对两边相同，相对比较有效；绝对分数不能当成"系统很强"。
- **规模由时间预算定，不由统计功效定**：负责人的时间有限，所以——**公开最终集**：单个系统、每题跑一次，一次评测约 1.5 小时，只在基线 1、基线 2、基线 3 各确定的时候跑一次，平时不进日常；**开发集**：单个系统每题一次约 3 小时；三路并行；每题硬性截止 15 分钟。代码类与并行类的比例在两层里一致（约 2 比 1），所以两层都既考代码也考并行。代价要写明：最终集只有三十几题、每题一次，成功率差异的置信区间很宽（几十个题时约 ±15 个百分点以上），只能看出大差距，看不出小差距；配对比较与 token、耗时仍然有用。要更窄的区间，需要增加题数或重复次数，那是里程碑时的额外批次，不在日常里。
- **并行类的特殊困难**：没有成熟的公开"并行加速"测试集（M2ReleasePlan 之外的调研见第 9 节）。并行类主要靠自建的生成器与留出集，公平性弱于代码类，用"别的模型独立出题"补强，并在报告里写明。

## 4. 度量与记录

- 成功：由运行结束后才放入的隐藏验收测试判定；问答类按"必须出现的要点"判定。Agent 自己说"做完了"不算。
- token 与时间：统一在**模型接口处**记录（本地记录代理读取接口返回的 `usage`，转发请求不改内容），不依赖各 harness 自己的日志。我们的系统可以配置模型的基础地址；对照 harness 通过自定义的 OpenAI 兼容 provider 指向记录代理。
- 每次运行记录：任务编号与哈希、配置（我们的哪个版本、对照的版本）、种子、成功与失败原因分类（答错、超时、崩溃、被拒、越界）、token、耗时、模型请求数、工具调用数、并行度。
- 比较：同一批题两边都跑，做**配对**比较（同一题的结果配成一对），报告成功率差与置信区间，不只报平均。
- 每次运行有时限与花费上限：超出则判失败并记录原因。

## 5. 对照对象与退路

- **首选：DeepSeek Harness（`dsh`）。** 无头一次性运行：`dsh --profile headless "<任务>"`，从调用目录作为工作区，只打印最终回答，退出码 0 为完成；官方标注开发者预览，会有不兼容改动，对照时固定具体版本与提交。官方没有文档化的自动批准开关、时限与 token 输出，需试跑确认（第 9 节）。
- **退路：OpenCode。** 如果 `dsh` 无法在 WSL 里正常工作，对照基准改用 OpenCode。判定"无法正常工作"的条件（任一）：
  1. 无法在 WSL 里装起来并无人值守地跑完试跑任务（3 个不同形态的任务，不卡在权限询问上，不需要人干预）；
  2. 无法让它的模型调用经过记录代理（没有可用的自定义基础地址）；
  3. 无法固定版本，或同一版本多次运行因自身故障而失败的比例超过 20%；
  4. 无头运行没有可靠的结束信号与退出码。
- 无论用哪个对照，运行条件相同：同一个模型与思考强度、同一段任务文字、同样的预算与时限、同样的权限（自动批准在工作区内的读写与命令，联网关闭，除非任务需要）、每次在全新的工作目录副本里运行、两边交替运行以免时间偏差。
- 对照 harness 没有的功能（如并行）只比结果、token、耗时，不比行为。

## 6. 语言与预算

- 语言：TypeScript（Node）约 45%，Python 约 40%，Shell 约 15%（终端运维类）。这台机器上这三样都有；不引入需要另装工具链的语言，除非公开集本身要求（待核实）。
- 预算：粗估，依据只有两次实测（小任务约 $0.002，子 Agent 长报告任务约 $0.015，折合每百万 token 约 $0.1）。编码任务按每次 50 万 token 估约 $0.05，并行任务每次 100–200 万 token 估约 $0.1–0.2。上限：基线阶段 $100，优化阶段 $200，每次运行硬顶 $1。试跑后再按实际花费调整。

## 7. 运行规矩

- 真实模型运行带 `--yes` 与请求预算，密钥只从环境或指定文件读取，不写入记录或文档。
- 每次运行在 `mas` 之外的临时目录里进行；并行运行最多 3 个进程（WSL 内存只有 7.5 GB）。
- 没有评测数据的提示词不定稿；每个优化改动前后在开发集上比较，留出集与公开最终集只在里程碑运行。

## 8. 筛选流程

```text
候选收集 → 去重与许可核对 → 区分度检验（消融）→ 试跑（定难度）→ 定稿与封存
```

1. **候选收集**：从公开测试集与论文里找（第 9 节），记录来源、许可、规模、运行环境要求。
2. **去重与许可核对**：三道去重；确认许可允许使用，并记录。
3. **区分度检验**：对一批候选，用同一模型在我们的系统里做消融（关并行、关压缩、减工具），保留分数有变化的；与对照 harness 各跑一遍，两边都全对或全错的剔除。
4. **试跑**：每题 1–2 次，剔除环境跑不起来的、判分不稳定的、明显做不成的。
5. **定稿与封存**：写入任务清单与种子；封存部分的编号哈希写入仓库，之后不再改动。

### 9.1 DeepSeek Harness 在 WSL 里的试跑（2026-11-11，已完成）

结论：**能正常工作，不需要退到 OpenCode。**

| 项 | 结果 |
|---|---|
| 安装 | `npm i @deepseek-ai/dsh`，版本 0.2.2-rc.1（`latest` 与 `next` 都指向它，另有 `alpha`），要求 Node ≥ 24.9，本机 24.19；不需要 pnpm、不需要编译；包里有几个带安装脚本的依赖（node-pty 等）被跳过，无头模式不受影响 |
| 无头运行 | `DSH_HOME=<目录> dsh --profile headless "<任务>"`，从调用目录作为工作区；最终回答在标准输出，思考内容在标准错误；一个修缺陷的任务 8–10 秒完成，退出码 0；跑了真实命令（`node test.js`）并自己验证了结果 |
| 模型 | 缺省 `deepseek-flash`，与我们相同 |
| 密钥与地址 | 读环境变量 `DEEPSEEK_API_KEY`；`DEEPSEEK_BASE_URL` 可以改地址（官方页面没写，从包里找到，实测有效） |
| 接口形式 | 走 **Anthropic 风格**的 Messages 接口（`/v1/messages`），记录代理的上游要写 `https://api.deepseek.com/anthropic`；我们的系统走 OpenAI 风格的聊天补全，记录代理要把两种用量格式统一 |
| token 记录 | 经本地记录代理（转发不改内容）读到每次请求的用量：`input_tokens`（未命中缓存的输入）、`cache_read_input_tokens`、`output_tokens`；注意响应是压缩的，代理要请求不压缩 |
| 权限 | 缺省预设 `workspace-write`，但无头运行实测：联网命令（`curl`）直接放行，用文件工具写 `/tmp` 下的文件也成功，**没有卡在审批上**。它比我们宽松（我们的命令默认无网络、写入限于工作区） |
| 并行运行 | 同时跑 3 个，全部成功，内存占用约 730 MB，没有问题 |
| 遥测 | 缺省会上传会话日志；比较时设 `DSH_TELEMETRY_DISABLED` 关掉（变量名从包里找到，是否生效待核实） |
| 时限与轮数 | 没有文档化的上限，由外面的超时兜底 |
| 没测的 | 它的子 Agent 与并行功能（负责人确认可以正常使用，不需要测）；`DSH_PERMISSION_MODE` 各取值的行为；失败时的退出码 |

对比条件由此补充：对照 harness 的权限比我们宽松，所以评测里我们的系统对所有授权询问一律回答"允许"（评测任务的缺省），使两边在权限上等价；离线任务不依赖联网，任务隔离靠每次运行用全新的临时目录，验收只看工作区里的结果。

**关键的共同点与障碍：**

1. **几乎都需要 Docker。** 这台机器上 Docker Desktop 装在 Windows 里，但 WSL 的 Ubuntu 里没有启用集成，`docker` 命令不可用。要用公开集，必须由你在 Docker Desktop 里打开 WSL 集成（设置 → 资源 → WSL 集成 → Ubuntu-24.04）；我不改这个系统设置。
2. **Agent 要在任务环境里运行。** Harbor、LoopsBench、FeatureBench 都把 Agent 装进任务容器。我们的 `mas` 用 bubblewrap 当沙盒，容器里多半没有用户命名空间权限，应走"沙盒不可用则询问"的路径并自动允许（评测里对询问一律回答"允许"），容器本身就是隔离。dsh 则通过 Harbor 的 `BaseInstalledAgent` 装进容器。这需要各写一个适配器（接入工作量，不是测试集本身的问题）。
3. **耗时是真正的成本。** 这些任务单个常需数十分钟到数小时（SWE-bench Pro 每题 50 分钟，FeatureBench 缺省 1 小时，ProgramBench 6 小时）。按每题平均 10 分钟估计，100 题、每题 3 次、两个系统，约 100 小时，3 路并行约 33 小时。要为每题设时限（建议 20 分钟）并在试跑后再定题目数。
4. **去重未做。** 各集合可能共用同一批开源仓库（如 FeatureBench 的 24 个 Python 仓库与 Commit0 的库、SWE-bench 系列的仓库）。去重要在拿到各集合的数据后按仓库名与补丁内容比对，现在只能标"待核实"。

### 9.3 并行类任务的来源（2026-11-11）

**公认的并行测试集没有。** 能用的是下面三类，按可靠程度排序：

1. **LoopsBench（依赖图任务）**：任务本身是单元的依赖图，"没有前后依赖的单元"可以并行做，其余必须串行。它不直接测并行，但能测 harness 是否抓得住并行机会（耗时与 token 的比较），公开、MIT、有自定义 Agent 入口。**首选。**
2. **"关闭派生"的消融**：借用论文 arXiv 2610.10263 的做法——同一个模型，同一提示，同一时限，只关闭子 Agent 工具，其余不变，在公开的长任务（LoopsBench、FeatureBench 二级、RepoZero、NL2Repo、SWE-bench 系列）上比较成功率、耗时、token。该论文的结论对我们很有用：
   - 并发"不一致地有帮助"：成功率变化从下降 11.9 个百分点到提高 2.3 个百分点；
   - 最长的任务（LoopsBench）上成功率提高最多（最多 14.3 个点），受限的小任务（SWE-bench Verified）上反而下降（Claude Code 从 83% 到 59%）；
   - token 增加 1.41 到 3.31 倍，耗时在 15 个组合中的 14 个增加；
   - 失败的主因是共享状态与合并（33.2%），其中并发写入同一交付物（26.5%）最多，其次是任务编排问题（28.5%）和执行治理问题（29.0%）；
   - 作者的建议：并发应当"按需开启，而不是缺省开启"。
   这直接对应我们 D 组（适不适合派生）和 P 组的设计：**对系统的要求不是"尽量并行"，而是"在合适的任务上并行，在不合适的任务上不并行"。**
3. **自建的并行任务生成器**，借用 MS-Eval 的任务分类：把每个任务标成"需要委派"或"不需要委派"，度量**不足委派率**与**过度委派率**，以及相对"单 Agent"基线的成功率、效率与成本。MS-Eval 自己的任务是办公与电商的 MCP 任务，不是代码，所以只借方法，题目自建（宽读、宽写、有依赖、冲突、失败回收、不该并行的小任务）。该论文还给出一个提醒：关闭委派工具得到的单 Agent 基线，是衡量"并行是否有价值"的唯一可靠参照。

**由此对任务集设计的修正：**

- 并行类不只看"成功率、token、耗时"，要加两个度量：**不足委派率**（该并行没并行）和**过度委派率**（不该并行却并行，含失败后无限重派生）。
- 并行类的每个题要预先标注"该不该并行"，由生成器产生，不由我们的系统的行为决定。
- 对照 harness（dsh）没有内置并行时，并行类只比结果、token 与耗时。

**去重的办法（按优先级）：**

4. **与开发集、留出集之间不重复**：公开最终集封存之前，用同样的比对检查一遍。

**"测 harness 不测模型"的筛选办法（草案，待消融检验）：**

- Terminal-Bench 里有一部分任务主要考领域知识或算法功力（如密码分析、国际象棋、定理证明、代码高尔夫、编译器移植），换 harness 区别不大；另一部分考的是工具与流程（git 恢复、日志处理、构建、调试、系统配置、文件操作），区别大。先用类别与说明文字做初筛，再用第 8 节的消融检验确认；**初筛只是启发式，不是结论。**
- FeatureBench 与 SWE-bench Pro 的多文件、长链路任务更看重上下文管理与恢复，其中 FeatureBench 在"同模型不同 harness"的研究里差距最稳定；但 FeatureBench 的镜像太大、SWE-bench Pro 单题偏长，最终只取 SWE-bench Pro 里补丁小的题（见 9.9）。
- 并行类按第 9.3 节办理。

**暂定的来源分配（草案，试跑后调整）：**

| 层 | 来源 |
|---|---|
| 公开最终集（封存，30 题） | 代码类 20 题：Terminal-Bench 14、SWE-bench Pro 6；并行类 10 题：自建生成器（封存的种子，开发集不用）。全部按第 9.8 节的规则选出 |
| 开发集（36 题） | 代码类 23 题：Terminal-Bench 20、SWE-bench Pro 3；并行类 13 题：自建生成器 |
| 自建留出集 | 别的模型独立出的题；**尚未做**，不计入上面的时间预算 |

**耗时与成本的现实约束：** 一个系统在最终集上跑一次要约 1.5 小时（三路并行，每题 15 分钟封顶，平均按 7 到 8 分钟估计）；开发集约 3 小时。两个系统同时比较时耗时翻倍。每次运行记录追加、可续跑（沿用评测体系的规矩）。FeatureBench 的镜像每个约 10 GB，所以**不入选**（见 9.9）；LoopsBench 每题超时至少 30 分钟（多数 2 小时），放不进 15 分钟的封顶，也不入选。

### 9.5 Harbor-Index 与 Harbor 框架（2026-11-11）

**Harbor** 是 Terminal-Bench 2.0 的官方运行框架（Apache-2.0，`uv tool install harbor`），并把 80 多个公开测试集用适配器移植成统一的任务格式（注册表里有 terminal-bench 2.0 的 89 题、swebench-verified 的 500 题、swebenchpro 的 731 题等）。**对我们的意义：只要写一个 `mas` 适配器，就能跑所有这些测试集；dsh 同理。**

- 适配器接口（官方文档）：继承 `BaseInstalledAgent`，实现 `install`（在任务容器里装 Agent）与 `run`（执行任务，指令作为参数传入）；日志写在容器的 `/logs/agent`，运行结束同步回主机；模型的基础地址和密钥通过类属性 `MODEL_CONNECTION` 声明（可以指到我们的记录代理）；自定义 Agent 用 `harbor run -a 模块路径:类名`；容器里的网络按任务配置，指向代理要加 `--allow-agent-host`。每次试运行的超时由任务的 `task.toml` 里的 `[agent] timeout_sec` 规定，适配器不需要管。
- 我们的 `mas` 在容器里的问题：沙盒用 bubblewrap，容器里通常没有用户命名空间权限，所以适配器要让它走"沙盒不可用则询问"的路径并自动回答"允许"，容器本身就是隔离。

**Harbor-Index**（精选集，`github.com/harbor-framework/harbor-index`，已发布到 1.4 版，目前 100 个任务目录，README 称 80 个）：

- 筛选过程（论文）：从 6627 个候选里，先留下三个前沿模型（各用原生 harness 与通用 harness、重复三次）成功率不超过三分之一的 1311 个，再经 AI 审计、14 人人工复核、三人评审组，最后修复或剔除坏题。官方强调"紧凑、多样、难、高质量"，且"没有可被利用的验证漏洞"。
- **harness 区分度有证据**：原生 harness 对通用 harness 的通过率：GPT-5.5（Codex）28.0 对 19.5，Claude（Claude Code）20.7 对 15.9，Gemini 3.1 Pro（Gemini CLI）13.4 对 11.0；原生 harness 用的工具调用和输出 token 更少，超时率从 42% 降到 26%。整体上，换模型的影响（范围 0.451）远大于换 harness（0.087）——**这个提醒很重要：公开集上"模型的影响比 harness 大五倍"，所以一定要在同一个模型下比较，并配对。**
- 组成（核对到的 100 个任务目录，按来源前缀）：hle 8、gso 7、swebenchverified 5、gaia2 5、bix 5、arcagi2 5、algotune 5、swebenchpro 4、labbench 4、featurebench 4、tb 3、scicode 3、gaia 3、spider2 2、skillsbench 2、omnimath 2，其余零星。**其中不少偏考模型本身**（HLE、数学、ARC、科学知识），不符合"测 harness 不测模型"，不能整套使用。
- 其余核对：没有任务要 GPU；其中 62 个任务的网络模式是 `public`（需要联网），29 个是无网络；单任务超时从 3 分钟到 3 小时不等；**一部分任务用大模型组成的"评审团"打分，要 OpenAI、Anthropic、Gemini 的密钥**，我们只有 DeepSeek 的，而且这违背我们"确定性验收"的规矩，所以这一部分要剔除。
- **选择偏差**：它专挑前沿模型成功率低的题，所以通过率很低（论文里最强的组合 28.0%，没有组合超过 30%）。通过率这么低时，两个 harness 的成功率差异很难看出来（样本小、噪声大）。结论：可以取其中"编码类、确定性验收、无需大模型评审"的子集（初步估计 30 个左右，包含 swebench、featurebench、gso、tb、spider2、cybergym 等来源），但**不能作为唯一的最终集**，要和 Terminal-Bench 2.0 全量（中等难度的题更多）搭配。
- 许可：未查到 Harbor-Index 自己的许可文件；使用前必须确认（它的任务来自许多不同来源，各有各的许可）。
- **没有跨测试集的去重说明，也没有污染处理说明**（论文里没找到），我们仍要自己去重。

**对第 3 节规模的说明：** Harbor-Index 与 Terminal-Bench 的任务大多不是"一次一两分钟"，单任务超时常为 20 到 30 分钟；所以第 3 节的规模按 15 分钟封顶与 1.5 小时、3 小时的预算来定。

### 9.7 自建并行任务生成器的设计（草案）

公开集里，LoopsBench 能测"有独立变更请求时的并行"，但没有一个公开集专门考"不该并行"和"并行出了问题怎么办"。这几类必须自建，设计依据是第 9.3 节两篇论文的结论（并发要按需开启；失败多出在共享状态与合并、编排和执行治理上）与 MS-Eval 的"需要委派／不需要委派"分类。

**原则：** 每个题在生成时就带着"标注答案"，由生成器给出，**不由我们系统的行为决定**：该不该并行、可以并行成几份、哪些文件会冲突。验收只用隐藏的确定性测试，不用大模型评审。

| 族 | 形态 | 标注 | 度量重点 |
|---|---|---|---|
| 宽读 | 在一个有 N 个互不相关模块的仓库里，回答每个模块的几个具体问题（答案在代码里，要读才能知道），汇总成一份文件 | 需要委派；可并行份数 = N | 成功率、耗时、token；不足委派率；加速比 |
| 宽写 | N 个互不相交的文件各需要实现一个功能（有各自的测试）；N 取 2 到 16，同一族里放大 N 看加速比与 token 随规模的变化 | N 小时不需要委派，N 大时需要；N 份互不冲突 | 成功率、耗时、写入是否越界 |
| 先调研后实现 | 先从 N 处读出信息，汇合后在一个地方实现 | 调研可并行，实现不可 | 是否错误地并行了实现；成功率 |
| 小任务陷阱 | 一个很小的任务（改一行、答一个问题） | **不需要委派** | 过度委派率；多花的 token 与时间 |
| 冲突陷阱 | N 个独立请求都要往同一个文件里加内容 | 不能并行写 | 是否出现覆盖、丢改动；成功率 |
| 失败回收 | 一个子任务注定做不成（引用了不存在的东西） | 需要主 Agent 处理失败，不能无限重派生 | 是否停下并报告；重派生次数 |
| 依赖链 | A → B → C，后一个用前一个的产物 | 不能并行 | 是否错误地并行；成功率 |

**生成与独立性：**

- 生成器是一个带种子的脚本，同一个种子得到同一个题；换种子得到同类新题。题的各部分（模块内容、测试、答案）由脚本填充，不依赖我们系统的任何输出。
- **出题要独立**：留出集由别的模型（或人）按上表的"族"出题，出题时不给它看我们的系统、提示词、日志；出完后由我们只做可运行性检查（能构建、参考解能通过、空解不通过），不改难度。
- 每个题要有：参考解（让隐藏测试通过）、空解（必须不通过）、测试在运行结束后才放入工作区，Agent 看不到。
- **题要足够大**：顺序做一遍至少要一分钟以上，否则并行省不出时间；用参考的顺序运行时间校准。
- **对照**：同一个题在"关闭派生的同一系统"上跑一遍，作为单 Agent 基线（借用 MS-Eval 与并发论文的方法）。
- 要先用脚本化的假模型证明判分能判出通过、失败、越界和重复派生，再换真实模型（沿用评测体系第 7 节）。

**规模：** 7 个族（规模梯度并入宽写）。开发集 13 题、最终集 10 题，两层用不同的盐值生成，同一族里两层的 N 互不相同，内容和任务文字都不重复（检查过：0 个重复）。已实现并验证：生成器 `scripts/taskset/gen-parallel.mjs`，每个题的参考解得 1 分、空解得 0 分（68 次检查全部符合）。真实运行的成本按每题约 50 万到 100 万 token 估，每题约 $0.05 到 $0.1。

### 9.8 切分与隔离的规则（2026-11-11，已实现为脚本）

隔离是任务集的最高优先级。规则与脚本（试验用，尚未放进仓库）如下，全部是**与任何运行结果无关**的纯函数：

1. **切分的单位是"组"，不是单个任务。** 一个组是一个仓库（如 `repo:navidrome`）或一个任务族（Terminal-Bench 的同族题、LoopsBench 里主题相同的课程项目）。组的键在所有来源之间共用，所以同一个仓库不管在哪个测试集里出现，都落在同一层。这样不会出现"开发集里调过某个仓库的题、最终集里又考同一个仓库"。
2. **组落在哪一层由固定盐值的哈希决定**：`sha256(盐 | 组键)` 的前 32 位除以 2³²，小于最终集比例（暂定 0.5）的组进最终集，否则进开发集。盐值与规则写进仓库，之后不改；不看任何成绩。
3. **组内限量**：最终集每组至多 3 题，开发集每组至多 5 题，按任务编号的哈希排序取前几个。
4. **孪生题去重**：FeatureBench 的同一个目标有 lv1、lv2 两个难度（任务文字相似度最高 0.79），每对只留哈希最小的一个（200 题里 30 对）。
5. **文字去重**：对 1043 个候选的任务文字做 5 个词一组的片段比对（相似度阈值 0.4），**跨测试集没有发现重复**，重复只出现在 FeatureBench 内部（上一条）。
6. **筛选只用静态条件和参考解检查，不用任何模型结果决定最终集里有哪些题**：题必须能起得来、参考解通过、空解不通过、资源与耗时在限制内。"全对或全错就剔除"这类依据结果的筛选，**只在开发集上做**，用来校准规则；最终集不按结果筛，否则就等于看过它。
7. **最终集封存**：封存时记录题目清单的哈希，之后不再改；一旦分析过最终集里某题的失败原因，这一题作废，换同组之外的候选。

**运行器：** Harbor 的安装（`uv tool install harbor`）被这台机器的自动审批拦下，未获批准，不绕过。Terminal-Bench 与 SWE-bench Pro 的任务本身就是 Harbor 格式（镜像、指令、`tests/test.sh`、参考解），所以写了一个最小运行器：起容器、放入测试、运行、读 `/logs/verifier/reward.txt`。已验证：Terminal-Bench 的 `regex-log` 参考解得 1 分、空解得 0 分。

**来源核对（补）：** FeatureBench 的许可是 MIT；`full` 划分 200 题、24 个仓库（mlflow 49、transformers 34、pandas 20、astropy 17、pytorch-lightning 12、seaborn 12 为大头），`fast` 与 `lite` 是它的子集；SWE-bench Pro v2 的 642 个任务目录在 `v2/tasks/`（早先读到的 1000 个条目是旧版 `run_scripts`）。
