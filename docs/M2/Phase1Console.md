# phase 1 控制台与流式输出：问题记录与方案

> 状态：`mas log`（第 3 节）、流式输出（第 4 节）与界面问题 UI-1 至 UI-5（第 2.1 节）已实现；并行优化（第 2.3 节）的大部分与网页授权（第 2.3 节）已实现；授权与工作区的其余部分（第 2.2 节）**尚未实现**。来源：phase 1 开始前，Cary 在实际使用中提出的问题与要求（2026-11-07）。
> 范围：控制台（`apps/cli` 的 Ink 界面与 `UserInteraction` 的文字）、流式输出、日志查看器；授权与工作区、并行优化三组问题记录在案，**留到前面做完之后**，因为它们牵动业务逻辑。

## 1. 已定的顺序与决定

1. 先做**日志查看器**（`mas log`），再做**流式输出**，再做**控制台界面问题**；授权与工作区放最后。
2. 思考内容的展开与折叠：**键盘方式**，规则按**块**（一次模型调用的思考）。思考放在**它发生的位置**：还展开着的块，和从最老的那个起的授权、步骤、提示、回复，都留在底部可改动的区域，按先后顺序排。这一块能用的行数有**限额**（终端的行数减去活动区、询问、状态行和输入框，再留余量），画面只用其中的 **90%**：到了 90% 就把最老的展开的块折叠（折了就不再展开）；最新的这一块自己就超过时，省略它开头的部分，用 `…` 代替，只留最后面的；它结束后保持这样，下一次思考一开始就把这个被省略过的块折叠。`Ctrl+O` 折叠或展开正在显示的块，`/think <N>` 打印第 N 段的全文。
3. 配色：用户输入**柔绿**（`#7ee787`）；系统层面的一切（系统的话：新对话、已打开、已允许……；授权与询问；排队提示；输入框上方的状态行除外）统一**浅黄**（`#F9F1A5`，固定色号，不随终端配色变）；状态行是**粉色**（`#ff79c6`），写成 `------ 运行中 ------`；仓库的对话列表（`LIST` 记录）是灰色，标题行仍是系统的黄色；助手的回复**浅蓝**（`#79c0ff`）；思考是灰色（流式时和结束后一样）。
4. 流式输出走旁路，**不进 SessionLog、不经过 Workflow、不影响任何业务判断**，只给使用者看。

## 2. 问题清单

### 2.1 界面（先做）

| 编号 | 现象 | 原因 | 方案 |
|---|---|---|---|
| UI-1 | "未开始"状态在输入的字下面，输入法候选框更靠下 | 状态行画在输入行**下面**；输入法锚定真实光标，而 Ink 把真实光标留在整块输出的最后一行 | 用 Ink 8 的 `useCursor` 把真实光标放到输入位置；状态行移到输入框上方 |
| UI-2 | 看不出输入位在哪，只能改最后一位 | 输入缓冲只是一个字符串，只支持末尾追加与退格，没有光标位置 | 自有的带光标输入组件：左右、Home/End、Ctrl+A/E、向前删除、Ctrl+W/U；反色光标；光标列按全角宽度计算；粘贴；单元测试 |
| UI-3 | 等待授权时显示数字，像在催人 | 活动行对所有阶段都正计时 | 等待使用者（授权、输入、回答）的阶段不显示耗时；只有模型和工具在运行时才显示 |
| UI-4 | 授权提示把整条命令全文展示（heredoc 把整个文件都刷出来） | 提示文字原样输出命令 | 只显示前 3 行或 240 个字符，注明"共 N 行、M 个字符"，输入 `v` 查看全文（不算回答）；写入范围、网络、命中名单照常显示 |
| UI-6 | 粘贴很长的文字后，屏幕被同一段内容重复刷好几遍，出现乱码 | 输入框的高度没有上限：它和终端一样高时，整个画面就和终端一样高；Ink 每次重绘只擦掉上一帧，光标向上够不到已经滚出屏幕顶部的行，于是每次重绘（例如活动行的秒表）都在滚动历史里留下一份新的。复现：24 行的终端里粘贴 40 行，再重绘 4 次，输入框的第一行出现 5 次、滚动历史多了 191 行 | 长粘贴折叠成一个占位符；输入框有自己的高度，超出时只画光标所在的一段；画面总高度有硬保证（见第 6 节）。输出方式保持 Linux 终端原生的样子：活动区的高度就是它的内容的高度，紧接在已写出的内容后面，不补空行，也不保证输入行在屏幕最下方（内容不到一屏时输入行在内容后面，活动区变矮时输入行会上移，下面是没用到的屏幕）；备用屏幕的全屏模式不做 |
| UI-5 | 用户与助手都是白色 | "全是白色"**没有复现**（可能是颜色等级检测，或终端主题把颜色映射成了别的） | 用户柔绿 `#7ee787`、系统层面的一切浅黄 `#F9F1A5`、助手回复浅蓝 `#79c0ff`、状态行粉色 `#ff79c6`；颜色由测试在强制开启颜色时检查 |

### 2.3 并行优化

依据：一次真实的 SubAgent 运行（一轮约 7.6 分钟，8 个 explorer 在同一时刻启动，会话日志与 Kernel 审计）。

| 观察 | 说明 |
|---|---|
| 搜索不慢，抓取有一批撞上超时 | 搜索 47 次，中位数 0.5 秒，最长 6 秒；抓取 43 次，中位数 9.6 秒，**6 次（14%）以 `UNIT_TIMEOUT` 失败，耗时 65 到 77 秒**（超时 60 秒加排队），其中 4 次重叠在 133 到 213 秒之间，同一时间的模型调用要 22 到 35 秒，平时几秒 |
| 联网和模型调用抢同样的名额 | 全局只有 `maxConcurrentAttempts`（6）个尝试在执行，联网与模型调用、读文件共用；同时在途的 `web-fetch` 最多 13 个，超过的在排队。几个慢抓取占着名额，别人的模型调用就等 |
| 一个确实存在的缺陷 | 网页转 Markdown 在每个块之后重数已写出的全部内容，耗时与页面大小的平方成正比：400 KB 要 12.6 秒，4 MB（抓取允许的上限）要几分钟；它在进程唯一的线程上同步运行，期间其他抓取、模型调用、界面和超时计时器都停着。日志没记原始页面大小，无法证明这次真的发生过 |
| 授权问题的粒度 | `web.search` 整个运行问一次；`web.fetch` 每个新主机问一次；命令按命令行问，关键命令每次都问 |
| 日志的缺口 | `UNIT_SUBMITTED` 到 `UNIT_COMPLETED` 之间混着授权等待与名额等待，没有各自的开始与结束，只能推断；授权询问不写进 Session 日志 |

**已做（2026-11-09）：**

- 网页的搜索与抓取是 WEB 类别，有自己的池（`kernel.maxConcurrentWeb`，缺省 10，超出排队），不占那六个名额，也不是屏障（Kernel/Execution 4）。
- `web_fetch` 的超时从 60 秒改为 30 秒。
- 网页转 Markdown 改为与页面大小成正比（400 KB 约 40 毫秒，4 MB 约 0.3 秒），有回归测试（Library/ExecutorSet 5d）。
- `web.fetch` 的询问可以回答"本次运行内所有公开网站"，`web.search` 可以"这个文件夹以后都允许"（Kernel/Core 5f）；放宽的同时，网址最长 800 个字符、查询值里像编码数据的内容由 Executor 拒绝；私网地址与 `deniedDomains` 仍然拒绝；命令联网（`command.network`）与网页完全隔离，仍是极危险级、每次询问。

**还没做：** 授权等待与名额等待的开始与结束写进日志；用 RP1-RB-1 的 P3（重任务上的并行收益）度量收益；抓取缓存（同一个网址在一次运行内只抓一次）。

## 3. 日志查看器（`mas log`）

目的：不必手读 `log.v1.jsonl` 就能看清一次运行发生了什么，也是评测与排错的工具。

- 输入：Session 的日志（含 `MODEL_TURN` 的 `reasoningRef`、工具调用与结果）。**只读**，不改日志，不需要模型与网络。
- 输出：按 Turn 分段的时间线：模型轮（耗时、用量、思考摘要）、工具调用（名称、参数摘要、结果摘要、授权）、授权询问与回答、压缩、结束原因；可展开某一段看完整思考与完整输出。
- 用法：`mas log [<对话>] [--repo <路径>] [--turn <n>] [--full] [--json] [--list]`。`<对话>` 是 `--list` 里的编号、对话 id 或 id 的开头；不给时取本仓库最近的一个。
- 实现：`apps/cli/src/log/`（`timeline.ts` 从日志记录与产物构建时间线，`render.ts` 画成文字）与 `apps/control-plane/src/log-command.ts`（读文件）。在启动任何模块之前处理，不取实例锁与 Session 锁，所以另一个 `mas` 正在运行时也能看；日志最后一行还没写完整时略过。
- 一致性：认不出的记录类型被跳过；产物已过期或缺失时显示"内容已过期或缺失"而不是失败；日志某一行无法解析或不符合格式时，指出行号并以退出码 1 结束。
- 安全：从模型、网页、工具结果来的正文在输出前去掉控制字符与转义序列（终端输出的注入防护）。
- 局限：列表里的轮数来自 Session 索引，正在进行的那一轮要等它结束才计入；每次模型调用的用量取自日志里 `MODEL_TURN` 的 `usage`（旧日志没有这个字段，则取自模型输出产物）。
- 与流式的关系：流式只给实时观察；**事后完整的思考内容以日志为准**，查看器从日志里的 `reasoningRef` 读取。

## 4. 流式输出

### 4.1 链路

```
ModelCall Executor ──(progress 回调)──▶ Supervisor ──▶ Kernel ──(旁路，无 seq、不入日志)──▶ UserInteraction ──▶ 界面
        │
        └──(流累积成与一次性应答完全相同的结果)──▶ 原有的唯一终态事实 ──▶ Workflow
```

1. **Executor**：有旁观者（`environment.progress` 存在）时用 `doStream`，没有时仍用 `doGenerate`；流累积出的结果（工具调用参数保持 provider 原文、用量、结束原因、缓存命中）必须与一次性应答逐字相同，业务路径不变。DeepSeek 的缓存命中字段 SDK 会丢，所以取自原始的最后一个数据块。
2. **旁路出口**：`ExecutorEnvironment` 增加可选的 `progress` 回调；Supervisor 转交 Kernel；Kernel 直接发给 UserInteraction。这类事件不盖 seq、不进有序队列、不写日志、不经过 Workflow。Supervisor 仍然只报告**一个**终态。
3. **事件**：Supervisor 发给 Kernel 核心的是 `kernel.execution.ModelProgress`（`executionId`、`kind: REASONING|ANSWER|TOOL|END`，`REASONING` 带 `delta`，`TOOL` 带 `name` 与可选的 `target`；另有 `CONTEXT`（`used`、`limit`）只在 `kernel.control.ModelStream` 上，由 Kernel 在组装时直接发出，不经过 Supervisor），Kernel 核心按它记着的"这次调用属于哪个 AgentRun"转成 `kernel.control.ModelStream`（加上 `agentRunId` 与 `callId`）发给 UserInteraction。思考合并后再发（40 毫秒一批，单条不超过 16 KB），`ANSWER`、`TOOL` 与 `END` 立刻发（排在还没发出的思考之后），消费不及时就丢（积压超过 64 条丢弃），**不能拖慢业务**。流式显示的只有**思考**；**回复不流式**（决定：回复一边写一边显示会挤占思考的位置，规则复杂，收益小）：模型一开始写给使用者的答案——只有调用了标为 `answer: true` 的工具（`reply` 就是，经 Kernel 的 `pinned-agent` 写进 `ModelToolSpec.answer`，到执行器），和工具调用一起出现的普通文字**不算**——执行器只发一次 `ANSWER`，**不传正文**；界面把这个 Agent 的活动行变成"正在输出回答"并重新计时，正文在消息发布时整条进入记录。其他工具调用：工具名一写出来，执行器就发 `TOOL { name }`，参数里的 `path` 写完整后再发一次 `TOOL { name, target }`（读参数用 `JsonStringField`，只读 `path`，不传其余参数），活动行显示"正在生成 write_file docs/a.docx"并从工具名出现时计时；这次调用的流结束后，那一行回到工具自己的活动。同一时刻一个 Agent 只有一个时钟：回答或工具调用一开始，思考块立刻结束。
4. **安全**：模型输出直接打印到终端，旁路事件在进入界面前**过滤控制字符与转义序列**。
5. **失败**：流中途断开要归入明确的失败类别并说明能否重试（现有重试判定依赖"请求是否发出、是否收到响应"），不能当成功；abort 时同时取消流。
6. **思考要从网络这一侧读**（真实模型测试发现）：提供方 SDK 在交出流之前，会先读到第一段"正文或工具调用"，而思考总是排在最前面，所以经 SDK 的思考要等整段思考结束才到。执行器因此在 `trackedFetch` 里把流式应答的字节旁路给 `streamTap`（`stream-tap.ts`），逐行解析 SSE 里的 `reasoning_content`，并在正文或 `answer` 工具的调用出现时发一次 `ANSWER`，立刻通知旁观者；SDK 读到的仍是同样的字节，结果不变。真实运行里实测：同一个问题的思考在 1.1 秒里分 18 次长出来，而不是在最后一刻一次到齐。

### 4.2 记录、保存与删除

结论先说：**流式内容不单独保存**，它只是正在发生的事的预览；事后需要的完整思考，系统本来就已经保存在日志里。

| 问题 | 规定 |
|---|---|
| 怎么记录 | UserInteraction 在**进程内存**里按块记一份"思考段"：`{编号, agentLabel, 开始, 结束, 文本, 状态}`，编号从 1 起按调用开始的顺序；状态为进行中、完成或已中止（中止时保留已收到的部分并标明） |
| 记在哪里 | **只在内存**。不写 SessionLog，不写磁盘，不发给 Kernel 或 Workflow |
| 完整版从哪来 | 每次模型调用结束后，完整的思考内容由 Execution 作为 `reasoningRef` 写进日志（回传 `reasoning_content` 需要它）。流式预览只是它的前身；`/resume` 之后控制台里没有以前的思考，要看就用 `mas log`（它读日志里的版本） |
| 显示 | 展开的块、和它们之间与之后的记录在底部按先后顺序画；放不下时按"限额的 90%"折叠最老的块或省略最新块的开头（见 4.3）；折叠过的在记录里是一行"✻ main 思考 3.2s（/think N 展开）"；`Ctrl+O` 折叠或展开正在显示的块；`/think` 列出所有块，`/think <N>` 打印第 N 段的全文 |
| 上限 | 单段不超过 64 KB（超出截断并标明）；内存里最多保留最近 100 段，更早的丢掉最旧的 |
| 何时删除 | ① 进程退出；② `/new`、`/resume` 切换到别的 Session；③ 超出上限时按从旧到新；④ Session 关闭 |
| 为什么不落盘 | 思考内容可能包含敏感信息；DeepseekHarness 把它写进 stderr 后明确记下了"日志收集器会保留更多敏感内容"这一后果。日志里的版本已有既定的保留规则，不再增加第二份 |

可选的后续（本次**不做**）：`--save-thinking` 把流式内容写到数据目录下的单独文件，按产物的 7 天规则过期。

### 4.3 界面

- **思考放在它发生的位置。** 终端里写出去的行不能再改，所以对话的末尾一段留在可以改动的区域：从最老的、还展开着的思考块起的所有内容（这些块，和它们之间、之后的授权询问、步骤、提示、回复）按发生的先后顺序排。于是"思考 → 授权 → 思考"里，第一段思考在第一次授权的上面。一个块被折叠时，它和它之后到下一个展开的块之前的记录**依次进入记录**，之后不再变化，顺序始终是对的。
- **限额与 90%。** 限额 = 终端行数 − （活动行（含"正在输出回答"行）+ 询问的行数 + 排队提示 1 行 + 状态行 1 行 + 输入框的行数）− 3 行余量；平时大约是终端高度减 5 到 7 行。末尾这一段只用限额的 **90%**：记录按自己的行数放，每个展开的块先占 1 行标题，正文按全文放。放不下时依次：① **整块折叠**最老的展开的块——它的头部超出，就是整个块连同它之后、下一个展开块之前的记录一起变成一行进入记录，不是一行行压缩，折叠是永久的；终端里因此只剩最早的还没折叠的思考和它之后的内容；② 只剩最新的一个块还放不下（它自己就超过限额），才省略它的开头，画一行 `  …`，再画最后面能放下的几行；③ 它结束后保持这样；④ 下一次思考开始的那一刻，被省略过的块就被折叠。折叠永远不会反过来展开。因为回复不在画面里流式显示，回复变长不会挤动思考；只有思考自己在长，或新的记录到来，才会触发折叠，画面像是自己往上滚进了历史。
- **画面永远比终端矮。** 画面（可改动的那一块）一旦和终端一样高，终端里滚出去的那几行就再也擦不掉，下一帧的擦除少擦了，旧的一帧就留在滚动历史里：一个很长的回复出现时同一段对话会重复好几遍（真实使用中见到过）。所以先按终端的高度算出能放下的部分，**只画最新的、放得下的那些项**，放不下的同一时刻进入记录；一项连单独都放不下（一个几十行的回复）就整个进入记录。每一行都先按本进程的宽度尺子（第 6 节，`string-width`）切好再画，保证终端不会把任何一行再折一次，Ink 数的行数就是真实的行数；右边留两列。`ink-terminal.test.ts`（窄）与 `ink-terminal-wide.test.ts`（歧义宽度字符画成两列）用一个会折行、会擦行、会保留滚动历史的小终端回放五轮长回复，检查每个回复只出现一次。
- 块的标题一行（"▾ ✻ main 思考 3.2s"，流式时和结束后都是灰色）与它下面的内容。折叠过的块是一行"▸"（`Ctrl+O`）或进入记录的一行；省略过开头的块在标题下有一行 `…`。英文的思考按词换行，不把一个词切成两半。
- **回复**不在画面里一点点出现：模型在写的时候，这个 Agent 的活动行变成 `· main 正在输出回答 3s`（灰色，和其他活动行一样带计时）。消息发布（`MessagePublished`）时它回到原来的阶段，整条回复一次性进入记录（浅蓝，完整）；同一个 Agent 的下一次调用、运行转为等待输入、中断，也会清掉这一行。回复本身放不进限额时，也是整条进入记录，它之前还展开的思考块整块折叠进记录。
- 非 TTY 的逐行适配器不画思考块，只在 `/think` 时和折叠行出现时打印文字。

## 6. 界面问题的实现说明（RP1-UI-4）

- **UI-1、UI-2**：输入框是带光标的自有组件（`apps/cli/src/presentation/text-input.ts`，纯函数，有单元测试）：左右、Home/End、Ctrl+A/E、向前删除、Ctrl+U/K/W、多行内上下移动，字符按全角宽度计算，光标处用反色字符显示，粘贴按光标位置插入。用 Ink 的 `useCursor` 把真实光标放到输入位置（光标的行 = 画面上方各行的行数，由布局直接算出；每一行都固定占一行，所以不需要事后测量），输入法的窗口因此开在文字处；状态行在输入框上方，输入框是画面的最后一行。输入框的每一行文字由 `layoutBox` 切成屏幕行：切法是 Ink 自己的那一个（`wrap-ansi` 的同一个调用、同样的参数，宽度度量用 `string-width`，即 Ink 的 `wrapText` 用的那两个），较长的行接在文字下面而不是提示符下面，每一屏幕行画成一个 `Text`（所以不会再被切一次）；光标的行和列由同一份行算出，不另建模型。用 Ink 画出随机的多行、中英文混排、宽字符、表情和占位符的输入，在 Ink 画出的结果里找光标处的字符，行列必须等于计算值（`input-box-ink.test.ts`），Ink 的切法一变这个测试就失败。
- **粘贴占位符（UI-6）**：用 Ink 的 `usePaste`（括号粘贴模式）接收粘贴，一次粘贴超过 15 个字符就不放进输入框的文字，而是放一个占位符字符（私有区字符加序号，文字存在旁表里），输入框把它画成 `[paste 14 lines]`（一行的粘贴写 `[paste N chars]`）。占位符在文字里只是**一个字符**，所以光标移动、退格、`Delete`、Ctrl+U/K/W 对它都是整体的一步；发送时 `expand` 换回原文，输入框里手打的占位符字符被剔除，不能伪造。不是括号粘贴、但一次到达且含换行的输入同样按粘贴处理（输入法一次上屏的文字不含换行，不受影响）。**历史（`↑`）与取回排队消息保存整个输入状态，所以取回时仍是占位符**：取回排队消息时按"哪条历史展开后等于它"找回状态，找不到才还原成文字。
- **输入框的高度（UI-6）**：高度取 `max(2, min(10, 终端行数 − 8))`，无论终端多矮都不少于 2 行。超出时只画光标所在的一段，被藏起来的那一侧用一行 `…` 顶替一行文字，所以在中间时上下两侧都有；窗口在光标还在里面时不动，光标出界才移动最少的距离；至少画一行文字。
- **画面总高度的硬保证（UI-6）**：画面（可改动的那一块）永远比终端矮。输入框有自己的高度；询问文字和活动行共用剩下的行数，询问优先，放不下时询问保留首尾、中间用 `…`，活动行只画前面几条，最后一行写"… 另有 N 项活动"；剩下的才是上方记录区的限额。终端矮到连最少的行数都放不下时无法保证，这是已知的下限。
- **消息大小上限**：用户消息不超过 100 KB（UTF-8 字节，`MAX_INPUT_BYTES`）。没超过时什么都不提示；超过时不发送，控制台提示"消息太长（N KB），超过 100 KB 的上限，没有发出"，输入框里的内容原样留着，不丢。限制写在 `Console.submit` 和 `Console.steer`（所有适配器共用），输入框先用同一条规则判断，所以超限时不清空输入。
- **字符宽度只有一把尺子**（`apps/cli/src/presentation/terminal-width.ts`）：中文里常见的弯引号“”、破折号——、省略号……、间隔号·在 Unicode 里是歧义宽度，终端按字体、语言或设置画成 1 列或 2 列，而 Ink、`wrap-ansi`、输入框的光标都按同一个宽度算，否则换行的位置和光标会与屏幕差一格。启动时（`createTerminal` 之前、画任何东西之前）量一次：在备用屏幕上、文字被隐藏、包在同步更新里，一次写出“ — … · 并各发一个光标位置查询（`ESC[6n`），由回报的列数得到 1 或 2，最后恢复屏幕、光标和输入模式，使用者看不到任何一步，打字期间输入的内容原样还给输入。不是终端（管道、CI、`TERM=dumb`）、终端不回应（150 毫秒）或任何一步出错，就用标准的默认（窄），所有系统同一条规则；环境变量 `MAS_AMBIGUOUS_WIDTH=narrow|wide` 覆盖测量，`auto` 或不设为测量。结果放在 `globalThis[Symbol.for('multiagentos.ambiguousIsNarrow')]`，由 `patches/string-width@8.3.0.patch` 让 `string-width`（Ink 与 `wrap-ansi` 都用它）在没有显式参数时读取，所以不改 Ink，也没有第二个尺子；`string-width` 升级时补丁会因对不上而失败，要重新做。上方记录区域的预先切行也用同一把尺子（`wrapLines`）。`ESC[…R` 的迟到回报不会变成输入（Ink 把它当作不认识的控制序列，有测试）。Ink 会把量过和切过的结果缓存一个进程，所以尺子一个进程只设一次，测试里宽、窄两种情形各占一个测试文件。
- **UI-3**：等待使用者的阶段（授权、回答、暂停）不显示秒数，`ActivityLine.waitsForUser` 标明；系统在工作的阶段仍然计秒。
- **UI-4**：授权询问里的命令超过 3 行或 240 个字符时只显示开头与"共 N 行、M 个字符"，并多一个选项 `v`（查看完整命令）：`v` 把完整命令打印出来，询问仍然留着，**没有回答**。命令里的转义序列按文字显示。放行范围、网络、命中名单照旧显示，并且"批准的就是显示的那一条命令"这一点不变。
- **上下文占比**：状态行在状态后面写 `(上下文已用N%)`（`------ 等待输入 (上下文已用30%) ------`，所有状态都带）。数值是 Kernel 每次组装 main 的下一次调用时算出的（实测加估算），除以单次输入上限；这次组装需要压缩时不发（压缩之后会重新组装，发的是新的值）。刚进入或切换到一个对话时没有，`/compact` 被受理或运行自己的压缩开始时清掉，到下一次组装才回来。没有主动提醒，是否压缩由用户判断。
- **UI-5**：用户的输入是柔绿（`#7ee787`），系统层面的一切是黄色（系统的话、授权与询问、排队提示），状态行是粉色并写成 `------ 状态 ------`，对话列表是灰色，助手的回复是浅蓝（`#79c0ff`）；颜色由测试在强制开启颜色时检查。"全是白色"没有复现；如果仍然是白色，先看环境变量 `NO_COLOR` 与 `FORCE_COLOR`，以及终端是否支持颜色。
