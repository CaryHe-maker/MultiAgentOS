# MultiAgentOS M2 发布计划

> 2026-11-07。本文是从现在到 M2 发布的计划，取代已冻结的旧计划（[History/M2/M2Plan](../History/M2/M2Plan.md)）。
> 范围与设计以 [M2Design](M2Design.md) 为准；已实现部分的现状见 [M2Baseline](M2Baseline.md)；仍然有效的决定见 [M2Decisions](M2Decisions.md)。
> 本文按 phase 0–3 组织，不设日期。任务编号 `RP<phase>-<工作流>-<序号>`，与旧计划的 `S<阶段>-…` 不会混淆。

## 1. 权威与关系

- M2 交付什么、怎样设计，以 M2Design 为准；本文只规定按什么顺序、分成哪些任务、达到什么标准发布。本文与 M2Design 冲突时以 M2Design 为准，并修正本文。
- 旧计划已冻结，不再是标准。它的"阶段 0–8"与本文的 phase 0–3 没有对应关系；旧阶段做完了什么见 M2Baseline 第 2 节。
- 范围变化必须先发布 M2Design 的新版本，再修改本文（第 9 节）。
- 全部任务由同一位负责人（Cary）承担，任务拆分的首要目标仍是让尽可能多的任务同时进行：每个任务有明确的目录归属、只依赖已经合入的契约、有能独立运行的测试。

## 2. 发布标准

M2 发布必须同时满足（承接旧计划的完成定义与阻断项，重新表述）：

1. M2Design 第 13 节的全部验收用例通过，第 8 节的量化标准满足（第 6 节补充了判定方式）。
2. M2Design 第 12 节的每条不变量都有对应的测试。
3. 每个组件文档的状态都是"已实现"，文档与实现一致；`Interface/`、SharedContracts 与 AgentToolPool 一致。
4. 在 Ubuntu 24.04 LTS 上，`pnpm run check`、端到端测试与全部验收用例通过，真实模型评测的结果写入验收证据。
5. `M2Usage.md`、`M2Limitations.md`（含威胁模型的结论）、`docs/` 根目录的 `M2AcceptanceEvidence.md` 与 README、索引一致。
6. 发布阻断项全部清零：M2Design 第 14.1 节列出的阻断项；不变量缺少测试；接缝修改未经契约门进入 `feat/M2`；文档状态与实现不一致；M2Baseline 第 5 节的缺口要么修复，要么逐条写入 `M2Limitations.md`。

## 3. 侧重点

下面四个方向是优化的重点，**不是实现顺序**：每个 phase 都会涉及其中几个，具体落在哪个 phase 见第 5 节。另有两项支撑工作贯穿全程。

| 方向 | 要做什么 | 主要落在 |
|---|---|---|
| **Workflow 设计与 Orchestration** | 使用者模板、条件边、有界循环、`all_done`、并行 main 节点；预置工作流；模板运行的额度、回退与报告 | phase 2 |
| **Agent 与 Prompt 设计** | main、explorer、worker 与新增 Agent 的提示词与定义；派生准则（D 组）；Prompt 模板库；用固定任务集迭代并比较版本 | phase 1（Turn-chat 的 Agent）、phase 2（预置工作流的 Agent） |
| **Tool、Executor 与工具提示词** | 审计现有工具从模型视角看到的描述、参数、错误文字与结果形状；按评测证据增加工具；优化工具的提示词 | phase 1、phase 2（都可以看情况增加工具） |
| **系统层与业务层隔离、安全、健全性** | 避免注入攻击（工具结果、网页、仓库文件、模板、`AGENTS.md`）；对抗用例集；威胁模型复核；系统健全性（恢复、资源、错误处理） | 贯穿；phase 3 集中审计 |
| 支撑一：评测基础设施 | 统一的任务集、运行器、判分、记录与版本对比；成本与延迟基线 | phase 0 建立，其余 phase 使用 |
| 支撑二：发布准备与效率 | 成本与延迟优化、缓存命中、完成度、使用与限制文档、验收证据 | phase 3 |

两条贯穿的约束：

- **每个新增工具、模板或 Agent 都带安全检查。** 加入时同时写它的注入路径分析与对抗用例，不留到最后统一补。
- **提示词与定义的改动必须有数据。** 改动之前与之后都在固定任务集上运行，结果记录在案；没有评测的提示词只能保持 `v0.1.0` 草稿。

## 4. 组织原则

### 4.1 每个 phase 的四道工序

```text
文档门 → 契约门 → 并行实现 → 集成与退出
```

1. **文档门**：本 phase 涉及的组件文档章节与 `Interface/` 章节写完并评审，状态改为"已评审"。下一 phase 的文档门可以在本 phase 并行实现期间同时编写。
2. **契约门**：只修改共享接缝（第 4.3 节）：Schema、Port、`packages/testing` 中的 fake 与契约测试。单独一个 PR，合入后才开始并行实现。
3. **并行实现**：任务按工作流同时进行，每个任务只改自己工作流的目录，只依赖已合入的契约，用 fake 替代其他组件。
4. **集成与退出**：组合根接线、跨组件集成测试、本 phase 的验收用例与真实模型评测；全部通过后进入下一个 phase。

### 4.2 工作流与任务编号

| 工作流 | 编号 | 目录归属 |
|---|---|---|
| 文档与整理 | `DOC` | `docs/` |
| 评测与测试环境 | `EV`、`EN` | `apps/control-plane/test/`、`packages/testing`、`scripts/`、CI 配置 |
| Workflow | `WF` | `packages/modules/workflow` |
| Kernel 与执行 | `KC`、`KX` | `packages/modules/kernel` |
| Agent、Prompt 与模板定义 | `PA`、`TPL` | `packages/libraries/agent-tool-pool` |
| 工具与 Executor | `TL` | `packages/libraries/executor-set`，以及对应的契约 |
| 界面 | `UI` | `packages/modules/user-interaction`、`apps/cli` |
| 安全 | `SC` | 跨目录；用例在 `packages/testing` 与 `apps/control-plane/test/` |
| 健壮性与效率 | `RB`、`EF` | 跨目录 |

### 4.3 分支与共享接缝

- `feat/M2` 是集成分支，M2 发布时经 PR 合入 `main`。工作分支 `feature/M2/rp<N>-<主题>`（文档用 `docs/M2/rp<N>-<主题>`），从 `feat/M2` 创建，经 PR 合回，使用 merge commit；每个 phase 完成后合入一次，合入前在 Ubuntu 24.04（WSL）跑完整质量门。
- 当前工作分支 `feature/M2/prompt-agent` 承载 phase 0 的整理；phase 1 起按上面的命名另开分支。
- 以下内容是接缝，只在契约门或集成任务中修改：`packages/libraries/contracts`、`packages/testing`、`packages/modules/kernel/src/interfaces`、各包的 `XxxDeps` 与工厂签名、根目录的构建与检查配置（`package.json`、`tsconfig*.json`、`eslint.config.js`、`vitest.config.ts`、`pnpm-lock.yaml`）。
- 修改规则：先合入 `feat/M2`，其他任务分支同步之后再依赖它；任务发现接缝缺口时先用本地 fake 继续，同时提出契约任务补齐；每次同步之后在 Ubuntu 24.04 上运行 `pnpm run check`。

### 4.4 真实模型评测的规矩

- 运行器必须带 `--yes` 与请求预算，密钥只从环境或指定文件读取，不写入记录。
- 记录追加到文件，已有的运行会跳过；每条记录带提交、模型、定义摘要、token、缓存命中与耗时。
- 结果是单个模型、有限次数的事实，写明次数与局限，不写成统计结论。
- 评测发现的问题当场修复并重跑，修复前后的记录都保留。

| RP0-EV-1 | **统一评测运行器**：任务规格（fixture 仓库、提示、确定性判分）、记录格式（提交、模型、定义摘要、token、缓存命中、耗时、成本）、预算与 `--yes`、两个版本之间的对比报告 | |

### 5.2 phase 1：达到发布标准的 Turn-chat 模式

**目标。** `chat` 模板的全部验收达到发布标准：用户与 main 对话，main 读、写、运行命令、联网、派生 SubAgent、被暂停与回退，压缩支撑长对话。重点是 Agent 与 Prompt、工具、安全与健壮性；这一 phase 可以按证据增加工具。

| 任务 | 内容 |
|---|---|
| RP1-PA-1 | **main 的提示词与派生准则**：目标 D 组达标（适合派生的 10 个中 ≥ 8 个正确派生，不适合的 10 个中误派生 ≤ 2 个）；每次改动在固定任务集上前后对比 |
| RP1-PA-2 | explorer、worker 的定义与提示词；`compaction-system` 的复核（摘要的各节、注入防护）；封存 `v1.0.0` 的条件写入 AgentToolPool |
| RP1-TL-1 | **工具审计**：从模型视角逐个检查现有工具的描述、参数、错误文字与结果形状；用真实模型找出会乱填参数、误解结果的地方（以往每次真实评测都找到过这类问题） |
| RP1-TL-2 | **按证据增加工具**：候选包括多处编辑一次完成的补丁工具、带结构化结果的测试运行工具、批量读取、代码轮廓或符号检索；每个候选先用评测证明有收益再实现，实现时带安全分析 |
| RP1-SC-1 | 对抗用例集覆盖 Turn-chat 的全部入口：网页、仓库文件、工具输出、`AGENTS.md`、命令输出、压缩摘要；加入多种注入写法，而不只是一种 |
| RP1-SC-2 | 授权、沙盒、回退的复核：恢复的 Session 不复用授权、凭据不进子进程与日志、`STOP_UNCONFIRMED` 后不继续推进 |
| RP1-RB-1 | 补齐没有端到端版本的验收：P3（重任务上的并行收益）、B1/B3/B4、H13、`ask_user` 的同意不产生授权 |
| RP1-RB-2 | 压缩之后的上下文上限：最新一段含超大工具结果时的处理；早先只修剪的压缩造成的信息缺口；压缩参数在真实窗口下的校准 |
| RP1-EV-1 | C1–C4 按发布口径（每个任务 5 次、至少 4 次成功）；R 回归；成本与延迟与 phase 0 的基线比较，不劣于基线 |
| RP1-UI-1 | 控制台的完成度：`/status`、帮助、错误文字、活动区的等待依赖任务、重复派生的提醒 |

**退出（M2Design 第 13 节）。** R、C、P（P4 与 P5 的并行 main 部分除外）、D、B、H、A、W、S、L 通过；成本与延迟不劣于基线；Turn-chat 的使用说明草稿写完。

### 5.3 phase 2：达到发布标准的预置编排模式（pre-orchestration）

**目标。** 在 Turn-chat 之外，提供预置的任务工作流：用户用 `mas run <模板> "<目标>"` 或 `/run` 启动一个按固定图运行的任务，图中有人类确认、并行分支、审阅循环与确定性的运行报告。这一 phase 交付编排的机制、**至少两个通用的特定任务工作流**，以及一组供模板调用的 Agent 与 Prompt 模板。可以按证据增加工具。

**至少交付的工作流**（具体清单与验收阈值在文档门中与负责人确认，见第 8 节）：

| 工作流 | 用途 | 图的形状（草案） |
|---|---|---|
| `research` | 研究架构：对一个问题做调研并写出带来源的报告 | clarify（询问）→ plan → 并行 explorer 调研 → synthesize → review（人类审阅，不通过回到 plan，最多 3 次）→ report |
| `paper` | 论文架构：写一份有结构的长文 | 提纲 → 人类确认提纲 → 分节并行撰写 → 引用与事实核对 → 审阅循环 → 汇编 |
| `task` | 通用任务架构：把一个任务拆开做完 | clarify → plan → 人类确认 → 并行 worker（`writeScope` 不相交）→ verify（失败回到执行，有界）→ report |

**Agent 与 Prompt 模板库。** 在现有 main、explorer、worker、planner、code-viewer 之外，按工作流的需要增加 Agent 定义（候选：researcher、writer、reviewer、verifier），并把可复用的提示词片段做成 Prompt 模板，由工作流模板按名字引用、带参数。库的格式、版本与摘要比较沿用 AgentToolPool 的定义机制，不为模板另开一套。

| 任务 | 内容 |
|---|---|
| RP2-WF-1 | 使用者模板的读取、编译与校验（含并行可写节点的 `writeScope` 检查，错误指明规则与节点） |
| RP2-WF-2 | 条件边、有界循环、`all_done` 的运行；输出节点未能运行时的确定性运行报告；模板运行的回退与差异 |
| RP2-KC-1 | 模板节点的份额从 Turn 账本划出；并行 main 节点的写入占用检查（P4、P5 的并行部分） |
| RP2-PA-1 | Agent 定义与 Prompt 模板库：库的格式、新增 Agent、片段的参数与引用；用固定任务集评测每个 Agent |
| RP2-TPL-1 | `research`、`paper`、`task` 三个模板，各带固定任务集与判分；`analyze` 与 `chat` 保持不变 |
| RP2-TL-1 | 工作流需要的工具：候选包括来源与引用的记录、报告与长文的汇编、`implement`（编程用）模板所需的验证工具；按证据决定，带安全分析 |
| RP2-SC-1 | 模板的安全：模板不携带权限（只能收窄）、模板与仓库材料都不可信、模板中的 HUMAN 节点、并行写入、`prompt` 节点不能由模板预设 |
| RP2-UI-1 | `mas run`、`/run`、模板列表与说明；运行中的图状态；结束后退出 |
| RP2-EV-1 | O 组（同一问题分别用 Turn-chat 与 `research` 运行，比较完成率、耗时与 token）、G 组、P4、P5；每个预置模板在自己的固定任务集上达到文档门定下的阈值 |

**退出。** O、G、P4、P5 通过；至少两个预置工作流在固定任务集上达到阈值，并有真实模型的评测记录；使用者模板的校验错误指明规则与节点；Turn-chat 的全部验收仍然通过（回归）。

### 5.4 phase 3：完善、加固，整理成可发布的 M2

**目标。** 不再增加功能。集中提高安全性、健壮性与效率，补齐完成度，把项目整理成可以发布的 M2。

| 任务 | 内容 |
|---|---|
| RP3-SC-1 | **安全审计**：复核 M2Security 的威胁模型；跑完整的对抗用例集（含 phase 1、2 新增的）；扫描日志与产物中的凭据；沙盒逃逸用例；实体机上的复核 |
| RP3-SC-2 | 隔离审计：系统层与业务层的边界是否被任何路径绕过（Agent 输出进入系统决定、模板改变权限、仓库材料被当作指令、摘要被当作指令） |
| RP3-RB-1 | **健壮性**：崩溃与恢复（任意时刻杀进程）、日志损坏、长时间运行、资源限制（沙盒的 CPU 与内存、内存压力的真实验证）、错误信息的可理解性、故障注入 |
| RP3-EF-1 | **效率**：缓存命中、成本与延迟优化、压缩与并行参数的校准、并发上限；与 phase 0 的基线比较，写入验收证据 |
| RP3-CO-1 | **完成度**：M2Baseline 第 5 节的缺口逐条修复或登记；控制台与错误文字；配置项的文档；`/thinking`、图视图等推迟的非安全功能按范围决定 |
| RP3-DOC-1 | `M2Usage.md`、`M2Limitations.md`（含威胁模型的结论）、`M2AcceptanceEvidence.md`；README 与索引；各组件文档的状态改为"已实现" |
| RP3-REL-1 | 冻结功能；在 Ubuntu 24.04 上运行全部质量门、全部验收用例与真实模型评测；`feat/M2` 经 PR 合入 `main` |

**退出。** 第 2 节的发布标准全部满足；阻断项清零；验收证据完整。

## 6. 验收标准的补充规定

承接旧计划第 8 节，仍然有效：

- **`analyze` 回归**：`analyze` 没有特殊额度，按 planner、code-viewer 的额度参数运行，模型调用关闭思考；成功率与来源完整性不低于 M1 的验收基线（[M1AcceptanceEvidence](../History/M1/M1AcceptanceEvidence.md)）。
- **D 组**：固定的判定表，每个任务事先写明"是否适合派生"与可接受的派生方式；结果按判定表自动比对，再由负责人逐项复核。
- **P3**：完工时间不超过关键路径的 1.3 倍，关键路径按同一次运行中各节点的实际耗时计算；并与"分批派生"及 LangGraph 同构图的对照数据一起写入证据。
- **O、成本、延迟**：在 phase 0 的基线上取值，此后作为回归门槛，后续 phase 与发布时的结果不得劣于已记录的值。
- **固定任务与 fixture**：R 是 M1 的 F1–F5 原样使用；C1–C4 各有一个固定 fixture 仓库；C5、S、H、A 是确定性用例（假模型、假时钟）；W 用本地固定内容服务器（含注入页面与指向内网的重定向）；L 用记录请求的假 provider，L1 另用真实模型跑固定的长对话；P、B、D、G、O 各有固定任务与判定表，由 phase 0 与对应 phase 的文档门给出。
- **新增的验收**：每个预置工作流有自己的固定任务集与阈值（phase 2 文档门定下）；对抗用例集中的每一项都必须被拦截或被模型识破后仍不产生副作用。

## 7. 风险

| 风险 | 对策 |
|---|---|
| 提示词与模板的改动没有可比较的基准，优化变成凭感觉 | phase 0 先建评测基础设施与基线；第 3 节的约束：没有评测数据的提示词不定稿 |
| 真实模型评测的成本与波动 | 预算与 `--yes`；记录次数与局限；确定性判分；基线随提交保存 |
| phase 2 的编排机制与预置工作流同时开发，互相拖延 | 机制（WF、KC）先在最小模板上通过 G、P4、P5，再做三个预置模板；模板之间互不依赖 |
| 新增工具与模板扩大攻击面 | 第 3 节的约束：每个新增项带注入路径分析与对抗用例；phase 3 再做一次整体审计 |
| 旧文档与代码注释里残留旧阶段编号，造成误读 | phase 0 的 RP0-DOC-1 与 RP0-CL-1 一次清掉；History 之外不再使用旧编号 |
| 范围蔓延 | 第 9 节 |

## 9. 范围控制

范围不足时，可以减少各组 fixture 的数量，或推迟非安全相关的界面功能（如 `/timeline`、`/thinking`、图视图），
但不得削减授权两步判定、沙盒、写入占用、额度收尾与必有报告、停机、日志的可重建性与安全验收。
任何范围变化必须先发布 M2Design 新版本，再修改本文。
