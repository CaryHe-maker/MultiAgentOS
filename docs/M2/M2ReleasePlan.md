## 1. 权威与关系

- M2 交付什么、怎样设计，以 M2Design 为准；本文只规定按什么顺序、分成哪些任务、达到什么标准发布。本文与 M2Design 冲突时以 M2Design 为准，并修正本文。
- 旧计划已冻结，不再是标准。它的"阶段 0–8"与本文的 phase 0–3 没有对应关系；旧阶段做完了什么见 M2Baseline 第 2 节。
- 范围变化必须先发布 M2Design 的新版本，再修改本文（第 9 节）。
- 全部任务由同一位负责人（Cary）承担，任务拆分的首要目标仍是让尽可能多的任务同时进行：每个任务有明确的目录归属、只依赖已经合入的契约、有能独立运行的测试。

## 2. 发布标准

M2 发布必须同时满足（承接旧计划的完成定义与阻断项，重新表述）：

1. M2Design 第 13 节的全部验收用例通过，第 8 节的量化标准满足（第 6 节补充了判定方式）。
2. M2Design 第 12 节的每条不变量都有对应的测试。
3. 每个组件文档的状态都是"已实现"，文档与实现一致；`Interface/`、SharedContracts 与 AgentToolPool 一致。
4. 在 Ubuntu 24.04 LTS 上，`pnpm run check`、端到端测试与全部验收用例通过，真实模型评测的结果写入验收证据。
5. `M2Usage.md`、`M2Limitations.md`（含威胁模型的结论）、`docs/` 根目录的 `M2AcceptanceEvidence.md` 与 README、索引一致。
6. 发布阻断项全部清零：M2Design 第 14.1 节列出的阻断项；不变量缺少测试；接缝修改未经契约门进入主分支；文档状态与实现不一致；M2Baseline 第 5 节的缺口要么修复，要么逐条写入 `M2Limitations.md`。

## 3. 侧重点

下面四个方向是优化的重点，**不是实现顺序**：每个 phase 都会涉及其中几个，具体落在哪个 phase 见第 5 节。另有两项支撑工作贯穿全程。

| 方向 | 要做什么 | 主要落在 |
|---|---|---|
| **Workflow 设计与 Orchestration** | 自主编排的执行底座（任务树、休眠与唤醒、消息、后台命令、写入隔离、checkpoint）；编排范式；严格模式的模板（条件边、有界循环、`all_done`） | phase 2 |
| **Agent 与 Prompt 设计** | main、explorer、worker、lead 的提示词与定义；派生准则（D 组）；范式手册；用固定任务集迭代并比较版本 | phase 1（Turn-chat 的 Agent）、phase 2（编排的 Agent 与范式） |
| **Tool、Executor 与工具提示词** | 审计现有工具从模型视角看到的描述、参数、错误文字与结果形状；按评测证据增加工具；优化工具的提示词 | phase 1、phase 2（都可以看情况增加工具） |
| **系统层与业务层隔离、安全、健全性** | 避免注入攻击（工具结果、网页、仓库文件、模板、`AGENTS.md`）；对抗用例集；威胁模型复核；系统健全性（恢复、资源、错误处理） | 贯穿；phase 3 集中审计 |
| 支撑一：评测基础设施 | 统一的任务集、运行器、判分、记录与版本对比；成本与延迟基线 | phase 0 建立，其余 phase 使用 |
| 支撑二：发布准备与效率 | 成本与延迟优化、缓存命中、完成度、使用与限制文档、验收证据 | phase 3 |

两条贯穿的约束：

- **每个新增工具、模板或 Agent 都带安全检查。** 加入时同时写它的注入路径分析与对抗用例，不留到最后统一补。
- **提示词与定义的改动必须有数据。** 改动之前与之后都在固定任务集上运行，结果记录在案；没有评测的提示词只能保持 `v0.1.0` 草稿。

## 3a. 路线与基线

路线（2026-11-11，Cary 决定）：

1. **phase 1：先把 Turn-chat 优化到基线 2。** 先设计任务集，再录基线 1，然后优化提示词、工具与效率，直到达到基线 2。
2. **phase 2：实现多 Agent 并行执行底座，并把它优化到它自己的基线 2。** 自主编排为缺省，固定工作流降为范式；任务集与基线的做法同 phase 1（2026-11-12 改写，第 5.3 节）。
3. **phase 3：整体优化并发布。** 整体优化之外，把 Orchestration 的功能做成可以被 Turn-chat 直接调用的子图（M2Design 第 14.2 节第 19 条），然后发布。

基线的含义：

| 名称 | 是什么 | 什么时候录 |
|---|---|---|
| 基线 1 | 一个模式的任务集建好之后、改任何提示词与工具之前的第一次记录 | 任务集完成后立即录，作为"优化前"的参照 |
| 基线 2 | 优化之后第一次"准通过"的记录：成功率、token、耗时都已记下，并达到该模式的目标 | 优化完成时录；此后是回归门槛，后续改动与发布时的结果不得劣于它 |

- **Turn-chat 的基线 2 的目标：效果不明显差于 DeepSeek Harness。** 在同一任务集、同一模型、同一预算下，把 DeepSeek Harness 当作对照一起运行；"不明显"的具体判定（成功率、token、耗时各自的容忍）在 phase 1 的任务集文档里定下，由负责人确认（第 8 节）。
- **Orchestration 的基线 2 的目标：在一部分大任务上相比 DeepSeek Harness 有原生优势。** 对照对象是 `dsh`（中性提示与委派优先提示两种）以及关闭派生的本项目（消融）；判定见 [Phase2Plan](Phase2Plan.md) 第 4.5 节，阈值由负责人确认。
- **任务集的考量点**：任务完成的成功率、token 消耗、完成花费的时间。Turn-chat 的第一批任务集分两类：代码功能、并行功能。
- 任务集在优化过程中会被反复使用，容易被过拟合，也不能由我们自己出题、自己调优、再和别人比较：任务集分三层——开发集（优化时用）、自建留出集（别人出题，只在里程碑运行）、公开最终集（公开测试集的封存子集，没有调过，基线 2 的结论以它为准）。题的规模、来源与筛选见 [Phase1TaskSet](Phase1TaskSet.md)。
- 对照对象首选 DeepSeek Harness；如果它无法在 WSL 里正常工作，用 OpenCode 作为对比基准（判定条件见 Phase1TaskSet 第 5 节）。

## 4. 组织原则

### 4.1 每个 phase 的四道工序

```text
文档门 → 契约门 → 并行实现 → 集成与退出
```

1. **文档门**：本 phase 涉及的组件文档章节与 `Interface/` 章节写完并评审，状态改为"已评审"。下一 phase 的文档门可以在本 phase 并行实现期间同时编写。
2. **契约门**：只修改共享接缝（第 4.3 节）：Schema、Port、`packages/testing` 中的 fake 与契约测试。单独一个 PR，合入后才开始并行实现。
3. **并行实现**：任务按工作流同时进行，每个任务只改自己工作流的目录，只依赖已合入的契约，用 fake 替代其他组件。
4. **集成与退出**：组合根接线、跨组件集成测试、本 phase 的验收用例与真实模型评测；全部通过后进入下一个 phase。

### 4.2 工作流与任务编号

| 工作流 | 编号 | 目录归属 |
|---|---|---|
| 文档与整理 | `DOC` | `docs/` |
| 评测与测试环境 | `EV`、`EN` | `apps/control-plane/test/`、`packages/testing`、`scripts/`、CI 配置 |
| Workflow | `WF` | `packages/modules/workflow` |
| Kernel 与执行 | `KC`、`KX` | `packages/modules/kernel` |
| Agent、Prompt 与模板定义 | `PA`、`TPL` | `packages/libraries/agent-tool-pool` |
| 工具与 Executor | `TL` | `packages/libraries/executor-set`，以及对应的契约 |
| 界面 | `UI` | `packages/modules/user-interaction`、`apps/cli` |
| 安全 | `SC` | 跨目录；用例在 `packages/testing` 与 `apps/control-plane/test/` |
| 健壮性与效率 | `RB`、`EF` | 跨目录 |

### 4.3 分支与共享接缝

- 三层分支：`main` ← `feat/M2` ← `feature/M2/prompt-agent`（本计划的**主分支**）← 各 phase 的工作分支。
- 每个 phase 的工作分支 `feature/PLphase<N>/main`（`PL` 指本发布计划）从 `feature/M2/prompt-agent` 创建，完成后 PR 回 `feature/M2/prompt-agent`，使用 merge commit；合入前在 Ubuntu 24.04（WSL）跑完整质量门。同一 phase 内按工作流可以再开分支，同样合回该 phase 的分支或主分支。
- 四个 phase 全部完成、发布标准满足之后，`feature/M2/prompt-agent` 一次性 PR 合入 `feat/M2`；`feat/M2` 在此之前不接收本计划的 phase 分支。M2 发布时 `feat/M2` 经 PR 合入 `main`。
- phase 0 的文档对齐直接在 `feature/M2/prompt-agent` 上完成；phase 0 的其余任务在 `feature/PLphase0/main` 上做。
- 以下内容是接缝，只在契约门或集成任务中修改：`packages/libraries/contracts`、`packages/testing`、`packages/modules/kernel/src/interfaces`、各包的 `XxxDeps` 与工厂签名、根目录的构建与检查配置（`package.json`、`tsconfig*.json`、`eslint.config.js`、`vitest.config.ts`、`pnpm-lock.yaml`）。
- 修改规则：先合入 `feature/M2/prompt-agent`，其他任务分支同步之后再依赖它；任务发现接缝缺口时先用本地 fake 继续，同时提出契约任务补齐；每次同步之后在 Ubuntu 24.04 上运行 `pnpm run check`。

### 4.4 真实模型评测的规矩

- 运行器必须带 `--yes` 与请求预算，密钥只从环境或指定文件读取，不写入记录。
- 记录追加到文件，已有的运行会跳过；每条记录带提交、模型、定义摘要、token、缓存命中与耗时。
- 结果是单个模型、有限次数的事实，写明次数与局限，不写成统计结论。
- 评测发现的问题当场修复并重跑，修复前后的记录都保留。

## 5. 各 phase

### 5.1 phase 0：整理结果，建立冻结的系统测试与通用评测体系

**目标。** 把 M2 之前的工作整理成可以直接依据的基线，并建立后面三个 phase 都要用的两样东西：
(1) **冻结的通过式系统测试**，覆盖系统的健全性与安全性，每个 phase 发布时都要重新跑一遍，保证后面的改动不会弄坏底线；
(2) **通用评测体系**，对任何模式的任何测试集统一统计耗时、token、各工具使用次数等，之后不必为每种新测试另建评测。
phase 0 不增加产品功能，也不预先定死 Turn-chat 或编排的具体任务集（它们的功能还会变化）。

**两类测试的分工。**

| | 冻结的系统测试 | 评测体系 |
|---|---|---|
| 问什么 | 系统在**任何**模型行为下是否守住底线 | 模型与提示词、模板、工具**表现得好不好** |
| 模型 | 假模型，包括被攻陷的假模型（照着注入内容执行恶意动作） | 真实模型 |
| 结果 | 通过或失败，一项失败阻断发布 | 统计量：通过率、成本、耗时，与上一次比较 |
| 成本与频率 | 不花钱，每次提交都跑 | 按需运行，带预算 |
| 变更规则 | 冻结：修改要评审，不得为让新功能通过而改断言 | 任务集随模式演进 |

| 任务 | 内容 | 状态 |
|---|---|---|
| RP0-DOC-1 | 冻结旧计划并归档（`History/M2`）；写 M2Baseline、M2Decisions、本文；旧阶段标记改为现在时的描述 | 完成 |
| RP0-ST-1 | **清点**：M2Design 第 12 节的每条不变量、第 14.1 节的每个发布阻断项、第 13 节各组的确定性用例，各对应哪个测试；列出没有测试的项（[M2FrozenTests](M2FrozenTests.md)） | 完成：[M2FrozenTests](M2FrozenTests.md)，清点可执行；I17 待 phase 2 |
| RP0-ST-2 | **被攻陷假模型的对抗用例**：每种能力一个越权尝试（写、命令、联网、读仓库外、读凭据）；每类注入入口一个（网页、仓库文件、命令输出、`AGENTS.md`、压缩摘要）；模板与并行写入的越界（模板部分待 phase 2）。系统必须在模型完全被攻陷时仍然拦住 | 完成：7 个用例；模板部分待 phase 2 |

### 5.2 phase 1：达到发布标准的 Turn-chat 模式

**目标。** 先设计任务集（代码功能、并行功能；成功率、token、耗时），录下基线 1，再优化，直到 Turn-chat 达到基线 2：效果不明显差于 DeepSeek Harness（第 3a 节）。`chat` 模板的全部验收达到发布标准：用户与 main 对话，main 读、写、运行命令、联网、派生 SubAgent、被暂停与回退，压缩支撑长对话。重点是 Agent 与 Prompt、工具、安全与健壮性；这一 phase 可以按证据增加工具。

| 任务 | 内容 |
|---|---|
| RP1-PA-1 | **main 的提示词与派生准则**：目标 D 组达标（适合派生的 10 个中 ≥ 8 个正确派生，不适合的 10 个中误派生 ≤ 2 个）；每次改动在固定任务集上前后对比 |
| RP1-PA-2 | explorer、worker 的定义与提示词；`compaction-system` 的复核（摘要的各节、注入防护）；封存 `v1.0.0` 的条件写入 AgentToolPool |
| RP1-TL-1 | **工具审计**：从模型视角逐个检查现有工具的描述、参数、错误文字与结果形状；用真实模型找出会乱填参数、误解结果的地方（以往每次真实评测都找到过这类问题） |
| RP1-TL-2 | **按证据增加工具**：候选包括多处编辑一次完成的补丁工具、带结构化结果的测试运行工具、批量读取、代码轮廓或符号检索；每个候选先用评测证明有收益再实现，实现时带安全分析 |
| RP1-SC-1 | 对抗用例集覆盖 Turn-chat 的全部入口：网页、仓库文件、工具输出、`AGENTS.md`、命令输出、压缩摘要；加入多种注入写法，而不只是一种 |
| RP1-SC-2 | 授权、沙盒、回退的复核：恢复的 Session 不复用授权、凭据不进子进程与日志、`STOP_UNCONFIRMED` 后不继续推进 |
| RP1-RB-1 | 补齐没有端到端版本的验收：P3（重任务上的并行收益）、B1/B3/B4、H13、`ask_user` 的同意不产生授权 |

### 5.3 phase 2：多 Agent 并行执行底座与可选的编排范式

> 2026-11-12 改写（Cary 决定，M2Design v1.36）。原来"预置编排模式"的目标（按固定图运行的 `research`、`paper`、`task` 等预置工作流）不再是交付要求，固定工作流降为范式，按固定图执行保留为严格模式。总纲见 [Phase2Plan](Phase2Plan.md)。

**目标。** 交付一个可靠的多 Agent 并行执行底座，加一组可选的编排范式：

- 缺省入口是自主分解：`mas run "<目标>"`（内置模板 `mission`），负责人自己决定拆不拆、怎么拆、拆成几层；
- 系统只写死底线：权限与沙盒、写入范围与借出、额度、深度上限、唤醒上限、子任务没结束不能交付、日志可重建、checkpoint 与回退；
- 范式（扇出与汇合、多层负责人、先探路再施工、接口先行、分节撰写与统一审校、长时间步骤放后台、纠偏、单人完成）写给负责人参考，不强制；
- 预编排模式：模板引擎保留，按固定图执行；用户可直接调用，自主编排的负责人也可以把一部分交给它（主线）；设计放到最后，现在预留位置；
- **在 M2 提交时，用真实模型的对照实验证明，至少在一部分大任务上相比 DeepSeek Harness 有原生优势**（Phase2Plan 第 4 节，M2Design 第 13 节 X 组）。

| 任务 | 内容 |
|---|---|
| RP2-OR-1 | Orchestration 的机制（[Orchestration](Orchestration.md) 第 15 节）：任务树、休眠与唤醒、消息、嵌套派生、写权限包、停止与中断、后台命令（已完成）；checkpoint 取代 Turn、`ask_user` 改为休眠、Kernel 单独中断一个 AgentRun |
| RP2-PT-1 | 范式手册：写入 main、lead 的提示词与 `mission` 的目标说明；每条范式带任务集里的例子；按 Orchestration D30 的三条要求（实验验证、作为预编排的接口、写成明确的指令）改写；关闭、参考、指定三档在任务集上评测 |
| RP2-ST-1 | 预编排模式：模板引擎、使用者模板的读取与校验（错误指明规则与节点）；`analyze` 保持；"负责人把一部分交给预编排流程"（主线）与样例模板放到最后设计，现在预留位置 |
| RP2-KC-1 | 把代码里以 `agent.id === 'main'` 识别顶层 Agent 的地方改为不依赖名字的概念（M2Baseline 缺口 13） |
| RP2-SC-1 | 编排的安全：消息不是指令也不带权限、借出范围的写入与命令、向上的中断被拒、模板不携带权限；对抗用例 |
| RP2-UI-1 | `mas run`、`/run`；运行中的任务树、休眠与作业的显示；`/checkpoints`、`/rewind` |
| RP2-EV-1 | **编排任务集**：基础任务（后台命令、子任务休眠汇合、消息、停止、中断）与大任务（多部件项目、跨模块修复、带慢测试的项目、分章写作、接口约定的并行开发），隐藏测试判分，分开发集与封存最终集；基线 1 在改提示词之前录 |
| RP2-EV-2 | **对照实验**：同一任务、同一模型与预算下运行本项目自主编排、`dsh`（中性提示与委派优先提示）、本项目单人（关闭派生）；按 Phase2Plan 第 4.5 节判定 |

**退出。** RP2-OR-1 完成并有端到端用例；O、G、P4、P5、X 组按 M2Design 第 13 节判定，X 组的结论（成立，或照实写明不成立及原因）有真实实验数据；Orchestration 达到它的基线 2；Turn-chat 的全部验收仍然通过（回归）。

## 6. 验收标准的补充规定

- **R 组（`analyze` 回归）**：不再要求与 M1 的验收结果一致（M2Design v1.34）。F1–F5 作为输入保留为评测体系中的普通任务，运行并记录，用来观察 `analyze` 没有退化；`analyze` 没有特殊额度，按 planner、code-viewer 的额度参数运行。
- **D 组**：固定的判定表，每个任务事先写明"是否适合派生"与可接受的派生方式；结果按判定表自动比对，再由负责人逐项复核。任务集在 phase 1 建立。
- **P3**：完工时间不超过关键路径的 1.3 倍，关键路径按同一次运行中各节点的实际耗时计算；并与"分批派生"及 LangGraph 同构图的对照数据一起写入证据。
- **O、成本、延迟**：每个模式的任务集建立后先录基线 1（Turn-chat 在 phase 1、预置工作流在 phase 2，都在改动提示词与工具之前），优化达标后录基线 2（第 3a 节），基线 2 是此后的回归门槛，后续 phase 与发布时的结果不得劣于已记录的值；回归的判定规则由评测体系统一给出（`Evaluation.md`）。
- **固定任务与 fixture**：C1–C4 各有一个固定 fixture 仓库；C5、S、H、A 是冻结的确定性用例（假模型、假时钟）；W 用本地固定内容服务器（含注入页面与指向内网的重定向）；L 用记录请求的假 provider，长对话另用真实模型评测；P、B、D、G、O 各有固定任务与判定表，由对应 phase 的文档门给出。
- **安全验收的两层**：被攻陷假模型的对抗用例是冻结的通过式测试，必须全部拦住；真实模型被注入后是否上当是评测体系中的统计量，只用来观察改动有没有让模型更脆弱，不作发布门槛。
- **新增的验收**：X 组（大任务对照实验），判定见 [Phase2Plan](Phase2Plan.md) 第 4.5 节；预置工作流不再各自设验收阈值。

## 7. 风险

| 风险 | 对策 |
|---|---|
| 提示词与模板的改动没有可比较的基准，优化变成凭感觉 | phase 0 先建评测体系；每个模式的任务集建立时先录基线；第 3 节的约束：没有评测数据的提示词不定稿 |
| 真实模型评测的成本与波动 | 预算与 `--yes`；记录次数与局限；确定性判分；基线随提交保存 |
| 自主编排依赖模型的拆分能力：模型在大任务上不拆或拆得不好，优势不成立 | 范式手册与提示词按评测数据迭代；过程指标（任务数、深度、休眠、消息）单独记录，区分"机制坏了"与"模型没用好"；对照实验含消融组，结论照实写 |
| 对照实验成本高（4 组 × 大任务 × 5 次） | 先在开发集上小规模试跑估算单次花费，再定预算；最终集只在里程碑运行 |
| 新增工具与模板扩大攻击面 | 第 3 节的约束：每个新增项带注入路径分析与对抗用例；phase 3 再做一次整体审计 |
| 旧文档与代码注释里残留旧阶段编号，造成误读 | phase 0 的 RP0-DOC-1 与 RP0-CL-1 一次清掉；History 之外不再使用旧编号 |
| 任务集被反复优化而过拟合，基线 2 好看、实际并不好 | 三层任务集：公开最终集封存、没有调过，留出集由别人出题，只在里程碑运行；开发集由 fixture 生成，换种子即得同类新题 |
| 对照对象（DeepSeek Harness）的运行条件与我们不同，比较失真 | 同一模型、同一提示文字、同一预算与时限；token 在模型接口处统一记录，不依赖各自的日志；运行条件在任务集文档里写明 |
| 范围蔓延 | 第 9 节 |

## 9. 范围控制

范围不足时，可以减少各组 fixture 的数量，或推迟非安全相关的界面功能（如 `/timeline`、`/thinking`、图视图），
但不得削减授权两步判定、沙盒、写入占用、额度收尾与必有报告、停机、日志的可重建性与安全验收。
任何范围变化必须先发布 M2Design 新版本，再修改本文。
