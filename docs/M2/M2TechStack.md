# MultiAgentOS M2 技术栈

> 状态：草稿。第 3 节的实测在阶段 0 完成后填写结果；第 4 节的新增依赖在所属阶段的文档门中确定。

## 1. 目的与权威

本文记录 M2 的运行环境、技术选择、新增依赖与阶段 0 的实测结果。
机制与设计以 [M2Design](M2Design.md) 为准；实测结果与 M2Design 不符时，先发布 M2Design 新版本，再改本文。
M2 沿用 M1 的工程基线（[M1TechStack](../History/M1/M1TechStack.md)），本文只写增加与改变的部分。

## 2. 运行与工程基线

| 项目 | 选择 | 相对 M1 |
|---|---|---|
| 平台 | Ubuntu 24.04 LTS（验收平台）；WSL2 中的 Ubuntu 24.04 用于日常验证 | 不变；沙盒相关的测试只能在这两种环境中运行 |
| Runtime、包管理、语言、Schema、测试、质量门 | Node.js `>=24.19.0 <25`、pnpm、TypeScript、TypeBox、Vitest 与 fast-check、ESLint 与 Prettier | 不变，版本见 M1TechStack 第 2 节 |
| 协议版本 | 新的 Schema 发布为 v2；v1 冻结，供 `analyze` 回归 | 新增 v2 |
| 系统依赖 | `bubblewrap`（`bwrap`）、`git`、`rg`（可选，M1 已有） | 新增 `bwrap` 与 `git` |

## 3. 阶段 0 实测

### 3.1 bubblewrap（任务 S0-T-1）

**环境**：每一项分别在 Ubuntu 24.04（原生）与 WSL2 中的 Ubuntu 24.04 上，以非特权用户运行。
记录 `bwrap --version`、内核版本、AppArmor 状态（`kernel.apparmor_restrict_unprivileged_userns`）。

| # | 检查项（M2Design 第 6.1、6.2、14.1 节） | 预期 | 原生结果 | WSL 结果 |
|---|---|---|---|---|
| 1 | 以完整 profile 运行 `/bin/true`（可用性探测） | 成功；不成功时记录原因与修复方法 | 待填 | 待填 |
| 2 | 先以 tmpfs 遮蔽 `$HOME`，再只读挂回白名单目录与仓库，再以 `--bind` 挂载可写根目录 | 挂载顺序生效；白名单外的 `$HOME` 内容不可见 | 待填 | 待填 |
| 3 | 以 `/dev/null` 只读覆盖单个敏感文件（如 `.env`）；以空 tmpfs 覆盖目录 | 命令读到空内容；写入失败 | 待填 | 待填 |
| 4 | 以 `--ro-bind` 重新挂载已存在的 `.git/`、`.multiagentos/`、`AGENTS.md` | 只读；运行结束后宿主仓库中没有新增文件或目录 | 待填 | 待填 |
| 5 | 命令在可写根目录中新建 `.git/hooks/x` 与 `AGENTS.md` | 能在沙盒内新建；运行后由事后检查发现（M2Design 第 6.1 节"新建保护"） | 待填 | 待填 |
| 6 | `--unshare-net`：访问外部地址与回环地址 | 失败 | 待填 | 待填 |
| 7 | `--unshare-pid`、`--die-with-parent`：杀死 bwrap 后，沙盒中的子进程全部结束 | 没有残留进程 | 待填 | 待填 |
| 8 | 对进程组先 SIGTERM、再 SIGKILL（M2Design 第 4.7 节） | 在宽限期内结束；记录实际耗时 | 待填 | 待填 |
| 9 | 环境变量白名单：沙盒中 `env` 的输出 | 只有白名单中的变量 | 待填 | 待填 |
| 10 | 在仓库位于 `$HOME` 之内、之外两种布局下重复 2–4 | 结果相同 | 待填 | 待填 |

**结论**：待填。需要写明可用的最低配置、AppArmor 的修复步骤（写入使用说明），以及与 M2Design 不符之处。

### 3.2 DeepSeek 思考模式（任务 S0-T-2）

**环境**：M1 使用的模型定义 `deepseek-flash@v1.0.0` 与 `deepseek-v4-pro@v1.0.0`；记录 API 的版本与调用日期。

| # | 检查项（M2Design 第 9.4、14.1 节） | 预期 | 结果 |
|---|---|---|---|
| 1 | 带工具的多轮请求中回传之前各轮的 `reasoning_content` | 正常返回 | 待填 |
| 2 | 带工具的多轮请求中不回传思考内容 | 记录是返回 400、静默停止还是正常 | 待填 |
| 3 | 历史中某一轮没有思考内容（例如那一轮关闭了思考），以空字符串补齐 | 记录 API 的实际行为 | 待填 |
| 4 | 收尾调用：只提供结束控制工具、`tool_choice = auto`、思考开启 | 记录模型调用结束工具的比例 | 待填 |
| 5 | 收尾调用重试：关闭思考、强制工具选择 | 与 M1 的行为一致 | 待填 |
| 6 | 思考强度：API 是否支持分档；支持哪些取值 | 给出 `none`、`low`、`high`、`max` 到 API 参数的映射；不支持分档时写明降级方式 | 待填 |
| 7 | 用量：思考 token 是否计入输出用量、计价方式 | 写明额度估算（Monitor 的 `est`）应当如何计入 | 待填 |

**结论**：待填。第 3、6、7 项的结果决定上下文组装与额度估算的写法，在阶段 1 的文档门中引用。
