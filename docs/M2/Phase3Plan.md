# Phase 3：完善、加固，整理成可发布的 M2

> 2026-11-15，Cary 决定。本文是 phase 3 的总纲：目标、新增的通用模式、评测任务集与运行规则、任务列表、顺序与需要的决定。
> 它取代 [M2ReleasePlan](M2ReleasePlan.md) 第 5.4 节原来的任务表；phase 2 移过来的事项见该文第 5.3 节的状态说明。机制的设计见 [Orchestration](Orchestration.md)，评测的做法见 [Evaluation](Evaluation.md)。

## 1. 目标

把项目整理成可以发布的 M2，并用证据回答两件事：

1. 在**小任务**上，系统不比 DeepSeek Harness（`dsh`）明显差，也不把简单任务搞复杂；
2. 在**大任务**上，多 Agent 并行相对 `dsh` 与本项目单人有没有原生优势（M2Design 第 13 节 X 组）。

两件事的结论不论成立与否都照实写入验收证据。**不设通过阈值**：尽可能做好，发布时以两组最终集的结果作为指标（第 3 节）。

## 2. 模式：保留 Turn-chat 与 Mission，新增通用模式 general（Orchestration D47）

### 2.1 为什么

phase 2 结束时的证据（[experiments](experiments.md) I2、I3）：

- 单纯的 Turn-chat 展示不出系统的并行能力，root 很少派任务；
- Mission 交付后就退出，不能接着对话；在小任务上，它多数时候和 Turn-chat 花费相当（不派任务的 28 题只多约 5%），开销集中在不该派的派发与范围过大的验证命令上。

### 2.2 三种模式

| 模式 | 是什么 | 状态 |
|---|---|---|
| `turn-chat` | 一轮一轮的对话：用户说一句，做到这一轮 `reply`，再等下一句 | 保留，不改 |
| `mission` | 一个预先给定的大任务一次跑出结果（`mas run "<目标>"`），交付后结束 | 保留，不改 |
| **`general`**（新增） | 一个模板同时支持两种用法：默认像 Turn-chat 一样一轮一轮对话；root 判断眼前是一段长任务时，**主动调用一个工具进入 Mission**，在同一个 Session、同一棵任务树上按 Mission 的方式完成；**交付结果后自动回到 Turn-chat**，用户可以继续追问或要求修改。`mas run` 下用 general 时，交付一次就退出 | 新建，待验证 |

- general 不一定比另外两种好，所以三种模式并存，由实验决定以后保留哪一种；在实验有结论之前不删除 Turn-chat 与 Mission。
- 进入 Mission 的工具：名字在实现时定，按 D39 的经验用模型熟悉的说法，不造新词；它的说明写明什么情况算长任务（两个以上能各自推进、只在接口上相接的部分；按规格从零构建；慢的构建或测试；一个人要做很久），以及"小的、一处改动贯穿几个互相依赖的文件，就自己做"。
- 进入 Mission 时才把团队的说明（决策表、工具说明书、完整例子）加进上下文，平时不常驻，小问题不背着整份手册。
- Mission 部分的规则沿用现有实现：计划书在第一次派任务时要求、root 派任务时打 checkpoint、子任务没结束不能交付。回到 Turn-chat 后 `ask_user` 原地等答复，超时按每次输入计算。
- 评价 general 用两组门槛同时看：小任务不比 Turn-chat 差（不把简单任务搞复杂），大任务上真的进入 Mission 并且有收益。只满足一边不算有效。

## 3. 评测任务集与运行规则（Orchestration D48）

### 3.1 四组任务集

| 组 | 小任务 | 大任务 |
|---|---|---|
| **开发集**（调参只用它） | 10 个，类似 phase 1 的小任务 | 4 个 |
| **最终集**（发布指标） | 10 个，类似 phase 1 的小任务 | 4 个以上，要求单个 Agent 至少运行 20 分钟以上 |

- **开发集与最终集不得高度相似**：不同的仓库、领域与题型；每个最终集任务写下与开发集的差别，选题时逐对检查。
- 小任务：开发集可以从 phase 1 的任务池（开发集 36 题、旧最终集 30 题）里选；最终集选 phase 1 没有用过的新题。phase 1 的旧最终集已经用过三次（mas 两次、dsh 一次，加上 I3 的 Mission 一次），不再作为最终集。
- 大任务：开发集可以用已经调过参的 `study.findex`、`study.healthhub` 与 study 系列；最终集的 4 个大任务由 Cary 写规格（形状分散：从规格做起的最多 1 个，其余如在已有代码库上分批迁移、跨模块的功能加修复、调研后实现、带长时间测试的项目），Claude 做 fixture、隐藏测试与参考解，离线验证判分有效（参考解通过、原始仓库不通过）。最终集的实现细节不用于调提示词。
- 大任务最终集（2026-11-15 定，**已被第 3.4 节取代**：这些题 `dsh` 都在 25 分钟内做完）：LoopsBench 2 道、DeepSWE 2 道；不设"大但不该拆"的任务（系统有任务间通信，拆开后可以等待协调）。单个 Agent 至少运行 25 分钟。DeepSeek 在这些集上的每题用时没有公开数字，按规模估计选题（开发单元数、参考解的大小、公开的 token 量），再用 `dsh` 的实际运行检验（第 3.3 节）。
- 小任务最终集：Terminal-Bench 2.0 中 phase 1 没用过的题 6 道（中等或较难、类别各不相同）、SWE-bench Pro 4 道（仓库不在 phase 1 用过的仓库中，尽量覆盖 Go、Python、TypeScript、JavaScript），不放合成的并行题（由本项目设计，对照 harness 天然吃亏）。用固定种子抽样，再按相似度规则剔除。

### 3.2 运行规则

- **最终集最多运行两次**（例如一次在优化完成后，一次在发布前），不得反复尝试，不用于调参。
- **为了经费，所有实验不在同样条件下重复，不做重复实验**：每个对照每题跑一次，尽可能减少开销。因此单题结果有波动，结论按任务集合计来读，并在验收证据中写明是单次运行。
- **不设阈值**：发布指标是两组最终集的通过数、按价格表折算的费用（"费用口径"见 [experiments](experiments.md)）与用时，以及大任务上的过程指标（是否进入 Mission、派了什么、通信是否起作用、有没有乱拆）。
- 对照（每题一次）：本项目（参加的模式在优化完成时确定，至少含 general 与单人）、`dsh`（中性提示；委派优先提示不跑，见第 3.3 节）。小任务最终集与大任务最终集都跑这组对照。
- 评测时授权由程序代答；至少有一轮开发集按真实授权策略与沙盒运行，记录拦截与询问。

### 3.3 封存与 `dsh` 对照（2026-11-15 定）

1. 先按第 3.1 节的规则选好两组最终集，记下题目清单、抽样种子与每题内容的哈希，**封存**（`scripts/taskset/phase3.json`）。封存之后只看合计数字，不看题目细节，不据此改动任何东西。
2. 封存后由 `dsh`（中性提示）把最终集的每题跑一次。它同时是计时（检验大任务"单个 Agent 至少 20 分钟"）与最终集的 `dsh` 对照，之后不再重跑。`dsh` 委派优先提示一组不跑。
3. 大任务中 `dsh` 不到 20 分钟就结束的，按封存时写下的候选顺序换成下一道，替补题同样由 `dsh` 跑一次；原题的记录保留并在证据中写明。不按 `dsh` 的成败或用时之外的结果挑题。
4. 运行条件冻结：同一模型（`deepseek-flash`）、同一 `dsh` 版本、同一容器与判分；单题上限两边相同（大任务 2.5 小时，小任务沿用题目的设置）；费用用同一张价格表折算。两边不在同一时间运行，用时含时段差异，证据中写明各自的运行日期。
5. 本项目在优化完成后才跑最终集（第一次），至多两次。
6. 运行方式（`scripts/taskset/phase3-dsh.sh`）：每题开跑前写下标记，有标记的题不再运行，崩溃也不自动重跑，只报告。小任务用 `agentrun.mjs`；LoopsBench 用官方 harness（`microsoft/loopsbench` f44331c，题包 c47e13a）加 `lb_dsh_agent.py`，DeepSWE 用 Pier 加 `pier_dsh_agent.py`，判分都是官方的。两个适配器把 Node 与 `dsh` 拷进题目容器，在其中运行 `dsh --profile headless`；模型请求都经 `usage-proxy.mjs` 计 token，与小任务同一口径（LoopsBench 经 Docker 网关在运行期的白名单内访问，Pier 经它的出网代理访问 `host.docker.internal` 的 80 端口）。适配器先在不属于任何一组的题上做过 5 分钟的冒烟检查。

### 3.4 设计题（2026-11-15，Cary 定的原则）

1. **用 DeepSeek 跑过的题都保留**，放进开发集或最终集，不丢弃，以免浪费 token。
2. 大任务改为本项目设计：最终集 3 道、开发集 3 道，按大学课程设计或毕业设计的角度选题；两组各有一道非编程的大任务（严格注明引用与参考文献的综述论文）。至少这 6 道设计题由 `dsh` 单独运行超过 20 分钟。
3. 当天把开发集与最终集的题都定下，并都用 DeepSeek 跑过一次。

**做法**：每道题是 Harbor 格式（`scripts/taskset/designed/<名>/`：`instruction.md` 规格、`environment/`、`tests/` 隐藏测试、`solution/` oracle），用 `agentrun.mjs` 运行，`dsh` 与本项目同一判分。判分按隐藏测试的通过比例给分。编程题的期望输出尽量取自真实的参考实现（`lua5.4`、`jq`、`gawk --posix`、GNU 工具、`sqlite3`、`re`、`cmark`、`git`），在任务镜像里事先生成；oracle 是调用参考实现的包装，按设计只不通过"禁止外部程序"一项，空实现为 0 分。论文题按结构检查与参考文献核对（DOI 经 Crossref、arXiv 编号经 arXiv 接口，题目、第一作者、年份都要对上）各占一半。

**离线**：`dsh` 在 mdhtml 上移植了现成的 commonmark.py（记录里写明"Our port from commonmark.py"），静态检查查不出。此后编程题在 `task.toml` 写 `allow_internet = false`，`agentrun.mjs` 把容器放进 internal 网络 `benchint`，只能访问记录代理（以及经它的模型接口）。mas 走代理的接法还没做，离线题暂不能跑 mas（RP3-EV 的待办）。
