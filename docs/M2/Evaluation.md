# MultiAgentOS 评测体系

> 状态：已实现（phase 0）。代码在 `apps/control-plane/test/eval/`，命令 `pnpm run eval`。
> 它回答"模型、提示词、模板、工具表现得好不好"；"系统在任何模型行为下是否守住底线"由冻结的系统测试回答（[M2FrozenTests](M2FrozenTests.md)），两者分开。

## 1. 目的与范围

M2 之后的工作大多是调提示词、加工具、设计工作流。每次改动都要问：做对的比例变了吗？花了更多 token 吗？工具用得更多还是更少？
如果每种测试集都自带一套统计，这些问题就没法跨版本、跨模式回答。评测体系把"怎么驱动、怎么判分"留给任务，把"怎么测量、怎么记录、怎么比较"统一起来：

- 任何模式（Turn-chat，以及以后的预置工作流）的任何任务，都得到同一组度量；
- 记录格式相同，两份记录可以直接比较；
- 回归的判定规则对所有任务相同。

不在本体系内：系统必须守住的底线（授权、沙盒、回退、恢复、凭据）。那些是通过式测试，用假模型，包括被攻陷的假模型，每次提交都跑，见 M2FrozenTests。

## 2. 评测角度

每次运行总是测量耗时、token、费用、请求数与各工具的使用（第 4 节）。判分检查按角度分类，任务声明自己判哪几个：

| 角度 | 问什么 | 例子 |
|---|---|---|
| `OUTCOME` 结果 | 任务做对了吗 | 测试通过、文件内容正确、回复里有要求的内容 |
| `BEHAVIOR` 行为 | 过程对吗 | 先读后写、该问的问了、适合派生时派生了、没有多余的调用 |
| `SAFETY` 安全 | 被诱导时有没有产生副作用 | 注入后没有越界写入、没有执行命令、凭据没有出现 |
| `CONTEXT` 上下文 | 压缩之后还记得吗 | 早先告知的事实在压缩后的请求里仍然存在 |

第五个角度是成本与效率：它不由任务判分，而是对度量设回归门槛（第 5 节）。

版本比较与稳定性（同一任务重复 N 次）是用法，不是角度：同一任务跑 N 次得到通过率，两份记录之间做差异比较。

真实模型下的 `SAFETY` 是统计量：它观察模型被注入后是否上当，用来看提示词改动有没有让模型更脆弱，不是发布门槛。发布门槛是冻结测试里被攻陷假模型的用例。

## 3. 任务与运行

一个任务（`TaskSpec`，`test/eval/spec.ts`）包含：

| 字段 | 内容 |
|---|---|
| `id`、`mode`、`tags`、`description` | 稳定的编号（不同版本的记录靠它对应）；`mode` 是 `chat`（交互控制台）或 `mission`（`mas run` 一个模板，没有对话，步骤为 `run`）；标签用于选取与汇总 |
| `fixture` | 把任务的文件放进一个空仓库 |
| `steps` | 用户做什么：`say`（发消息并等回复）、`submit`（发一行，如 `/compact`，立即返回）、`awaitInput`、`waitFor` |
| `answer` | 授权询问怎么回答，缺省全部允许 |
| `setup` | 本任务对配置与预设的改动 |
| `scripted` | 有则任务是确定性的，用脚本化的 provider 离线运行；没有则用真实模型 |
| `judge` | 只看产品留下的东西：最终文件、测试、对话记录、会话日志、provider 收到的请求；不用另一个模型当裁判 |

"怎么驱动"与"怎么判分"是分开的：驱动器（目前是 Turn-chat 的 `drive`）读 `steps`，判分只读 `Observation`。预置工作流到来时，加一个驱动器与它的步骤，判分与度量不变。

`runTask`（`runner.ts`）运行一个任务一次：建临时目录与仓库、启动完整的产品（真实的组合根、Kernel、Workflow、控制台、ExecutorSet，只替换 provider 的 HTTP）、驱动、读会话日志、判分、清理。步骤没有完成（超时、请求超预算）时记录里有 `error`，已有的东西仍然被判分。

## 4. 度量：全部来自会话日志

`metricsOf`（`metrics.ts`）只读会话日志（以及一个价目表），任务不埋点：

- 耗时（日志首尾）、Turn 数、模型请求数与失败的请求数；
- token：输入、输出、缓存命中；压缩的摘要请求另算（`CONTEXT_COMPACTED.usage`）；缓存命中率；
- 费用：按模型定义的价目表逐次计价（`modelCallCost`，含高峰时段），摘要请求一并计入；模型没有价目表时为 `null`；
- 各工具被请求的次数，以及每次调用的结局（`<工具>:OK`、`<工具>:REJECTED(<原因码>)`）；
- AgentRun 按 Agent 的数量；同一时刻在途的 Unit 数的最大值（并行度）；
- 压缩次数与修剪数、询问数（授权询问与局部询问）、收尾数。

系统本来就把这些都写进了日志，所以新增任何模式或任务集都不需要统计代码。需要新的度量时，先看日志里有没有，没有就先让系统记下来，再在 `metricsOf` 里加一项。

## 5. 记录与比较

每次运行追加一行 `RunRecord`（`schema: 1`）：任务编号、模式、标签、第几次、时间、**版本**（提交，以及全部定义文件——Agent、Prompt、Tool、Model——的摘要）、模型、provider（`real` 或 `scripted`）、是否通过、每个检查（名称、角度、结果、失败原因）、度量、总耗时、错误。

`eval report <文件>` 按任务汇总：通过数、平均耗时、请求数、token、费用、缓存命中、并行度、每次运行的工具使用。

`eval compare <基线> <新> [--fail-on-regression]` 比较两份记录，规则对所有任务相同（`report.ts` 的 `DEFAULT_RULES`）：

| 规则 | 缺省 |
|---|---|
| 通过率下降超过 | 0.2（绝对值），且两边各至少 3 次运行；运行次数不足时只提示，不判 |
| 平均费用增长超过 | 25% |
| 平均耗时增长超过 | 50% |
| 平均模型请求数增长超过 | 50% |
| 缓存命中率下降超过 | 10 个百分点 |

出现的新任务、消失的任务只提示。结果是几十次运行的事实，不是统计检验；比较给出的是"值得看一眼"的差异，门槛可以按任务集的规模调整。

## 6. 自检任务

`tasks/selfcheck.ts` 有几个脚本化的任务，各角度各一到两个：问候、读后改写、被攻陷的模型越界写与读密钥、压缩后的事实。它们不衡量产品，也不是发布标准，作用是证明评测器本身有效。`eval.test.ts` 检查：

- 自检任务离线运行并通过；
- 判分失败、步骤超时、判分函数抛错都被记成失败，并保留原因；
- 日志里的度量（含价目表计价与并行度）算对；
- 对比规则能找出通过率、费用、耗时、请求数、缓存命中的退化，对运行次数不足、新增与消失的任务给出提示；
- 需要真实模型而没有密钥的任务被拒绝。

## 7. 增加任务集

一个任务集是 `test/eval/tasks/` 下导出 `TaskSpec[]` 的文件，在 `tasks/index.ts` 的 `ALL_TASKS` 里登记，别的都不用改。写任务时：

- 编号稳定，带模式与主题标签；
- `judge` 只做确定性检查，每个检查写明角度；
- 需要的 fixture 在 `fixture` 里生成，不依赖外部状态；
- 先用脚本化 provider 证明判分能判出通过与失败，再换真实模型运行。

Turn-chat 的任务集在 phase 1 开头建立，并在改动任何提示词之前录下基线 1，优化达标后录基线 2；预置工作流的任务集在 phase 2 同样处理（M2ReleasePlan 第 3a 节）。

## 7a. 编排任务集与对照实验

- `tasks/orchestration.ts`、`tasks/orchestration-hard.ts`（`tag:orchestration`，难任务另有 `tag:hard`）：后台命令、超时转后台、读取与停止作业、子任务里的后台命令、并行子任务与休眠汇合、兄弟消息、停止与中断子任务，以及 `mission` 模式的大任务（小项目、键值存储、技术报告、分章综述、跨模块修复）。判分只看文件、模型没见过的验收命令（隐藏测试）与会话日志。
- 设置 `EVAL_ARCHIVE=<目录>` 时，每次运行的 Session（含日志）与结束时的仓库留档，供复查失败。
- 与 DeepSeek Harness 的大任务对照实验（M2Design 第 13 节 X 组）的设计见 [Phase2Plan](Phase2Plan.md) 第 4 节；`dsh` 与关闭派生的本项目作为对照组的驱动待加入（RP2-EV-2）。

## 8. 命令

```bash
# 离线的自检任务
pnpm run eval run --tasks tag:selfcheck --out /tmp/selfcheck.jsonl

# 真实模型的任务：需要 --yes 与请求预算，密钥取自 DEEPSEEK_API_KEY 或 MAO_ENV_FILE 指向的文件
pnpm run eval run --tasks tag:chat --runs 5 --out records/chat.jsonl --yes --budget 300

pnpm run eval report records/chat.jsonl
pnpm run eval compare records/before.jsonl records/after.jsonl --fail-on-regression
```

已经记录过的运行（同一任务、同一次、同一版本）会被跳过，所以中断后可以重新运行。运行是顺序的：真实模型的评测占内存与请求额度，不并行。

**看着它跑**（2026-11-14）：`run` 在进程里驱动产品，没有界面。mission 任务也可以由人用 `mas run` 带界面运行，事后按同样的评分记下：

```bash
# 准备与评测时相同的仓库和一个只给这次运行用的数据目录，并打印运行与评分的命令
pnpm run eval prepare --tasks study.healthhub --repo ~/hh --data ~/hh-data
# 按打印出的命令运行：MULTIAGENTOS_CONFIG 指向数据目录，结束后退出码写进 ~/hh-data.exit
# 评分：同一个评分函数（在仓库的副本上做，隐藏测试不留在仓库里），指标取自会话日志，追加与 run 相同的记录
EVAL_ARCHIVE=~/eval-records/study3-archive pnpm run eval judge --tasks study.healthhub --repo ~/hh --data ~/hh-data --exit "$(cat ~/hh-data.exit)" --out ~/eval-records/study3.jsonl
```

两种方式的差别只有两处：授权询问由人回答，而不是一律同意；记录里 `provider` 为 `real`，请求预算不由评测控制（`mas` 自己的额度照常）。`judge` 要求数据目录里只有这一次运行的会话。

## 9. 规矩

- 真实模型评测带 `--yes` 与请求预算，密钥不写入记录。
- 记录是追加的；评测发现问题，当场修复并重跑，修复前后的记录都保留。
- 结果写明运行次数与局限，不写成统计结论。
- 不为单个任务另写运行器；缺什么能力，补到这里。
