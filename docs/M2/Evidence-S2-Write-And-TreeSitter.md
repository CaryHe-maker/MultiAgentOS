# 阶段 2 实验记录：写入能力与 tree-sitter 的必要性

> 2026-11-04，`feature/phase2/main`，Ubuntu 24.04（WSL），模型 `deepseek-flash@v0.1.0`。
> 费用按定义文件的非高峰价估算，合计约 $1.16（写入约 $0.86，A/B 约 $0.30），高峰时段价格翻倍，这里没有按实际时段折算。
> 脚本：`apps/control-plane/test/acceptance/write-eval/`、`experiments/tree-sitter/`。原始记录在 `.multiagentos/`，不入库。

## 1. 结论

| 问题 | 结论 |
|---|---|
| 写入工具与安全边界 | 合格：36 个任务 108 次运行全部通过，没有写到受保护路径或仓库外 |
| 在真实大型仓库上完成任务 | **现在不合格**：12 次只过 4 次。主因是上下文上限被高估约 3.3 倍，Agent 被提前叫停 |
| 要不要为检索引入 tree-sitter | **现在不需要**：静态准确率确实更高，但 Agent 的成功率和用量都没有可测的提升 |

## 2. 写入实验

### 2.1 方法

- 每个任务是一个仓库和用户的话。判定靠**模型看不到的测试**，在最后一轮结束后运行，再加对文件本身的检查（换行符、BOM、改动范围）。
- 判定的有效性：`--baseline` 把判定放在未修改的仓库上跑，全部不通过，没有空题。
- 类别：修 bug、新功能、重构、编辑机制（同文件多处、长文件翻页、CRLF、BOM、中文与 emoji、不唯一的样板代码）、指令与注入、受保护路径、用户拒绝、多轮对话、回退、外部修改、能力缺口、写测试（要能抓住变异）、难题（从规格写解释器、跨 30 个文件改接口、原因与症状不在一处、缓存失效、五轮评审对话）。
- 语言：TypeScript、Python 可以运行验证；Go 任务只做文本校验（环境没有 Go）。

### 2.3 真实仓库（MultiAgentOS 自身，4 个跨包任务各 3 次，`tsc -b` 与 vitest 判定）

| | 现状上限（96,000） | 放宽 4 倍（384,000，仅实验） |
|---|---|---|
| 通过 | **4/12** | **9/12** |
| 一个字都没写就结束 | 8/12 | 0/12 |
| 因 `CONTEXT_LIMIT` 收尾 | 9/12 | 0/12 |
| 输入 token/次 | 192,159 | 825,752 |
| 缓存命中 | 74.4% | 91.0% |
| 费用/次 | $0.0106 | $0.0213 |

- **根因**：`estimateTextTokens` 把 UTF-8 字节数当作 token 数。实测估算值是真实值的 **3.3 倍**（2.63–3.70）。上限 96,000 实际只有约 25,000 个真实 token，而模型窗口是 1,000,000。Agent 读完相关文件，正准备动手就被强制收尾。
- 放宽后仍失败的 3 次，隐藏测试全部通过，失败的只有模型自己新加的测试（它不能运行代码，写错了也不知道，阶段 3 才有命令）。
- 放宽后有 2 次因 `BUDGET_WRAP_UP` 收尾，其中 1 次通过。说明 Turn 额度同样受估算偏高影响。

## 3. tree-sitter 实验

### 3.1 静态：真实代码上的声明查找

标准答案来自编译器（TypeScript Compiler API、Python `ast`），与被测的三方都无关。每个语料抽样约 400 个名字。局部变量单独统计，不算对也不算错。

| 语料 | 正则（现状） | 改进版正则 | tree-sitter |
|---|---|---|---|
| OpenCode（TS，441 文件） | P 98.4 / R 86.5 | P 98.3 / R 88.8 | P 100 / R 99.4 |
| DSH（TS，226） | P 95.1 / R 85.4 | P 84.9 / R 98.3 | P 100 / R 98.9 |
| MultiAgentOS（TS，88） | P 86.7 / R 81.2 | P 79.8 / R 97.6 | P 99.7 / R 100 |
| LangGraph（Py，480） | P 99.2 / R 100 | P 98.5 / R 100 | P 100 / R 100 |
| DeerFlow（Py，699） | P 99.6 / R 100 | P 97.4 / R 100 | P 100 / R 100 |
| MAF（Py，698） | P 99.2 / R 100 | P 98.6 / R 100 | P 100 / R 100 |

- 正则在 TS 上的漏报 **全部是类方法**，误报主要是多行 `import { type X }`。
- 正则还会命中局部变量：TS 语料每 400 多个名字有 379–789 次，tree-sitter 按查询规则不会。
- 改进版正则换来召回，却丢了精确率：单看一行，分不清 `foo(` 是调用还是声明。正则这条路到头了。
- 性能不是问题：解析每个文件 1.4–3.5 毫秒。TypeScript 语法文件 2.3MB，运行时 0.2MB。
- 文件大纲只有全文的 6–9%，大文件 5–9%。

### 3.2 真实模型 A/B

30 个任务由 AST 随机抽样，避免人为挑选。三组各 60 次对话，共 180 次。

| 组 | 成功 | 请求/次 | 输入 token/次 | 费用/次 |
|---|---|---|---|---|
| 现状正则 | 95% | 4.4 | 24,401 | $0.00171 |
| tree-sitter 版 SYMBOL | 95% | 4.3 | 23,458 | $0.00169 |
| tree-sitter 加文件大纲 | 98% | 4.5 | 23,458 | $0.00160 |

分任务看，差异只出现在部分类别，而且样本很小：

- 类方法定位（n=20）：三组都是 100%，tree-sitter 输入少 28%（16,174 → 11,669）。正则漏掉方法时，模型直接改用文本搜索找到了。
- 大文件 API（n=8）：大纲组输入少 38%，但模型几乎不用大纲：60 次对话里全部 `OUTLINE` 只有个位数。
- 找全所有声明（n=8）：75% / 62% / 88%，方向不一致，样本太小，看不出趋势。

**模型的实际用法才是关键**：`SYMBOL` 只占写入任务搜索的 9%（165 次中 15 次），真实仓库任务只占 3–6%。A/B 任务直接问“在哪声明”，占比才高（TEXT 仍是 SYMBOL 的 3 倍）。tree-sitter 改进的恰恰是这条很少走的路径。

### 3.3 判断

不引入。理由是 Agent 层面没有可测收益，而每种语言都要长期维护语法文件和查询规则。

重新考虑的条件（满足其一）：

1. 上下文上限修好后，真实仓库任务的失败或大量 token 明确来自找不到符号；
2. 要做文件大纲，并且能让模型真正用起来；
3. 需要跨语言的精确重命名。此时更该看 LSP，tree-sitter 不懂类型和跨文件引用。

阶段 3 引入 `web-tree-sitter` 解析 bash 后，运行时已经在依赖里，届时只增加语法文件和查询规则。

## 4. 这次实验的局限

- 只用了一个模型，真实仓库只有 4 个任务、一个仓库。
- 放宽 4 倍只是用来量化影响的实验配置，不是修复方案。
- A/B 第一轮有 3 次 `OUTLINE` 泄漏到对照组（第二轮已隔离），每组也只有 60 次。差异在 1–3 个百分点内时不能说明谁更好。
- A/B 任务是只读的定位题，没有测 tree-sitter 对写入任务成败的影响。
- 第一批真实仓库结果（`real`）不计入：隐藏测试有语法错误，题目也被模型读到了。上表是修正后的结果。
- 实验过程中 WSL 因内存不足崩溃多次，靠断点续跑补齐；崩溃前后的数据都按任务和轮次去重。
