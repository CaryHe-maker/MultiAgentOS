# Phase 2：多 Agent 并行任务的执行底座

> 2026-11-12，Cary 决定。本文是 phase 2 的总纲：最终目标、什么写死与什么只做指导、如何用真实实验证明架构价值。
> 它取代 [M2ReleasePlan](M2ReleasePlan.md) 第 5.3 节原来"预置编排模式"的目标（M2Design v1.36）。机制的设计见 [Orchestration](Orchestration.md)，评测的做法见 [Evaluation](Evaluation.md)。

## 1. 目标

**phase 2 交付一个可靠的多 Agent 并行执行底座，加一组可选的编排范式。**

- 缺省入口是**自主分解**：`mas run "<目标>"`（内置模板 `mission`）。负责人（main）自己决定拆不拆、怎么拆、拆成几层，系统不规定流程的形状。
- 原先设计的固定工作流（`research`、`paper`、`task` 等）降为**范式**：写给负责人参考的编排方法，可以选用、组合，也可以都不用。
- 需要可重复、可审计流程的场景，保留**严格模式**：用模板引擎按固定图执行（`mas run <模板> "<目标>"`），必须由用户显式选择。
- **验收的核心**：在 M2 提交时，用真实模型的对照实验证明，至少在一部分大任务上，本项目相比 DeepSeek Harness（`dsh`）有**原生优势**（第 4 节）。

为什么这样定：试跑表明，`mission` 模板本来就只有一个负责人节点，任务的拆法全由模型决定（kvstore 拆成引擎、命令行、测试、文档四个 worker，综述按章拆分，修三处 bug 时一个人完成）。真实任务的最佳拆法各不相同，固定的图不是太粗就是太僵；项目与 `dsh` 的区别在底座，不在流程。

## 2. 写死的与只做指导的

| 写死（系统保证，任何编排都不能绕过） | 只做指导（负责人自己决定） |
|---|---|
| 权限：能力上限、授权两步判定、沙盒 | 拆不拆、拆成几个、几层 |
| 写入范围与借出：同一路径同一时刻只有一个任务能写（[Orchestration](Orchestration.md) D17） | 用哪种范式、范式怎样组合 |
| 额度：按任务委派与记账，用完收尾 | 子任务的角色与目标怎么写 |
| 深度上限（缺省三层）、连续唤醒上限、停滞检测 | 什么时候休眠、等什么 |
| 子任务没结束，任务不能交付（D4） | 是否用后台命令、何时读输出 |
| 日志可重建、checkpoint 与回退、停机规则 | 是否给兄弟或子任务发消息、何时停止或中断 |

**范式手册**（写入 main 与 lead 的提示词，以及 `mission` 模板的目标说明，不写成图）：

| 范式 | 适用 | 要点 |
|---|---|---|
| 扇出与汇合 | 部件相对独立、接口清楚 | 写入范围不相交；休眠等全部结束；最后集成验证 |
| 多层负责人 | 一个部件本身仍很大 | 部件交给 `lead`，它再往下分；每层都验收下一层 |
| 先探路再施工 | 不清楚仓库或需求 | 先派 explorer 调研，再按结论派 worker |
| 接口先行 | 并行部件之间要对接 | 定接口的一方先发 `send_message`，另一方休眠等消息 |
| 分节撰写与统一审校 | 长文、报告 | 按章节借出写入范围；最后由负责人统一术语、引用与目录 |
| 长时间步骤放后台 | 慢构建、慢测试、批量评测 | `runInBackground` 或超时转后台；休眠等作业，不轮询 |
| 纠偏 | 子任务走错方向 | `send_message` 的 `interrupt` 改方向，或 `stop_subagents` 停掉重派 |
| 单人完成 | 小任务、强耦合的逻辑 | 不拆分：拆分的开销大于收益 |

## 3. 与 DeepSeek Super-agent 的比较

DeepSeek Harness 团队在 2026-10-31 发布了 Super-agent 的设计文章与开源原型 `dsh-superagent-prototype`（MIT，研究原型，不是正式产品）。下面依据原型仓库的 README 与 docs 000–003、007（原文），以及两篇转述文章的评测数字（原文文章未能读到）。

**相似之处**（方向一致，说明这条路是对的）：

| 方面 | Super-agent | 本项目 |
|---|---|---|
| 两层结构 | 常驻的 Main Session 只分派与汇报，Executor Session 干活 | 负责人（main）派生子任务，任务树记录谁负责什么 |
| 业务身份与会话分离 | Ticket 独立于执行它的会话，换会话不丢授权与内容 | 任务（MissionTree 节点）独立于 AgentRun，休眠前后是不同的 AgentRun |
| 单一写者的持久状态 | Engine 是 SQLite 状态的唯一写者，每条命令一个事务 | 会话日志只追加，是唯一事实来源，上下文由日志投影 |
| 权限由宿主执行 | Mandate 由宿主执行，消息与评论不能改变权限 | 能力上限由 Kernel 执行，消息是材料、不是指令也不带权限 |
| 后台命令 | 前台命令 5 秒后转后台，作业结束唤醒执行者 | 超时转后台、`runInBackground`，作业结束按 `sleep` 的 `jobs` 唤醒 |
| 等待事件再继续 | 执行者空闲等 Trigger，订阅的线程有新事件时恢复 | 任务休眠，按子任务、消息、作业、定时唤醒 |
| 少打扰人 | 一次只问一个具体问题；`observe` 缺省模式 | `ask_user`、分级授权询问 |

**关键区别**（也是本项目要证明的优势所在）：

| 方面 | Super-agent | 本项目 |
|---|---|---|
| 优化的对象 | **很多个独立请求**的吞吐：一个仓库里持续到来的需求，每个请求一个 Ticket、一个执行会话 | **一个大任务**的分解与协调：一个目标拆成任务树，各部分并行，最后汇成一个交付 |
| 任务分解 | Router **不分解单个任务**；把它列为团队负责人的角色、尚未解决 | 负责人分解，`lead` 可再分，缺省三层 |
| 执行者之间的通信 | 没有；文章把执行者直接通信列为待解决问题 | 父子、兄弟之间的消息，向下的中断，任务树可见 |
| 并行写入的冲突 | 没有文件级控制，订阅不是锁，靠 PR 与 git 分支 | Kernel 的写入占用与按路径借出，越界写入被拒，命令把借出的路径挂为只读 |
| 沙盒 | 没有：执行者以操作者的系统用户运行命令，目录与包装"不是安全边界" | bubblewrap 沙盒、网络与密钥隔离、分级授权 |
| 额度 | 按执行者槽位限制并发 | 按任务委派与记账，用完收尾 |
| 回退 | 未提到 | checkpoint 与回退（phase 2 实现） |
| 形态 | 常驻服务，由 GitHub、飞书事件驱动，主动接活 | 由用户发起的会话或一次运行，不主动接活 |
| 评测 | 合成的调度实验：约 300 条消息、20 个工作请求，编码换成只耗时的工具；p50 12.4 分钟、p95 15.7 分钟，对比单会话加 Subagent 工具的 20.4 分钟、29.5 分钟；作者称为初步结果 | 真实任务、隐藏测试判分（第 4 节） |

**结论**：两者在底座的理念上高度相似（会话之外的持久身份、单一写者的状态、宿主执行的权限、后台作业与事件唤醒），但解决的是两个不同的问题。Super-agent 解决"人同时盯不过来很多个 agent"，把很多个独立请求排队、分派、跟踪；本项目解决"一个任务大到一个 agent 做不好"，把一个任务拆开、并行、协调、合并。Super-agent 明确留下的空白——单个任务的分解、执行者之间的通信、并行写入的冲突控制、沙盒——正是本项目已经实现的部分。将来两者可以叠加：Super-agent 式的 Router 接活，每个 Ticket 交给本项目的一棵任务树去完成。

## 4. 证明架构价值：对照实验

### 4.1 要回答的问题

在**单个大任务**上，本项目的原生编排是否比 `dsh` 做得更好：通过率更高，或通过率不低而更快，且成本可以接受。并且回答优势来自哪里（编排，还是 harness 的其他差异）。

### 4.2 对照组

| 组 | 运行方式 | 作用 |
|---|---|---|
| A：本项目，自主编排 | `mas run "<目标>"`（`mission`） | 被检验的对象 |
| B1：`dsh`，中性提示 | `dsh --profile headless "<目标>"`，开着它的 Subagent 工具 | 主要对照（与 Super-agent 文章的单会话基线同构） |
| B2：`dsh`，委派优先的提示 | 同上，目标前加一段"能拆就拆、并行委派"的说明 | 排除"只是提示词没让它委派"的解释 |
| C：本项目，单人 | `mas run`，关闭派生（main 没有 `agent.spawn`） | 消融：同一 harness 下，编排本身带来多少 |

所有组：同一模型（`deepseek-flash`）、同一任务文字、同一时限与请求预算；token 在模型接口处统一记录（`dsh` 走 `usage-proxy.mjs`）；都在题的容器或同样的临时仓库里运行，结束后放入**模型没见过的隐藏测试**判分。`dsh` 固定版本与提交。

### 4.3 任务集

**大任务**（优势预期所在），至少 8 个，覆盖第 2 节的范式：

| 类别 | 例子 | 隐藏判分 |
|---|---|---|
| 多部件项目 | 键值存储（引擎、命令行、持久化、压缩）；带后端、客户端与迁移的小服务 | 隐藏单元测试与集成测试 |
| 跨模块修复与迁移 | 十几个模块各有缺陷；把一个接口在几十个文件里换成新接口 | 隐藏测试、无关文件未改 |
| 带慢测试的项目 | 全量测试要跑一两分钟的仓库上实现功能 | 隐藏测试；记录墙钟 |
| 并行调研与写作 | 分章综述、多来源的技术报告 | 结构、篇幅、引用一致性、事实核对 |
| 有接口约定的并行开发 | 服务端与客户端由不同部分实现，字段由一方决定 | 集成测试 |

来源：自建（`apps/control-plane/test/eval/tasks/orchestration*.ts`，由 fixture 生成，换种子出新题），加上公开测试集里规模大的题（Terminal-Bench 2.0、SWE-bench Pro 中跨多文件的题，经 `scripts/taskset/agentrun.mjs` 运行）。分开发集与封存的最终集，结论只以最终集为准（与 [Phase1TaskSet](Phase1TaskSet.md) 第 3 节同一办法）。

**小任务**（对照）：几个单文件修复。预期本项目没有优势，甚至更慢更贵；照实记录，用来说明适用范围。

### 4.4 度量

- **结果**：隐藏测试通过率。
- **时间**：墙钟的 p50、p95。
- **成本**：输入、输出、缓存命中 token，费用。
- **过程**（只记录、不判通过）：任务数、任务树深度、休眠与唤醒次数、作业与消息数、停滞唤醒、写入被拒次数、人工介入次数。
- 每个任务每组至少 5 次。结果写成次数与比例，并写明局限，不写成统计结论。

### 4.5 判定（待负责人确认，第 6 节）

"原生优势成立"指：在最终集的大任务中，**至少 3 个任务**同时满足：

1. A 的通过率比 B1、B2 中较好的一组高至少 20 个百分点；或者通过率不低于它，且墙钟 p50 少至少 30%；
2. A 的费用不超过该组的 2 倍；
3. A 比 C 好（通过率更高或更快），证明优势来自编排而不只是 harness 的其他差异。

做不到时照实写进验收证据，并说明在哪类任务上做不到、原因是什么。

## 5a. 来自管理学的设计依据（候选，按评测证据决定是否实现）

项目的定位是"承包公司"：root 接下整个任务，像公司把任务分给部门与员工一样分配、分批完成，而不是一个主 Agent 加临时的子 Agent。管理学与互联网公司的实践给出下面这些候选（来源与论证见 2026-11-12 的调研记录）：

| 优先 | 候选 | 依据 |
|---|---|---|
| 1 | 派生合同加"意图"（为什么做、上级要什么、可接受的风险）；root 先写交付物说明（并入计划书） | 任务式指挥的指挥官意图；Amazon 的 Working Backwards |
| 2 | 常设部门：后续工作交给原来的任务（休眠或已结束的任务带着记忆接手），而不是每次新派 | 部门与员工是持续存在的；返工、维护、二期工程 |
| 3 | 共享事实放在负责方的文件里，改后通知（已并入 D23） | 康威定律与"接口先行"；交互记忆（谁知道什么） |
| 4 | 结构化的阻塞上报与里程碑汇报；验收靠验证（父任务亲自跑验收），关键改动"做的人与审的人分开" | 例外管理；委托代理理论（监督的边际收益递减） |
| 5 | 每个经理同时进行的子任务数上限；分批派生、分批验收，批次边界对齐 checkpoint | Kanban 与 Little 定律；IPD 的阶段评审 |
| 6 | 运行结束自动复盘（原计划、实际、差别、下次怎么做），存为跨 Session 的经验 | 美军的事后复盘；学习型组织 |
| 7 | 范式补充：赛马（不确定的难点由两组并行，胜者留下）、额度在部门之间调拨、平台与专家部门；管理幅度的软上限（缺省 5–8） | 腾讯赛马；阿里中台的教训（共享平台要薄）；Team Topologies；管理幅度研究 |

结构的松紧随模型能力调整：研究显示能力较弱的模型在明确的结构下表现更好，较强的模型自组织更好。范式手册应可配置强度。

## 7. 进展

| 日期 | 内容 |
|---|---|
| 2026-11-13 | **修复后重跑 mission 任务**（各 3 次，636 个请求）：ledger 3/3、report 3/3、bugfix 3/3、kvstore 3/3、paper 2/3。paper 的第 3 次在评测的请求上限用完时被截断（模型调用报 `PROVIDER_ERROR`，运行按 `BUDGET` 结束），不计为产品失败；同时发现并修正：根任务最后一段失败时任务被记为成功。作废的 3 次（ledger、kvstore）在修复后全部通过。正式预算 1500 已用 1487 |
| 2026-11-12 | **正式运行**（13 个任务各 3 次，851 个请求，约 1.11 美元）：36/39 通过。失败与发现：① `subagents.stop` 一次：被停止的 worker 正以 10 分钟的超时在前台运行 5 分钟的脚本，停止要等这一轮结束，main 第 9 秒已有答案却等了 5 分钟以上——证明停止必须取消在途工作（Orchestration 第 14 节第 7a 条）；② `mission.ledger` 一次：main 自己写的测试有一个没过就交付了（模型行为）；③ `mission.paper` 一次：审校漏掉 2 处"任务拆分"（模型行为）。**复查留档日志又发现一个严重缺陷**：15 次 mission 运行中有 3 次，某个子任务用定时器休眠时其余子任务都结束了，运行在没有可启动节点、没有活动 AgentRun 时直接收敛，root 没有被唤醒、没有交付，却记为成功（判分只看文件，没有发现）。已修复：还有任务在休眠时运行不按完成收敛；判分增加"main 交付了回复"；有离线用例。这 3 次的"通过"作废，需在修复后重跑 |
| 2026-11-12 | 编排任务集第一版（13 个任务，`tag:orchestration`）；试跑：8 个基础任务 8/8 通过（117 个请求，约 0.09 美元），5 个难任务 3/5（预算用完与任务写法问题，已修）。试跑发现并修复：mission 中 main 无法再调用模型时 `mas run` 仍以 0 退出。此前（后台命令的实现中）还修复了任务工具（`sleep` 等）没有进入给模型的工具列表。正式运行（每个任务 3 次）进行中 |
