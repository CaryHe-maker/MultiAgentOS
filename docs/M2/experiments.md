## E1 到 E4（2026-11-11）：适配器上线与第一批 10 题

**目的：** 让 `mas` 与 `dsh` 在同一批开发集题上跑起来，找出适配层与 `mas` 自己的问题。

**题（10）：** Terminal-Bench `fix-code-vulnerability`、`git-multibranch`、`multi-source-data-merger`、`openssl-selfsigned-cert`；SWE-bench Pro `NodeBB-da0211b1`、`tutanota-de49d486`；自建并行 `wide-write-s2-n10`、`wide-read-s2-n14`、`research-then-implement-s2-n14`、`conflict-trap-s2-n8`。

**途中发现并处理的问题（按发现顺序）：**

1. **`mas` 在容器里没有命令工具。** 日志里 `sandbox: none (commands cannot be run)`：容器里没有 bubblewrap，默认配置 `sandbox.unavailable = deny`，命令工具整个不提供。评测方改成 `ask-unisolated`（容器本身就是隔离）。
2. **以路径开头的消息被当成指令。** 指令 `/app/registry.py 里有一张表……` 以 `/` 开头，控制台把它当作没有的指令，什么都没发给模型，评测空等到 15 分钟超时（请求数 0）。**产品改动：** 以 `/某目录/` 开头的行是消息，不是指令（`console.ts`，单元测试已加）。
3. **没有 `git` 的镜像里 `mas` 变成只读。** `compose-system.ts` 在找不到 git 时把整个会话设为只读（撤销靠 git），于是 `openssl-selfsigned-cert` 与 `multi-source-data-merger` 里既不能写文件也不能运行命令，两题得 0 分。评测方在容器里装好 git（两边一样）。**这是真实的产品限制**：在没有 git 的机器上 `mas` 什么都改不了。是否改成"无 git 也能写、只是没有撤销"留作设计问题，见下面"待决"。
4. 评测适配器自己的小问题：两个任务 id 写错前缀（SWE-bench Pro 目录名带 `instance_`）、WSL 偶发连接超时使后台进程残留容器（已清理，之后按名字前缀 `ar-` 清理，不碰别的容器）。

**注意：** 样本很小（每题一次），这些数字只能当作"适配器已通、没有明显的量级差距"的证据，不能下结论。

## E5（2026-11-11）：开发集剩余的题，`mas` 与 `dsh` 各一遍

**结果：** `mas` 通过 18/25，`dsh` 23/25；Agent 时间合计 `mas` 6729 s（其中 4 次 900 s 超时共 3600 s）、`dsh` 3383 s；token（读入加输出）`mas` 1626 万、`dsh` 1429 万；请求数 `mas` 414、`dsh` 486。逐题的表在 `~/bench/results/results.jsonl`，用 `node scripts/taskset/summarize.mjs ~/bench/results/results.jsonl e5 --md` 重新生成。

**`mas` 的失败与原因：**

| 题 | 现象 | 原因 |

2. 主 Agent 提示词（`main-system`）加一条：文件工具只收相对路径；指令里是绝对路径时先用 `pwd` 找到根，路径在根之下就去掉前缀；外部读取工具只用于根之外的文件夹。

**注意：** 在 `mas` 慢的几题（`gcode-to-text`、`headless-terminal`、`chess-best-move`）上 `mas` 的 token 是 `dsh` 的 2 到 3 倍，请求数相近，说明单次请求读入的更多（工具结果更长或上下文更大），列为下一步要看的问题。

## E9 与 E10（2026-11-11）：剖析 `mas` 的请求构成，并收紧命令输出预览

**E9（剖析，`mas` 三道长任务，`high`，默认限制）：** 测驱动现在把每次请求的构成（各类内容的字符数，不含内容）写进 `request-profile.jsonl`。`chess-best-move` 第 22 次请求时：回放的历史思考 17.8 万字符、工具结果 7.8 万字符、系统提示 0.7 万字符、工具定义 1.6 万字符；单条命令输出最大 2.2 万字符（命令输出预览的默认上限是 50 KiB 与 2000 行）。`headless-terminal` 通过（236 s），`chess-best-move` 通过（344 s），`gcode-to-text` 超时失败（902 s；E5 里同一题通过，619 s，同一题两次差别很大）。

**`dsh` 的同一指标（探针 p11，`dsh`，`chess-best-move`，28 次请求）：** `dsh` 同样回放思考（第 27 次请求里 `thinking` 块共 4.1 万字符、工具结果 1.7 万字符），但量远小于 `mas`（`mas` 同题 22 次请求就是 17.8 万与 7.8 万）；系统提示 2.6 千字符（`mas` 6.9 千）、工具定义 1.9 万字符（`mas` 1.6 万）。`dsh` 的 `bash` 工具长输出只留尾部、完整输出存文件；系统提示很短，只有工具用法的几条规则（先看退出码、用 `read`/`glob`/`grep` 代替 `cat`/`find`、后台任务与子 Agent 的用法）。

**结论：** 两边都回放思考；`mas` 的差别在于每一步想得多得多（同一指令下每次请求的输出 `mas` 约 2000 token、`dsh` 约 600 token）。E8 中 `mas` 的 `low` 与 `dsh` 的 `high` 输出量接近，提示 DeepSeek 的 OpenAI 兼容接口（`reasoning_effort: high`）与 Anthropic 兼容接口（`output_config.effort: high`）对同一档强度的实际思考量可能不同；设置对等，实际并不对等，之后比较时要记着这一点。

**E10（`mas`，命令输出预览 12288 字节与 300 行，其余默认，`high`）：** 已有的 5 题全通过：`headless-terminal` 221 s，`chess-best-move` 289 s，`merge-diff-arc-agi-task` 71 s，`raman-fitting` 245 s（E5 失败）、`polyglot-c-py` 162 s；`gcode-to-text` 未完。单次差异里有噪声，E5、E9 与 E10 同题时间相差可达一倍，不能把差异直接归于预览上限；需要重复运行才能下结论。

### dsh 沙箱问题（2026-11-12 发现）

**起因：** 复查 final1 中 dsh 的两个失败，只看是不是环境不适配（不看 mas 的失败）。

- 启动 dsh 时只传了 `--profile headless`，没有选权限模式，默认 `workspace-write`：Landlock 沙箱只允许写工作目录（`/app`），写不了 `/git`、`/var/www`、`/usr/local/bin`、`/var/lib/xkb`、`/root` 等。dsh 自带 `danger-full-access`（审批 never），评测没有用。
- configure-git-webserver：题目要求 `/git/server` 与 8080 的网页服务；dsh 把整套东西建在 `/app` 里，自己测通，最后让用户用 root 运行安装脚本；验收访问 8080 得到 HTTP 000，失败。
- sqlite-with-gcov：SQLite 编译成功，但沙箱拦了 `/usr/local/bin/sqlite3` 的软链接，只放进 `/app/bin`，验收找不到 `sqlite3`，3 个测试全失败。
- 通过的题里也有被沙箱拦过的绕路：qutebrowser（Xvfb 要写 `/var/lib/xkb`）、navidrome（Go 缓存目录 `/root` 不可写）、sparql-university（apt 要写 `/var`）。开发集的 dsh 数据同样受影响。
- 两题的失败都是 dsh 自己写明的"沙箱拒绝"，不是它做不出来。

**mas 有没有同样的问题：** 没有。对 final1 的 30 个与 s6 的 36 个 mas 运行统计：沙箱状态全部是 `UNISOLATED`（容器里没有 bubblewrap，没有用户命名空间），沙箱拒绝次数全是 0，日志里没有 Permission denied、Operation not permitted、只读文件系统。mas 的命令可以写任意路径（configure-git-webserver 里真的建了 `/git/server` 与 `/etc/nginx/...`）。所以此前的对比偏向 mas。

**mas 自己的路径规则**（不依赖沙箱，仍然生效）在这 66 个运行里共拒绝 28 个执行单元：读外部路径不可用 17 次（14 个运行，全部通过）、写越界 2 次（query-optimize、git-multibranch，都通过）、受保护路径被创建 1 次（merge-diff 里的 `git init`，通过）、读越界 5 次（4 个运行，只有 headless-terminal 失败，原因是后台服务没起来，与这次拒绝无关）、其余 3 次是普通的工具错误（文件已变、查询无效、没有匹配）。

**评测对 mas 的安全设置，需要知道：** bench 把没有沙箱时每条命令要问用户的授权，一律自动回答"允许"（`bench.ts` 里注释写明"容器本身就是隔离"）。所以评测中 mas 的"命令授权"和"沙箱写入根"两层保护都没有生效；评测只证明任务能力，不证明这两层机制好用。**未做的审计：** 被自动放行的命令实际改了仓库外的什么文件，没有逐条核对（只统计了被拒绝的）；要做时对比命令前后受保护路径与写入根之外的变化即可，不花模型费用。如果要把安全机制也放进比较，需要另做一组：让 mas 在能开用户命名空间的环境里用真实的 bubblewrap 沙箱跑。

**改动：** `scripts/taskset/agentrun.mjs` 给 dsh 加 `--permission-mode danger-full-access`，让两边的条件一致：容器是沙箱，命令不再受限。

### Phase 1 的结论（已更正）

此前"最终集 mas 30/30 对 dsh 28/30，目标达成"是在 dsh 被沙箱限制的条件下得出的，**作废**。两边条件一致之后：

- 最终集：mas 30/30、3949 s、0.361 美元；dsh 29/30、3311 s、0.248 美元。通过数 mas 多 1 题（在噪声内），时间 mas 慢约 19%、费用高约 46%。
- 开发集：mas 31 到 33/36，dsh 35/36；费用 mas 0.461 到 0.565 美元，dsh 0.332 美元（高 39% 到 70%）。
- Phase 1 的目标"Turn-chat 不明显差于 DeepSeek Harness"在费用上没有达成，在通过数上最终集持平、开发集落后 2 到 4 题。
- 最终集已经用过一次（mas 一次、dsh 两次）。后续若要再验收，需要新的最终集，或明确同意复用。

**决定（2026-11-12，用户）：** Phase 1 的优化暂停，不再对 mas 做提示词或工具的调整；留到 Phase 3 做整体优化时再处理上面归因出的几项（单步思考长度、每次请求上下文大小、长任务里上下文的增长、收尾清理）。本次已有的修复（提示词 V、外部读取暂停规则、批量失败只计一次）保留。

### I3：用 Mission 跑 phase 1 的最终集（2026-11-14）

**目的**：phase 1 的最终集（30 题，Terminal-Bench 类与 SWE 类的小任务和合成的并行题）原本用 Turn-chat 跑。把 mas 换成 Mission（`mas run "<题目>"`）再跑一次，与 final1（mas Turn-chat）、final2（`dsh` 全权限）对比，看 Mission 在小任务上是否更好，以及它会不会把简单任务搞复杂。

**结果**：

|---|---|---|---|---|

- 失败的两题：`configure-git-webserver`（写了 `docker-compose.yml`，而任务容器里没有 docker，判分时网页连不上；`dsh` 也失败）、`query-optimize`（查询 1.15 秒，要求不超过参考解 0.77 秒的 1.05 倍；Turn-chat 通过）。
- 只有 2 题派了子任务，而且是最贵的两题：`qutebrowser`（lead 与 2 个 explorer，$0.065，Turn-chat $0.010）、`tune-mjcf`（2 个 worker，$0.081，Turn-chat $0.035）。两题都是改一处代码的任务。去掉这两题，其余 28 题 Mission $0.332、Turn-chat $0.316，只多约 5%。

**发现**：

- 这批题以改一个仓库的小任务为主，Mission 的拆分用不上，只剩开销：比 Turn-chat 少过 2 题、费用多 32%、用时多 62%。"这批题更偏向 Mission"的设想不成立。
- Mission 的说明本身没有让普通任务明显变贵（不派任务时约 +5%）；问题是两次不该派的派发，和"最后跑一遍检查"带来的大范围验证命令。
- 每题只跑一次，两题的通过差距在噪声内（一题看运行时间，另一题 `dsh` 也失败）。
- 这是旧最终集的第四次使用（mas 两次、`dsh` 一次），结果不用于调参；phase 3 起它不再作为最终集。

**随后**：Phase3Plan 第 2 节（新增 general 模式：平时对话，长任务时进入 Mission，交付后回到对话）与 RP3-ME-3（"不该拆"的判断与验证命令的范围）。
