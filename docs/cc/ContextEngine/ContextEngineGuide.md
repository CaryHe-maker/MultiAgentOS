# ContextEngine 理解指南（写给 meti）

> 这份是“讲给人听”的版本：解释 ContextEngine 做什么、为什么这样设计、怎么动手。  
> 需要精确的字段、默认值、测试清单时，看 `ContextEngineSpec.md`（写给开发者和 AI 编码助手）。  
> 两份文档的章节是对应的，本文会注明“见规格 §x”。  
> 作者：Claude（Cowork）

---

## 0 先用一个比喻

把大模型想成一位**非常聪明、但完全失忆的新同事**：

- 他每次开口之前，只能看到桌上的一叠纸。桌子外的东西，他一概不知。
- 桌子很小（token 预算），纸放多了，他也会看不过来，重要的内容反而被淹没。
- 每看一页纸都要花钱（token 费用），但**如果这叠纸的前半部分和上次一模一样，那部分几乎免费**（缓存）。

**ContextEngine 就是给这位同事准备这叠纸的助理。** 它要决定：

1. 先给他看什么：仓库概览；
2. 他要找东西时，帮他把相关代码翻出来：搜索；
3. 每次开口前，把任务说明、他之前做过的事、目前的进度，整理成一叠不超过桌面大小的纸：组装。

这三件事，就是规格里的三种操作：`ORIENT`、`SEARCH`、`ASSEMBLE`。

---

## 1 为什么这件事重要

- **同一个模型，套不同的外壳，成绩能差 20–30 个百分点。** 外壳里最重要的部分之一，就是模型每一轮看到什么。
- 面试复盘里的六层能力，第二层就是“能不能给 LLM 正确的信息”。面试官会追问：文档怎么切、为什么这么切、检索方案怎么选。
- 我们用的是便宜模型（DeepSeek Flash）。便宜模型更依赖好的上下文：给对了信息，它能做得很好；给乱了，它比贵模型更容易跑偏。

## 2 用一个完整的例子走一遍

**任务（固定任务 F2）：** “定位折扣边界逻辑、调用方和相关测试，并解释潜在错误。”仓库是一个陌生的小电商项目。

### 第 0 步：ORIENT，给新同事一份仓库概览

ContextEngine 读一遍仓库，生成大约 2,500 token 的概览：

```text
[项目记忆] AGENTS.md：使用 pnpm；测试命令 pnpm test；价格计算在 src/pricing
[目录树]   src/ (23 个文件)  cart/  pricing/  api/ …  test/ (11 个文件)
[清单]     package.json：name=shop-lite，scripts: test, build
[符号大纲] src/pricing/discount.ts: applyDiscount L40, DISCOUNT_THRESHOLD L12 …
[测试布局] test/**/*.test.ts
```

这份概览**整个运行只生成一次**，之后每一轮都原样放在最前面。原因见第 3.2 节。

### 第 1 步：ASSEMBLE，第一次组装

模型第一次看到的内容，从上到下是：

```text
┌ PREFIX（整个运行不变）────────────────┐
│ 系统指令：你是仓库分析助手，只能读…     │  ← 来自 AgentToolPool
│ 工具定义：SEARCH / READ / FINAL …        │
│ 任务：定位折扣边界逻辑…                 │
│ 仓库概览（第 0 步的结果）               │
├ HISTORY（目前为空）────────────────────┤
├ STATUS（每轮都变，放在最后）───────────┤
│ [运行状态] 第 1/24 步 · 已读：无         │
└────────────────────────────────────────┘
```

模型回答：`SEARCH "applyDiscount"`。

### 第 2 步：SEARCH，帮他翻代码

ContextEngine 用 rg 在仓库里找 `applyDiscount`，得到定义 1 处、调用 3 处、测试 2 处。然后：

- 每处命中截取前后几十行，重叠的合并成一块，并加上行号；
- 打分：定义处得分最高，其次是精确命中和路径命中，测试文件也有加分；
- 按预算装入前 8 块，每块附上得分理由，例如 `def-hit+exact×2`。

### 第 3 步：再次 ASSEMBLE

PREFIX 原封不动（这部分命中缓存，几乎免费），HISTORY 里多了“第 1 步：SEARCH → 搜索结果”，STATUS 更新为“第 2/24 步”。

模型看完结果，回答：`READ src/pricing/discount.ts L30–90`。读取由 Kernel 完成，读到的内容作为观察结果进入 HISTORY。

### 第 N 步：历史太长怎么办

走到第 15 步时，HISTORY 已经很长，快超出预算。ContextEngine 把最旧的 8 步**一次性**压缩成一行行摘要：

```text
#1 SEARCH "applyDiscount" → 6 条命中，涉及 src/pricing/discount.ts、src/cart/total.ts、test/pricing/discount.test.ts
#2 READ src/pricing/discount.ts L30–90（已读）
…
```

最近 6 步保持完整。完整的原文一直保存在 Artifact 里，模型需要时可以重新 READ。

### 最后：FINAL

模型给出结论，并附上文件路径和行号作为引用。Workflow 检查每条结论都有来源，生成报告。

## 3 每个设计背后的“为什么”

这一节和你的学习笔记是对应的，很多结论你已经在书里读到过。

### 3.1 为什么让模型自己搜，而不是提前检索好推给它

原始设计是在每次调用模型前，由 ContextEngine 主动检索、拼一个 Pack 推给模型，这是 RAG 的思路。问题在于：**提前检索用的是任务描述里的词，而真正相关的代码往往要读了第一处之后才知道下一步该找什么。**

Claude Code 和 Codex 都让模型自己搜（agentic search）。你在笔记里记录的书中实验 3-8 也是同一个结论：让 Agent 分解查询、多轮检索，证据召回率从 76% 提升到 100%（离线实验、预标注子查询，数字仅供参考）。

所以我们的做法是：ORIENT 给一份概览，让模型知道从哪里下手；之后由模型自己决定 SEARCH 什么、READ 哪里。ContextEngine 负责把每次搜索做好。

### 3.2 为什么前缀必须不变：钱

你的笔记写过：“稳定前缀是性能契约。只要前缀发生变化，后续的缓存命中会从变化处失效。”

具体算一笔账：DeepSeek Flash 在非高峰时段，缓存**命中**的输入每百万 token 0.003 美元，**未命中**是 0.15 美元，相差 50 倍。一个 20 步的任务，每轮都要重新发送前面的全部内容，累计输入可能有 40 万 token。前缀稳定时，大部分都能命中缓存。

所以规格要求：

- PREFIX 里不能有时间戳、随机 ID、计数器；
- 会变的东西（进度、步数）全部放到最后的 STATUS；
- 每次组装都输出 PREFIX 的哈希值，测试时检查它从头到尾不变。

### 3.3 为什么不用滑动窗口，而用“截断 + 成批压缩”

你的笔记总结过两点：简单的滑动窗口会破坏前缀稳定，还可能删掉关键的工具结果；另外，压缩要区分“持久记录”和“模型看到的投影”。

我们的做法对应得很直接：

- **持久记录**：每一步的完整观察都存在 Artifact 里，永远不删。
- **模型看到的投影**：只是一份“视图”。长观察截掉中间，保留开头和结尾，并告诉模型“完整内容在哪、需要可以再读”；旧步骤压成一行摘要。
- **成批压缩**：每次改写历史，都会让改写位置之后的缓存失效。所以不要每轮压一点，而是等快满时一次压一大批，这样只失效一次。
- **M1 不用 LLM 做摘要**：用固定格式生成摘要，结果可预测、不花钱、可测试。你的笔记也提到，摘要不能成为无法验证的唯一事实。

### 3.4 状态栏：事实由别人提供，我们只负责展示

笔记 2.3.4 的结论是：状态栏的事实来源不应该是 LLM。第几步、用了多少 token、读过哪些文件，这些由 Workflow 统计，ContextEngine 只负责格式化并放到最后。

它解决的问题是：对话一长，模型会忘记“我已经读过这个文件了”，然后重复读；或者忘了还剩多少步。状态栏每轮提醒一次。这也回答了田园在会上提到的“初始提示词会被淹没”。

### 3.5 代码为什么这样切

面试高频问题：“文档怎么切，为什么这么切？”面试官要的是完整的前因后果。

我们切代码的思路是：

- **不按固定长度切**：固定每 500 token 切一刀，很可能把一个函数切成两半，模型看到的是残缺的逻辑。
- **以命中位置为中心取一段**，再向上扩展到函数或类的开头，向下在空行处结束。这相当于一个轻量的“结构感知分块”（面试复盘里阿里那一轮的原话是 structure-aware chunking）。
- **每行带行号**：模型引用来源时可以精确到行，Workflow 也能核对引用对不对。
- **单块有上限**：避免一个超长函数占满预算。

M2 以后可以用 tree-sitter 做真正的语法树切分；M1 用正则近似，先看评测结果够不够用。

### 3.6 为什么打分要确定、可解释

打分公式是固定权重的加减法，而不是交给模型或向量相似度决定。好处有三个：

1. **可测试**：同样的输入永远得到同样的顺序，能写单元测试。
2. **可解释**：每条结果都附带得分构成，例如“定义命中 + 精确命中两次”，出了问题一看就知道是哪一项在起作用。
3. **可调优**：权重放在配置里，改一个数字，跑一遍检索评测，就能看到效果。

### 3.7 为什么需要“检索台账”

模型经常换个说法再搜一遍，结果还是同一段代码。台账记录这次运行已经给过哪些代码块（按内容哈希）。再次命中时，不重复放全文，只放一行“这段在第 3 步给过了”。**省 token，也提醒模型别绕圈。**

### 3.8 提示注入：外部内容只能待在“数据”的位置

你的笔记写得很清楚：模型不是安全边界。仓库里的代码、注释、README 都可能包含“像指令的文字”，例如“忽略之前的所有指令”。

ContextEngine 能做的是软防线：外部内容只出现在 HISTORY 的观察结果里，永远不进入系统指令；每段内容都标明来源。真正的硬防线在 Kernel：M1 仓库只读，写入和命令一律拒绝。另外，`.env`、密钥文件永远不会被放进 Pack，模型明确要搜也返回空。

### 3.9 为什么 M1 不上向量数据库

面试复盘里说，向量库选型“考的是 trade-off”。我们的回答模板：

> 我们的场景是单个中小型代码仓库。代码里的函数名、变量名是精确的标识符，文本搜索加符号匹配的召回已经很高，而且零成本、可解释、不需要建索引。向量检索擅长的是“字面不同但语义相关”，比如用户说“打折”、代码写 `promotion`。我们的做法是先用检索评测测出文本搜索的召回率；如果失败案例主要是这类语义不匹配，再引入 embedding。

这就是规格 §10 的 D6：**用数据决定何时升级**。

## 4 ContextEngine 和其他模块怎么配合

```text
          ┌───────────── Workflow（Cary）──────────────┐
          │ 决定下一步：调用模型、搜索、读文件、结束     │
          │ 提供：步骤历史、状态事实、预算              │
          └──────┬─────────────────────────────▲──────┘
                 │ UnitIntent                   │ UnitResult
          ┌──────▼─────────── Kernel（田园）─────┴──────┐
          │ 准入检查；把 CONTEXT 交给 ContextEngine；      │
          │ 执行 MODEL 和 FILE_READ                     │
          └──────┬──────────────────────────────────────┘
                 │ buildContext()
          ┌──────▼──── ContextEngine（meti）─────┐
          │ ORIENT / SEARCH / ASSEMBLE              │
          │ 自己拥有：检索台账、诊断信息            │
          └─────────────────────────────────────────┘
      AgentToolPool：提供系统指令和工具定义的内容（ContextEngine 只负责摆放位置）
```

几条边界，面试时也要能讲清楚：

| 问题 | 谁负责 |
|---|---|
| 读取文件的某几行 | Kernel（FILE_READ），ContextEngine 不做 |
| 系统提示词写什么 | AgentToolPool；ContextEngine 只决定它放在哪 |
| 第几步、用了多少 token | Workflow 统计；ContextEngine 只负责展示 |
| 模型看到的内容如何排列、如何压缩 | **ContextEngine** |
| 转成 DeepSeek 的消息格式 | Kernel 的模型适配器 |

## 5 评测：最值得你花心思的地方

面试复盘里最重的一句话：“搭建 Agent 的能力不稀缺，稀缺的是证明这个 Agent 在变好的能力。”

### 5.1 先做检索评测，因为它不花钱

检索评测不调用模型：对每个 fixture 写几条查询，并写下期望出现在前几名的文件，然后直接运行 SEARCH 检查。它运行快、成本为零，可以放进每次提交的检查里。

你调整分块大小、打分权重时，就看两个数：

- **Recall@3**：期望的文件出现在前 3 名的比例；
- **MRR**：期望文件平均排第几，取倒数后求平均，越接近 1 越好。

### 5.2 再做端到端评测

真正调用模型，完整跑一遍任务，检查报告里的结论和引用对不对。因为模型有随机性，**每个任务跑 3 次**取平均。

### 5.3 证明“某个改动有效”的方法

每个功能都做成开关：ORIENT、符号大纲、符号搜索、历史压缩、状态栏。开和关各跑一组，看差值。

面试官还可能问：“bad case 消失了，你怎么知道是你的改动起了作用？”我们的回答：

1. 失败过的任务**永久留在回归集**里，不会因为修好了就消失；
2. 每次改动都有开关对照数据；
3. 每次运行都有完整 trace，可以找到“修好之前在哪一步出错、修好之后那一步发生了什么变化”。

## 6 动手顺序（第一周）

目标：**第一周结束时，检索评测能跑起来。**

1. **读现有代码**：`packages/context-engine/src/index.ts`（约 120 行）和它的测试。现在的实现是逐个文件数关键词出现次数、整个文件塞进 Pack，这是起点。
2. **写合约变更提案**：把规格 §3 整理成一个 PR，只改 `packages/contracts`，请 Cary 和田园评审。这是和别人协作的第一步，越早越好。
3. **`adapters/workspace/reader.ts`**：路径安全和文件过滤，先写测试（规格 §8 的“安全”一行）。可以和田园对一下 Kernel 的路径检查，争取共用一套实现。
4. **`adapters/ripgrep/rg.ts`**：调用 rg 并解析 `--json` 输出。
5. **SEARCH 最小版**：TEXT + PATH 两种模式，先不做分块和打分，返回命中的整块内容。
6. **F1–F5 的 `expected.json`** 和检索评测脚本。

### 用 AI 写代码的方法

- 把 `ContextEngineSpec.md` 的相关章节给 AI 看，**一次只让它写一个文件**。
- **先让它写测试，你读懂测试，再让它写实现。** 测试就是规格的翻译，读懂测试就等于读懂了这个功能。
- 每个文件写完，问自己：这里为什么这样做？答不上来就问 AI，然后把答案记进学习笔记。这些答案就是你面试时的素材。
- 日常写代码用 Sonnet；遇到设计上拿不准的问题，再用更强的模型集中讨论。

## 7 术语表

| 术语 | 意思 |
|---|---|
| ContextPack | ContextEngine 的一次输出，发布后不可修改 |
| PREFIX / HISTORY / STATUS | 模型输入的三段：不变的开头、逐步增长的历史、每轮变化的状态 |
| 稳定前缀 | 每轮都完全相同的 PREFIX，用来命中缓存 |
| 缓存命中 | 服务商发现这段输入之前处理过，按极低价格计费 |
| 截断 | 单条观察太长时，只保留开头和结尾 |
| 压缩 / DIGEST | 把旧步骤替换成一行固定格式的摘要 |
| 检索台账 | 记录本次运行已经给过哪些代码块，用于去重 |
| provenance | 每条内容的来源：哪个文件、哪几行、哪个版本、怎么找到的 |
| snapshotId | 仓库文件状态的指纹，用于确认运行期间仓库没有变化 |
| Recall@k / MRR | 检索评测的两个指标 |
| 开关对照 | 同一功能开和关各跑一次，用差值证明效果 |
