# 从面试官关心的问题，反推项目架构（讨论稿）

> 作者：Claude（Cowork）  
> 依据：B 站《我的 AI Agent 面试复盘》（作者面试了小红书、阿里、币安等公司的 AI engineer / AI application 岗位），以及本项目 `feat/M1` 的现行设计  
> 注意：这是一位求职者的个人经验，不代表所有公司，但它归纳出的“六层能力”和业界的普遍共识一致，可以作为倒推的依据

---

## 1 面试官到底在考什么

文章最后把所有问题归纳成六层能力。原文的关键判断有三句：

1. **“搭建 Agent 的能力其实不稀缺，稀缺的是证明这个 Agent 在变好的能力。”**（币安）
2. **“Agent 工程的复杂度不在 agent loop 本身，ReAct loop 几十行代码就写完了。真正的复杂度是它外围的问题：授权、permission、state、沙盒。”**
3. **“生产级 AI 系统的核心是限制模型犯错的空间；模型是否更聪明并非重点。”**

六层能力与面试中出现的具体问题：

| 层 | 能力 | 面试中出现的真实问题 |
|---|---|---|
| 1 | 会不会用 LLM | prompt、structured output、tool call |
| 2 | 能不能给 LLM 正确的信息 | 文档怎么切、为什么这么切；向量库怎么选、数据量扩大怎么办；上下文管理 |
| 3 | 能不能控制 LLM 的行为 | 预编排还是动态编排；多 Agent 和普通 workflow 有什么区别；Graph 的 state 是什么、怎么存 |
| 4 | 能不能把 Agent 接到真实世界 | MCP、外部数据接入、代码执行在哪里跑 |
| 5 | Agent 犯错了怎么办 | 读写权限是否一样；参数合法性检查；高风险操作要不要二次确认；生成的代码能不能直接在生产机器跑；什么时候执行、拒绝、澄清 |
| 6 | 怎么证明 Agent 真的有价值 | 怎么 evaluate；AB test 多久显著；bad case 消失了，怎么知道是你的改动起了作用；五条 trace 怎么合并成一个优化方向 |

还有两个贯穿全场的追问：

- **“为什么一定要 multi-agent，普通 pipeline 不行吗？”** 每场面试都会问，只要简历写了多 Agent 就必须准备。
- **“为什么选它，为什么不选别的，什么时候会切换？”** 所有技术选型都会被这样追问。

## 2 一个重要发现：六层能力正好对应我们的五个模块

| 面试六层 | 本项目的模块 | 负责人 |
|---|---|---|
| 1 会用 LLM | Kernel 的模型适配器 + AgentToolPool 的 Prompt 与工具定义 | 田园、Cary |
| 2 给正确的信息 | **ContextEngine** | meti |
| 3 控制行为 | **Workflow** | Cary |
| 4 接到真实世界 | Kernel 的工具执行器 + AgentToolPool | 田园 |
| 5 犯错怎么办 | **Kernel**（权限、校验、沙箱、确认） | 田园 |
| 6 证明有价值 | **评测体系**（目前没有明确负责的模块） | meti |

这说明现有的模块划分方向是对的：每个人都有一块能在面试里深挖的领域。**但第 6 层目前是空的**，而文章说“大部分面试官真的非常 care 这一层”。这是最需要补的地方。

## 3 从面试问题反推出的八条架构决定

### 决定 1：Workflow 提供边界，Agent 在边界里自主（第 3 层）

**面试问题：** 预编排还是动态编排？多 Agent 和 workflow 有什么区别？

**文章给出的答案：** “controller + workflow”：核心逻辑用 workflow 控制，关键节点设置约束；局部的地方，比如选哪些工具、检索哪些信息，让 Agent 动态判断。**“workflow 提供边界，Agent 在边界里面获得自主性。两者不是二选一。”**

**对我们的意义：** 这句话正好化解了 Cary（重工作流）和“让模型自主循环”之间的分歧。具体设计：

```text
Workflow 固定阶段（确定性，由代码控制）：
  理解任务 → 定位代码 → 形成结论/修改 → 验证 → 报告
每个阶段内部（Agent 自主）：
  自己决定搜什么、读哪个文件、下一步做什么
阶段之间的关卡（确定性检查）：
  步数与 token 预算、是否有来源证据、测试是否通过
```

面试时可以清楚地说出：哪些是写死的、哪些交给模型、为什么这样分。

### 决定 2：确定性的事交给代码，LLM 只做判断（第 3、5 层）

**面试问题：** 数据要求非常精确时怎么办？

**文章原则：** “确定性的部分不要交给 LLM。LLM 真正适合做的是理解上下文、选择分析路径、做归因的解释。”

**对我们的意义：** 系统里每个环节都要标明“这是代码做的，还是模型做的”：

| 由代码负责（确定性） | 由模型负责（判断） |
|---|---|
| 搜索、读文件、执行测试 | 决定搜什么、读哪里 |
| 路径与权限检查 | 理解代码逻辑 |
| 测试是否通过的判定 | 分析失败原因 |
| token 统计、预算控制 | 决定下一步策略 |
| 报告中的引用与原文是否一致 | 写出结论与解释 |

### 决定 3：多 Agent 只在满足条件时使用，并用实验证明（第 3 层）

**面试问题：** 为什么一定要 multi-agent？

**文章给出的四个条件**，至少满足其一，拆 Agent 才有意义：不同阶段需要完全不同的工具；需要不同的 prompt 和上下文；路径需要动态分支、失败后可回退；每个角色有清晰的责任边界。

**对我们的意义：** 项目名叫 MultiAgentOS，这个问题一定会被问到。建议只保留三种有充分理由的多 Agent 形态，并在文档中写明各自满足哪个条件：

| 形态 | 满足的条件 | 理由 |
|---|---|---|
| 探索子 Agent | 不同上下文、不同工具（只读） | 让大量搜索细节留在子 Agent 里，主 Agent 只拿摘要，节省上下文 |
| 验证 Agent | 不同 prompt、清晰职责、只读工具 | 写代码的 Agent 容易认为自己是对的，独立的审查角色更可靠 |
| 并行 Worker | 清晰的责任边界（任务树划定文件范围） | 前后端这类互不重叠的任务可以同时进行 |

**最重要的是：必须有“单 Agent 与多 Agent 在同一批任务上的对比数据”。** 面试官说“自己造出来的复杂度经不起追问”，而数据是唯一经得起追问的回答。

### 决定 4：“执行、拒绝、澄清”三种选择（第 5 层）

**面试问题：** Text-to-SQL 里用户说“卖得最好”，是指销量还是销售额？

**文章原则：** “一个好的 Agent 不应该什么问题都回答，它应该知道什么时候执行、什么时候拒绝、什么时候去澄清。”

**对我们的意义：** 给 Agent 增加两个动作：

- `ASK_USER`：需求有歧义时向用户提问，例如“你说的修复，是改实现还是改测试？”
- `CANNOT_DETERMINE`：证据不足时明确说“无法确定”，而不是编造结论。

M1 的只读分析报告里已经有“未确认项”，方向是对的。评测中还应该包含**故意设计的歧义任务**，检查 Agent 会不会乱猜。

### 决定 5：复杂度放在外围——权限、校验、确认、沙箱（第 5 层）

**面试问题：** 读写权限一样吗？参数合法性怎么检查？高风险操作要二次确认吗？AI 生成的代码能在生产机器跑吗？

**文章原话：** 把 Agent 生成的代码“丢到隔离沙盒里，超时直接杀掉，访问未授权的资源就直接拒绝。这个时候，你的 Agent 才真正从一个 demo 变成了一个 system。”

**对我们的意义：** 这段话几乎就是 Kernel 的需求说明，也印证了会议上田园坚持的“机器级隔离”方向是面试官真正看重的。Kernel 应当能清楚回答以下每一项：

| 面试问题 | Kernel 的对应设计 | 里程碑 |
|---|---|---|
| 读写权限一样吗 | 只读工具与写工具分级；写操作需要确认 | M1 只读，M2 加写 |
| 参数合法性检查 | 每个工具参数经 schema 校验；路径规范化与越界拒绝 | M1 已有 |
| 高风险操作二次确认 | 写文件、执行命令前请求用户确认 | M2 |
| 代码在哪里执行 | 命令在容器中执行，只挂载工作区，默认禁网，超时即杀 | M2 |
| 越权怎么处理 | 拒绝并向模型返回错误；多次越权则终止 | M1 起 |

### 决定 6：State 要具体到字段，存储选型要讲得出 trade-off（第 3 层与后端基础）

**面试问题：** Graph 里的 state 是什么、怎么存？为什么用这个数据库？

**文章原则：** “state 不是一个抽象的名词”，要说得出里面有哪些字段、在哪些节点被读写。数据库选型考的是“数据模型和存储模型是否匹配”。

**对我们的意义：**

- Workflow 应当有一份**具体的运行状态定义**：当前阶段、已用步数与 token、已读文件列表、已发现的证据、未确认项、最近一次错误。每个字段写明由谁写、谁读。这也正是 ContextEngine 渲染“状态栏”的数据来源。
- 存储选型要能讲出理由。例如：“M1 用 JSONL 文件存运行日志，因为单用户、只追加写入、便于人工查看和回放；如果要支持多用户并发查询，再换 SQLite 或 PostgreSQL。”**能讲清楚什么时候切换，比一开始就用 PostgreSQL 更加分。**

### 决定 7：把 Cary 的可靠性设计落到真实的小场景（后端基础）

**面试问题：** 消息堆积怎么办？重复消息怎么办？exactly-once 做不到时怎么设计幂等？

**文章原话：** 这些“全部都是 agent engineer 的问题”，但也提醒“不要为了 Agent 而 Agent”。

**对我们的意义：** Cary 文档中的幂等、重试、状态恢复等设计，面试官确实会问，**但必须对应到项目中真实发生的场景**，而不是凭空引入 Kafka。我们项目里就有天然的小场景：

- **模型 API 超时后重试**：同一个“修改文件”的动作会不会被执行两次？这就是幂等问题，可以用 `idempotencyKey` 解决，Cary 的设计里已经有这个字段。
- **并行 Worker 争抢资源**：同时发出的模型请求超过 API 限流怎么办？这是并发控制与限流问题。
- **进程中途崩溃**：从会话日志恢复时，已经执行过的工具调用要不要重放？

面试时的正确讲法是：“我们遇到了 X 问题，所以引入了 Y；如果流量再大十倍，我会考虑 Z。”

### 决定 8：从第一天起就能证明 Agent 在变好（第 6 层，最重要）

**面试问题：** 怎么 evaluate？bad case 消失了，怎么知道是你的改动起的作用？五条 trace 怎么合并成一个优化方向？

**文章原话：** “成功会摧毁自己的证据”：bad case 消失后，监控系统就失去了观测它的能力。作者复盘后给出的方法是：保留对照组；构造回归测试集，定期投放历史 bad case；在归因上看改动的命中日志与 case 消失的时间相关性。

**对我们的意义：** 评测体系应当包含五个部分：

| 组成 | 作用 | 对应文章里的问题 |
|---|---|---|
| **固定任务集** | 每次改动前后跑同一批任务，比较成功率、步数、成本 | 怎么 evaluate |
| **bad case 回归集** | 每个失败过的任务都永久保留，修好后继续跑 | 成功会摧毁自己的证据 |
| **开关对照实验** | 每个新功能都可以关闭，“开”和“关”各跑一遍 | 怎么知道是这个改动起的作用 |
| **完整 trace 记录** | 每一步的输入、模型输出、工具调用、结果都落盘 | 五条 trace 怎么合并成优化方向 |
| **失败原因分类** | 把失败归为：没找到文件、理解错误、工具调用出错、超出步数等 | 从多条 trace 中找共性 |

注意：模型输出有随机性，同一任务要跑多次（例如 3 次）取平均，否则“提升了 5%”可能只是运气。

## 4 对团队工作方式的启发

文章第 4 节的 AI Coding 面试考四件事：先自己理解问题；会不会拆任务；会不会验证 AI 的输出；能不能解释设计决定。面试官说：“真正想看的是这个设计到底是不是你自己做的决策。”

这对三个人用 AI 写代码有直接要求：

1. **每个设计决定都要有一段自己写的理由。** 建议建立 `docs/decisions/` 目录，每个重要选型一个短文件，写清楚：选了什么、考虑过哪些替代方案、为什么选它、什么情况下会切换。这份目录就是面试时“所有技术选型都要准备”的现成材料。
2. **AI 写的代码必须自己读过、跑过测试**，才能合并。
3. **每人都要能讲清楚别人的模块。** 面试官会问整个系统，而不只是你负责的部分。

## 5 每个人的面试故事

| 成员 | 可以深挖的面试主题 | 需要用项目证明的事 |
|---|---|---|
| Cary | 预编排与动态编排的取舍；state 设计；多 Agent 何时有必要；幂等与恢复 | 单 Agent 与多 Agent 的对比数据；任务树让重复劳动减少了多少 |
| 田园 | 权限分级；参数校验；二次确认；沙箱隔离；越权与异常处理 | 安全测试：越权、路径逃逸、超时，全部被拦截 |
| meti | 上下文怎么给（代码怎么切、为什么这么切）；检索选型的 trade-off；压缩与缓存；**怎么证明 Agent 在变好** | 每个上下文策略的开关对照数据；bad case 回归集；失败原因分析 |

## 6 已并入 M1 修改提案的内容

本文的以下建议已经写入 `M1ChangeProposal.md`，评审时以提案为准：

- Workflow 采用“固定阶段 + 阶段内自主”：提案第 5.1 节。
- AnalysisAction 增加 `ASK_USER` 与 `CANNOT_DETERMINE`：提案第 5.2 节。
- 从第一周起完整记录 trace：提案第 5.3 节。
- bad case 回归集、多次运行取平均、开关对照、歧义任务：提案第 4.2 节。
- 建立 `docs/decisions/` 设计决定记录：提案第 8 节。

## 附：文章中值得背下来的几句话

- workflow 提供边界，Agent 在边界里面获得自主性。
- 确定性的部分不要交给 LLM。
- 生产级 AI 系统的核心是限制模型犯错的空间。
- 一个好的 Agent 知道什么时候执行、什么时候拒绝、什么时候澄清。
- 搭建 Agent 的能力不稀缺，稀缺的是证明它在变好的能力。
- 你需要证明复杂度是业务要求带来的；自己造出来的复杂度经不起追问。
