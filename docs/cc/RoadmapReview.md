> **与当前提案的关系：** 本文写于 `M1ChangeProposal.md` 之前，是提案的分析依据。之后的讨论对部分结论做了调整，**凡与提案不一致之处，以提案为准**，主要有两处：

## 1 结论摘要

现有路线图的**方法**是对的：分里程碑推进、每个里程碑都能独立运行、禁止交付半成品、后一阶段必须通过前一阶段的回归、部分技术要有数据证明才能引入。这些原则应当保留。

问题出在路线图的**主轴**和**内容**上：

1. 里程碑按“平台成熟度”排序（持久化 → 并行 → 安全治理 → 多租户平台），而一个 Agent 产品真正的主轴应该是“Agent 能力”（能解决多难的任务、成功率多少、成本多少）。
2. 让 Agent 变聪明的工作，也就是提示词、工具设计、上下文管理和评测，在路线图里只是附属列，没有成为任何一个里程碑的核心目标，也没有量化指标。
3. 平台机制在没有任何运行证据之前就被冻结为“不得改写”的约束，前期投入大，收益遥远。
4. M2 到 M5 的体量远超三名学生、每人每周 20 小时的现实产能。项目的名字和差异化卖点“多 Agent”排在 M3，按目前的产能推算，有较大风险无法在项目周期内做到。

建议：保留“分阶段、可独立交付”的方法，把主轴换成 Agent 能力，每个里程碑用评测数字验收，平台机制改为“出现真实问题再按最小形态引入”。

## 3 具体问题

### 3.1 主轴错位：按平台成熟度排序，而不是按 Agent 能力排序

AchievePlan 的五个里程碑依次是：只读分析 → 持久化与恢复 → 多任务并行 → Checkpoint 与审批 → 多租户平台。每一步增加的主要是可靠性与治理能力。

但一个 coding agent 好不好用，首先取决于它能不能把任务做对。Claude Code、Codex、Aider 这些产品的早期版本都没有数据库、没有 durable execution、没有多租户，它们靠的是一个简单的主循环、好用的工具和精心管理的上下文。路线图第 3.1 节的“累积路线表”里虽然每个里程碑都列了 Agent、Tool、ContextEngine 的增量，但：

- 没有任何一个里程碑以“任务成功率达到多少”作为验收门槛。
- 评测集在 M1 只有 5 个任务，之后没有扩充计划。
- 提示词设计、edit 格式、错误恢复、上下文压缩这些直接影响成功率的工作，不是任何里程碑的核心交付。

**影响：** 可能做完 M2 之后，系统在崩溃恢复上非常严谨，但 Agent 本身连简单 bug 都修不好，而团队到那时才第一次发现这个问题。

### 3.2 M1 砍掉的是功能，保留的是架构仪式

TargetM1 把产品收窄为“单用户、单进程、单 Agent、只读”，这一步是对的。但同时要求五个 Module、五项 Infrastructure 从 M1 起建立稳定边界，并配套 Envelope、BoundaryContext、Protocol Registry、`Unsupported` 预留、兼容矩阵（S4-06）、身份链贯穿（S3-07）等机制。

这些机制解决的是跨进程、跨版本、多消费者的问题，而 M1 是一个单进程、没有外部消费者的 v0 工具。以 S4-06 为例，“旧 fixture、新 reader、未知 major、opaque Ref、Unsupported 兼容矩阵”，是在给一个还没有任何使用者的实验性协议做兼容性测试。

**影响：** 四周 240 人时里，有相当一部分会花在不会影响演示效果、也不会影响任务成功率的地方。

### 3.3 产品为了迁就架构而倒退

最初的 M1 目标是“单 Agent 完成简单真实编码任务”，现在变成了“只读仓库分析”，写文件、执行命令和测试都推到了 M2。按文档的解释，这是为了降低风险。但带用户确认的写文件和执行命令，实现起来并不难：一个查找替换工具、一个命令白名单、一次确认提示，再加上 git 就能撤销。

真正把它挤出 M1 的，是同时要满足的大量边界与协议要求。正常顺序应当是产品目标先定，架构为它让路；现在是架构先定，产品为它收缩。

**影响：** “只读分析报告”的演示效果远不如“Agent 自己把 bug 修好并跑通测试”，而后者才是这个项目的核心卖点。

**后续讨论的结论：** 考虑到 11 月 1 日的时间点和各人的实际投入，提案最终保留只读 M1，但要求 M2 只做 Coding Agent、不再捆绑持久化和 DBOS，使“能改代码”尽早到来（见提案第 7.1 节）。

### 3.4 M2 的体量是 M1 的数倍，而且难度集中在最难的地方

M2 同时包含：Coding Agent、隔离 worktree、PostgreSQL 分 schema 分 role、Kysely、DBOS durable execution、幂等与 expectedVersion、Event Journal、Outbox/Inbox、EffectRecord 与未知副作用 reconciliation、Fastify API、备份恢复、故障注入测试。验收任务要求在四个故障点强制终止进程，并证明恢复后副作用不重复。

“崩溃后副作用恰好执行一次”是分布式系统里最难的问题之一，工业界也要依赖 Temporal 这类成熟平台、花大量工程投入才能做好。对一个本地 CLI 工具来说，用户需求其实很简单：中断后能从会话日志接着来。一个 JSONL 会话文件加上 resume 命令就能满足，Claude Code 的会话恢复就是这样做的。

**影响：** M2 很可能成为项目停滞的地方。

### 3.5 M5 的目标是企业 SaaS，与项目目的无关

M5 要求多租户、OIDC、RBAC/ABAC、RLS、S3、PITR、跨区域灾备、高可用多控制面、滚动升级、React Web 审核台，并且“M5 完成时必须完整实现 TargetArchitecture.md”。

这个定义把终点设成了“完成架构文档”，而不是“为用户解决问题”。对一个以学习和求职为目的的学生项目，这些能力既无法在合理时间内完成，也不会在面试里加分：面试官不会期待学生项目有跨区域灾备，但一定会问“你的 Agent 成功率多少、怎么评测、遇到过什么问题”。

### 3.6 多 Agent 这个核心卖点排得太靠后

项目叫 MultiAgentOS，差异化在于多 Agent 并行。但在路线图里它位于 M3，前面还有持久化、DBOS 和故障恢复。以现有产能推算，M3 很可能在项目周期内无法到达。而多 Agent 真正依赖的前置条件只有两个：一个好用的单 Agent，以及 git worktree 隔离，并不需要数据库和 durable execution。

### 3.7 过早冻结架构

AchievePlan 规定：后续里程碑“不得改写五 Module、五 Infrastructure 的所有权和关键调用方向”。但 TargetM1 第 10.1 节自己也写了“M1 完成前允许修正抽象，避免把未经验证的设计永久化”。这两条互相矛盾。

在还没有一次真实模型调用的时候，把十个组件的边界定为永久约束，风险很大。Agent 领域的最佳实践变化很快，例如“让模型自己搜索”已经在很大程度上取代了“预先检索推送上下文”。架构需要能跟着证据调整。

### 3.8 流程成本偏高

每个里程碑有 8 项共同发布门，包括运维闭环（启动、健康检查、升级、回滚、运行手册）和兼容闭环（迁移和回滚方案）；M1Process 还要求功能、架构、测试三类负责人逐阶段签字。这些是生产团队的流程，对三人学生团队来说，会让大量时间花在文档和流程本身。

## 4 建议的调整

### 4.1 保留的原则

- 每个里程碑都能独立运行和演示。
- 后一里程碑必须通过前一里程碑的回归测试。
- 技术引入要有 ADR 和实测数据。
- 没有测试证据不算完成。
- 模型输出只是提案，副作用必须经过权限检查。
- 不修改用户原始仓库。

### 4.2 换主轴：按 Agent 能力排里程碑，用评测数字验收

> 下表为最初的示意方案，已由提案第 7 节取代，保留在此供参考。

| 里程碑 | 交付 | 验收门槛（示例，待团队校准） |
|---|---|---|
| M1（4 周） | 能修 bug 的单 Agent CLI：主循环，read/glob/grep/edit/write/bash 六个工具，写入和执行命令需用户确认，git 快照与撤销，JSONL 会话日志，评测框架 | 10 个自建任务，通过率 ≥ 40%；每题平均成本可统计 |
| M2（3 周） | 上下文工程：稳定前缀与缓存统计、AGENTS.md、输出截断、仓库地图、状态栏、历史压缩；edit 鲁棒性 | 30 个任务；每个功能都有开/关对照数据；通过率明显高于 M1 |
| M3（2–3 周） | 可靠性与体验：Docker 执行命令、从会话日志恢复、Plan 模式、流式界面、重试 | M1–M2 回归不下降；中断后可恢复会话 |
| M4（3–4 周） | 多 Agent：探索子 Agent；Planner 加并行 Worker 与 worktree；共享公告板（Scope Tree 的最小形态） | 与单 Agent 在同一任务集上对比通过率、耗时、成本，如实报告 |
| M5（可选） | MCP、通用任务 Agent（经济学作业类任务）、SWE-bench 子集 | 按需确定 |

### 4.3 平台机制的处理方式

PostgreSQL、DBOS、Outbox/Inbox、Lease/fencing、Envelope、Protocol Registry、多租户等机制不删除设计，而是移入“候选机制清单”。引入规则只有一条：**出现真实的失败案例或评测数据表明需要时，才按最小形态引入。** TargetArchitecture 保留为长期参考，不再作为完成定义。

### 4.4 对现有代码的处理

- **直接复用：** 工程配置与质量门、TypeBox schema 校验、FILE_READ 的路径安全实现与测试、ContextEngine 的文件遍历与 ignore 逻辑、fixture 设计思路。
- **简化：** Module Host、Communication Router、Persistence Port 在单进程里可以退化为普通的依赖注入与函数调用；Envelope 和 BoundaryContext 只保留 correlationId 这一类确实有用的字段。
- **冻结：** Protocol Registry、兼容矩阵、`Unsupported` 预留、身份链贯穿。

## 6 一个低成本的验证办法

在做出决定之前，可以用一周时间做一个对照实验：由一位同学在不使用现有框架的情况下，写一个 200 行左右的最小 Agent（主循环加 read/grep/edit/bash），在同样的 5 个 fixture 上跑一遍。如果它能解决其中一部分任务，就说明 Agent 能力的主要来源是模型、工具和上下文，而不是平台机制，路线图应当围绕前者组织。如果它表现很差，这个结果本身也会告诉我们该补哪些能力。无论哪种结果，这一周的投入都不会浪费。
