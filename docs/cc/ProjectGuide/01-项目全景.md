# 01 项目全景：MultiAgentOS 到底在做什么

> 写给 meti。目标：读完能用自己的话讲清楚整个项目，周日开会时有方向感。  
> 依据：`feat/M1` 分支（提交 `392a3b5`）的文档与代码。代码现状以 2026-09-26 为准。  
> 作者：Claude（Cowork）

## 1 一句话

**MultiAgentOS 想做一个“让 AI 自己读代码、改代码”的命令行工具，最终能让多个 AI 分工并行干活。** M1 先做最小的一步：一个只读的“仓库分析助手”。你问它一个关于陌生代码库的问题，它自己搜索、读代码，最后交给你一份每句话都标明出处（文件和行号）的分析报告。

---

## 2 整个项目的设计理念（五条）

读 Cary 的文档时，很多看起来复杂的设计，都可以归结为下面五条思想。理解了它们，就理解了项目的“骨架”。

### 理念 1：模型只能“提议”，不能“动手”

模型说“我要读 `cart.ts`”，这只是一个**提议**。真正去读文件的，是系统里的另一个部分（Kernel）。Kernel 先检查这个动作是否允许，再去执行。

> 类比：模型是出主意的参谋，Kernel 是握着钥匙的管理员。参谋不能自己开门。

**为什么：** 模型会犯错，也可能被仓库里的恶意文字诱导（提示注入）。只要所有动作都经过同一道关卡，就能把“模型犯错”的后果限制住。面试复盘里那句“生产级 AI 系统的核心是限制模型犯错的空间”，说的就是这个。

### 理念 2：每个模块只管自己的事

五个模块各有一块“地盘”，谁的数据谁负责，不能跨过去直接改别人的东西，只能通过约定好的接口（Port）去请求。

> 类比：公司里的部门。财务不能直接改人事的档案，要发申请。

**为什么：** 三个人各写各的模块，只要接口定好，就能同时开工、互不干扰。这就是田园说的“有明文规范，才不会甲乙两队同时施工”。

### 理念 3：每一步都留下记录，能查到来源

每个动作都有编号，每份结果都存档（Artifact），报告里的每个结论都要能指回“哪个文件、哪几行、哪个版本”。

**为什么：** 出了问题能回放、能定位；报告能被人验证，而不是“AI 说了算”。

### 理念 4：先做最小可用的一步，但给以后留好扩展的位置

M1 只做单 Agent、只读、单进程。但数据结构里已经带着以后会用到的 ID（比如任务树、图版本），以后加功能时，是“往上加”而不是“推倒重来”。

**这一条也是团队现在争论最多的地方：** 留多少扩展位置合适？Cary 倾向于多留，你和我的提案倾向于少留、先跑起来。周日开会要讨论的“第一版做最小有效单元，还是兼容后面大部分框架”，就是这个问题。

### 理念 5：最终目标是多 Agent 协作

项目名里的 “Multi”，指的是以后让一个规划 Agent 把大任务拆开，交给多个 Agent 并行完成（比如一个写前端、一个写后端），再合并结果。Cary 设计的“任务树”（MissionScope），就是为了让每个 Agent 知道自己在整个任务里的位置、不和兄弟重复干活。**这是 M3 以后的事，M1 完全不涉及。**

## 3 一次运行，从头到尾发生了什么（M1）

用户在命令行输入：

```bash
multiagent run --repo ./shop --prompt "定位折扣边界逻辑、调用方和相关测试，并解释潜在错误"
```

接下来发生的事，按顺序：

| 步 | 谁 | 做什么（大白话） |
|---|---|---|
| 1 | **UserInteraction**（前台） | 接收你的问题，登记一个会话，把请求交给 Kernel |
| 2 | **Kernel**（管理员） | 检查请求合不合法，转交给 Workflow |
| 3 | **Workflow**（项目经理） | 建一个“运行”，决定这次用哪个 Agent、哪个模型、哪套提示词（从 AgentToolPool 查） |
| 4 | **AgentToolPool**（工具库/人事档案） | 返回 Agent、模型、工具、提示词的固定版本 |
| 5 | Workflow → Kernel → **ContextEngine**（资料员） | 生成仓库概览（ORIENT） |
| 6 | Workflow → Kernel → ContextEngine | 把任务、概览、状态组装成模型的输入（ASSEMBLE） |
| 7 | Workflow → **Kernel** | 调用模型（DeepSeek），拿回模型的“提议”，比如“搜索 applyDiscount” |
| 8 | Workflow | 解读提议：是搜索、读文件，还是给出最终答案？ |
| 9a | 如果是搜索：Workflow → Kernel → ContextEngine | 执行搜索（SEARCH），结果存档 |
| 9b | 如果是读文件：Workflow → Kernel | Kernel 检查路径安全后读文件，结果存档 |
| 10 | Workflow | 把结果记为这一步的“观察”，回到第 6 步，开始下一轮 |
| 11 | Workflow | 模型给出最终答案时，检查每条结论都有出处；步数或预算用完就停止 |
| 12 | Kernel → UserInteraction | 把运行状态和报告展示给你 |

**核心循环**就是 6 → 7 → 8 → 9 → 10，反复进行，这就是所谓的 “Agent loop”。其余步骤都是开头的准备和结尾的收尾。

## 4 五个模块和五项基础设施，用大白话说

### 4.1 五个模块（有“业务逻辑”的部分）

| 模块 | 比喻 | 负责什么 | 负责人 | 代码目录 |
|---|---|---|---|---|
| UserInteraction | 前台 | 接收用户输入、展示结果；M1 只是一个命令行 | Cary | `packages/user-interaction`、`apps/cli` |
| Workflow | 项目经理 | 管理一次运行的全过程：Agent 循环、步数和预算、什么时候停、最终验收 | Cary | `packages/workflow` |
| Kernel | 管理员 + 执行员 | 所有动作的唯一入口：检查权限、调模型、读文件、记录每一步 | 田园 | `packages/kernel`、`apps/executor` |
| ContextEngine | 资料员 | 决定模型每一轮看到什么：仓库概览、搜索、组装输入、压缩历史 | meti | `packages/context-engine` |
| AgentToolPool | 人事档案 / 工具库 | 存放 Agent、模型、工具、提示词的“定义”，只存不执行 | Cary（M1 最小实现） | `packages/agent-tool-pool` |

**一个容易混淆的点：** Workflow 决定“做什么”，Kernel 负责“真的去做”。比如“下一步读 cart.ts”是 Workflow 根据模型提议决定的，但打开文件、检查路径安全的是 Kernel。

### 4.2 五项基础设施（不含业务逻辑的“水电煤”）

| 基础设施 | 比喻 | M1 的实现 | 以后可能换成 |
|---|---|---|---|
| Shared Contracts | 公司统一的表格模板 | TypeBox 定义所有模块之间传递的数据格式，并在运行时检查 | 不变 |
| Artifact Store | 档案室 | 本地文件夹，按内容哈希存放大块结果（文件内容、搜索结果、报告） | S3 对象存储 |
| Persistence | 账本 | 本地文件读写 | PostgreSQL |
| Communication | 内部邮件 | 进程内直接转发 | 消息队列（NATS） |
| Module Host | 开机管理员 | 按顺序启动各模块 | 多进程部署 |

**为什么基础设施要单独列出来：** 这样以后把“本地文件夹”换成“云存储”时，业务模块的代码一行都不用改。这是理念 4（留扩展位置）的具体体现，也是“架构仪式”争论的焦点：M1 里这五项的实现都很薄，但接口和测试都要写。

## 5 和主流项目比较

| 我们的模块 | 在主流项目里对应什么 | 说明 |
|---|---|---|
| Workflow 的 Agent 循环 | Claude Code 的主循环、mini-swe-agent 的 100 行核心、LangGraph 的状态图 | 本质都是“调模型 → 执行工具 → 结果放回 → 再调模型” |
| Workflow 的任务图与任务树（M3+） | LangGraph 的多节点图、Anthropic 多 Agent 研究系统的“主 Agent 分派子 Agent” | 我们的任务树强调让子 Agent 知道兄弟在做什么 |
| Kernel 的权限与隔离 | Codex CLI 的沙箱与审批模式、OpenHands 的 Docker 运行环境 | 主流做法：模型只能提议，执行在隔离环境里 |
| ContextEngine | Claude Code 的 CLAUDE.md 与自动压缩、Aider 的 repo map、OpenHarness 的记忆与压缩 | 主流做法：让模型自己搜 + 管好上下文窗口 |
| AgentToolPool | Claude Code 的 subagent 定义与 Skills、OpenHarness 的工具注册表 | 定义与执行分开 |
| 持久化与恢复（M2+，计划用 DBOS） | Temporal、DBOS 这类 durable execution 平台 | 主流 CLI 工具一般只用会话日志恢复，不用这么重的方案 |

### 我们和它们最大的不同

1. **模块划分更“正式”。** 主流 CLI 工具通常是一个程序里几个文件夹；我们是五个模块、五项基础设施，每个都有独立的包、接口和测试。好处是分工清楚，代价是前期工作量大。
2. **每个动作都是一个有编号的“Unit”，都经过 Kernel、都有记录。** Claude Code 也有权限检查，但我们把“提议—准入—执行—记录”做成了统一的流水线，审计能力更强。
3. **任务树（M3+）是 Cary 的核心构想。** 面试时可以讲，但要注意：Anthropic 的多 Agent 研究系统里也有“明确告诉子 Agent 任务边界”的做法，建议说“借鉴并实现”，而不是“主流没有”。

### 我们目前最明显的短板

还没有能跑起来的 Agent 循环。Workflow 目前只做到“建一个运行、查好定义”，模型调用还没接上。这是 M1 接下来最重要的工作。

## 6 从面试官的角度看这个项目

面试复盘把 Agent 岗位要求总结为六层能力，正好对应我们的模块：

| 面试官想看的能力 | 在我们项目里由谁体现 | 能讲的亮点 | 会被追问的地方 |
|---|---|---|---|
| 会用 LLM | Kernel 的模型调用 + AgentToolPool 的提示词 | 结构化动作输出、校验失败怎么处理 | 为什么用这个模型、成本多少 |
| 给 LLM 正确的信息 | **ContextEngine（你）** | 稳定前缀省钱、截断与压缩、检索打分可解释 | 代码怎么切、为什么不用向量库 |
| 控制 LLM 的行为 | Workflow（Cary） | 固定阶段 + 阶段内自主、步数与预算、终止条件 | 预编排还是动态编排、为什么需要多 Agent |
| 接入真实世界 | Kernel（田园） | 只读工具、路径安全 | 代码在哪执行、MCP 怎么接 |
| 犯错了怎么办 | Kernel（田园）+ Workflow | 越权拒绝、非法输出重试、结构化错误分类 | 权限分级、沙箱、二次确认 |
| 证明有价值 | **评测（你）** | 检索评测、开关对照、回归集、每次运行可回放 | bad case 消失后怎么证明是你修好的 |

**对你个人最重要的一点：** 面试官几乎一定会问“讲讲整个系统”，所以你不能只懂 ContextEngine。至少要能讲清楚第 3 节的一次运行全过程，以及理念 1 和理念 2。这两份文档（本文和《02 三人分工》）就是为这个准备的。

## 7 常见名词速查

| 名词 | 大白话 |
|---|---|
| WorkSession | 一次“对话会话”，用户视角的一段工作 |
| WorkflowRun | 一次完整的运行，从收到问题到交出报告 |
| TaskRun / TaskAttempt | 一个任务 / 这个任务的一次尝试（失败重试会产生新的 Attempt）；M1 只有一个任务 |
| AgentRun / AgentStep | 一个 Agent 的一次工作 / 其中的一步 |
| UnitIntent | 一个“动作申请单”：我要调模型 / 读文件 / 搜索 |
| UnitResult | 动作的“回执”：成功还是失败，结果存在哪个 Artifact |
| Artifact / ArtifactRef | 存档的大块结果 / 指向存档的“取件码” |
| DefinitionVersion | Agent、模型、工具、提示词的固定版本，运行开始后不再变 |
| MissionScope | 任务树上的一个节点：目标、预算、权限范围（M1 只有一个根节点） |
| GraphRevision | 任务图的版本号（M1 固定为 0） |
| Port | 模块对外公开的“窗口”，别的模块只能通过它请求服务 |
| BoundaryContext | 每次跨模块调用都带着的“随行单”：关联 ID、截止时间等 |
| ContextPack | ContextEngine 的输出：一包带来源的上下文内容 |
| AnalysisAction | 模型每一轮给出的动作提议（搜索、读取、结束等）；**还没定义，周日要定** |
| AnalysisReport | 最终的分析报告；**还没定义，周日要定** |
