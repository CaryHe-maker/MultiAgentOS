## 1 一次运行中，谁给谁传了什么

下面把《01 项目全景》第 3 节的流程展开到“传递的数据”这一层。✅ 表示代码里已经有这个数据格式，⚠️ 表示有但需要修改，❌ 表示还没有。

```text
用户
 │ 命令行输入问题
 ▼
UserInteraction
 │ UserIntent(RUN) ✅  + BoundaryContext ✅
 ▼
Kernel.submit()
 │ 检查格式后转交
 ▼
Workflow.create()
 │ DefinitionQuery ✅ ──► AgentToolPool ──► DefinitionVersion ✅（×5）
 │
 │ ── 以下进入 Agent 循环 ──
 │
 │ UnitIntent(CONTEXT, input=ContextRequest ⚠️)
 ▼
Kernel.execute() ──► ContextEngine.buildContext() ──► ContextPack ⚠️
 │                                                    （存入 Artifact，回执里给取件码）
 │ UnitResult ✅
 ▼
Workflow
 │ UnitIntent(MODEL, input=??? ❌)
 ▼
Kernel.execute() ──► 模型适配器 ❌ ──► DeepSeek
 │ UnitResult(output=AnalysisAction ❌)
 ▼
Workflow 解析动作
 ├─ SEARCH ──► UnitIntent(CONTEXT, SEARCH) ──► Kernel ──► ContextEngine
 ├─ READ   ──► UnitIntent(FILE_READ, input={path} ⚠️) ──► Kernel ──► Executor
 └─ FINAL  ──► 验收 ──► AnalysisReport ❌
 │
 │ 每一步记为 StepRecord ❌，回到循环开头
 ▼
Kernel ──► RuntimeProjection ✅ ──► UserInteraction ──► 终端显示
```

从图里能看出，**M1 真正缺的就是几个关键的数据格式**：模型的输入与输出、模型的动作、步骤记录、最终报告。它们一旦定下来，三个人就可以同时开工。这正是田园说“没有规定 API 就写不了代码”的原因。

## 2 接口冻结清单（草案）

建议周日会议逐行过这张表，每行确定“格式”和“负责人”。

### 2.1 已经有、基本不用改的

| 接口 | 作用 | 位置 |
|---|---|---|
| `UserIntent`（RUN / INSPECT / REPORT / CANCEL） | 用户请求 | contracts |
| `BoundaryContext` | 跨模块调用的“随行单” | contracts |
| `UnitIntent` / `UnitResult` | 动作申请单 / 回执 | contracts |
| `ModuleError`（10 种错误类别） | 统一错误格式 | contracts |
| `ArtifactRef` | 存档取件码 | contracts |
| `DefinitionQuery` / `DefinitionVersion` | 查询和固定 Agent、模型、工具定义 | contracts |
| `RuntimeProjection` | 给用户看的运行状态 | contracts |

### 2.2 已经有、需要修改的

| 接口 | 要改什么 | 为什么 | 建议负责人 |
|---|---|---|---|
| `ContextRequest` | 按操作拆成 ORIENT / SEARCH / ASSEMBLE 三种 | 三种操作需要的输入完全不同 | meti（已有草案：Spec §3.1） |
| `ContextPack` | 每一项增加类型、分段、token 数、内容哈希；整包增加请求 ID、是否截断等 | 预算、去重、稳定前缀、评测都需要 | meti（已有草案：Spec §3.2） |
| `ContextPort` 返回值 | 改为可以返回结构化错误 | 现在出错时 Kernel 只能报笼统的“执行失败”，丢失了错误类别 | meti 提议，田园确认 |
| `FILE_READ` 的输入 | 从只有 `{path}` 改为 `{path, startLine?, endLine?}`，输出带行号 | 只读整个文件会迅速耗尽上下文预算 | 田园 |
| `UnitResult.usage` | 增加“缓存命中的输入 token 数” | 评测要统计缓存命中率和真实成本 | 田园 |

### 2.3 还没有、必须在周日定下的

| 接口 | 作用 | 建议内容 | 建议负责人 |
|---|---|---|---|
| **`AnalysisAction`** | 模型每一轮的动作 | 判别联合：`SEARCH{query, mode}`、`READ{path, startLine, endLine}`、`FINAL{report}`、`ASK_USER{question}`、`CANNOT_DETERMINE{reason, checked}`。TargetM1 里还写了 `QUERY`，建议并入 `SEARCH` | Cary |
| **MODEL 单元的输入** | Workflow 让 Kernel 调模型时传什么 | `{ assembledPackRef, modelDefinitionRef, actionSchemaRef, maxOutputTokens }`：组装好的上下文、用哪个模型、要求模型输出的格式 | 田园 + meti |
| **MODEL 单元的输出** | Kernel 调完模型返回什么 | 校验通过的 `AnalysisAction`（或校验失败的原始文本 + 错误）、用量、模型原始输出的存档 | 田园 |
| **`StepRecord`** | 每一步的记录，ASSEMBLE 要用 | 步骤序号、动作摘要、观察结果的存档、观察类型（Spec §3.1 已有草案） | Cary 确认 |
| **`StatusFacts`** | 状态栏的数据 | 当前步数、预算用量、已读文件、未确认项、上一个错误（Spec §5.7 已有草案） | Cary 确认 |
| **`AnalysisReport`** | 最终报告 | 结论列表（每条带出处：路径、行号、版本）、未确认项、步骤数、用量、终止原因 | Cary |
| **上下文 → 模型消息的转换** | ContextPack 怎么变成 DeepSeek 的消息列表 | 由 Kernel 的模型适配器负责，按 ContextPack 每一项的 `role` 和 `segment` 转换 | 田园 + meti |

### 2.4 需要拍板的技术选择

| 问题 | 选项 | 我的建议 |
|---|---|---|
| 模型动作用什么格式输出 | A：模型原生的工具调用；B：让模型输出一段 JSON | **A**。服务商对原生工具调用做过专门训练，更不容易出错；消息结构也更利于缓存 |
| Workflow 和 Kernel 互相调用怎么接线 | 现在是先创建 Workflow，再把它交给 Kernel；但 Workflow 的循环也要调用 Kernel | 在启动代码里先建好两个对象，再把 Kernel 的 Port 注入给 Workflow；或者让 Workflow 在每次运行时接收 Port |
| 路径安全检查放在哪 | Kernel 的 Executor 和 ContextEngine 现在各写了一份 | 抽到一个共享的小工具包里，两边共用，保证规则一致 |
| 接口改动的流程 | — | 以后任何人要改共享接口，先提 PR 并附上测试，另外两人确认后再合并 |

## 3 周日会议准备

### 3.1 会议最该回答的核心问题

Cary 在群里提了：**“第一版是做完最小有效单元，还是就要兼容后面大部分框架？”**

建议你的立场是：**做最小有效单元，但把扩展点留好。** 具体说法可以是：

> “我们留扩展性的方式，不是提前把以后的模块都搭好，而是让接口可以往上加。比如 ContextRequest 按操作区分，以后加新操作不影响旧的；检索后端是一个可替换的接口，以后加向量检索只要新写一个实现；所有数据格式都带版本号。这样 M1 可以尽快跑起来，以后也不用推倒重来。”

这个说法兼顾了 Cary 的顾虑（以后要能扩展），也回应了田园的诉求（尽快定下接口、开始写代码）。

### 3.2 建议的会议议程（约 90 分钟）

| 时长 | 议题 | 目标产出 |
|---|---|---|
| 10 分钟 | 方向：最小有效单元 vs 兼容框架 | 一句话共识 |
| 40 分钟 | 逐项过第 2 节的接口清单 | 每个接口有格式草案和负责人 |
| 15 分钟 | 技术选择（第 2.4 节） | 四个问题各有结论 |
| 15 分钟 | 分工与时间：各自每周投入、第一次联调日期 | 联调日期写进 M1Process |
| 10 分钟 | 协作规则：接口变更流程、工作日志、PR 评审 | 写进 README 或协作文档 |

### 3.3 你可以准备带去的材料

1. `ContextEngineSpec.md` 第 3 节：作为“接口写成什么样”的示范，大家可以照这个格式定自己的接口。
2. 本文第 2 节的清单：直接投屏，逐行打勾。
3. 一个问题：“我们第一次三个模块接起来、用真实模型跑通一个任务，定在哪一天？”这个日期会逼着所有人把接口落地。

### 3.4 会上可能被问到的问题，以及你怎么答

| 可能的问题 | 你可以这样答 |
|---|---|
| “ContextEngine 为什么要三种操作，一种不行吗？” | “概览只在开头做一次，搜索是模型主动发起的，组装是每轮调模型前都要做。三者的输入完全不同，合成一种，接口里就会有一堆可选字段，容易出错。” |
| “为什么要由你来组装模型输入，不是 Workflow 自己拼？” | “怎么排列内容决定了缓存能不能命中、会不会超预算，这是上下文管理的核心。Workflow 负责提供事实（做过什么、到第几步），我负责决定怎么呈现给模型。” |
| “评测为什么要第一周就做？” | “检索评测不花 token，可以随时跑。没有它，我们改任何东西都只能凭感觉。” |
| “M1 为什么不用向量数据库？” | “代码里的函数名是精确的，文本搜索加符号匹配召回已经很高。先用检索评测测出现在的召回率，数据说明不够用了再加。” |
