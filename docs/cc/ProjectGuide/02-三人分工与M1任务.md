## 1 先看代码现在走到了哪一步

我逐个读了 `feat/M1` 的代码。整体情况是：**骨架和安全基础已经搭好，但 Agent 还不会“思考”：模型调用和 Agent 循环都还没写。**

| 部分 | 已经有的 | 还缺的 |
|---|---|---|
| 公共合约 `contracts` | 动作申请单与回执（UnitIntent / UnitResult）、上下文请求与结果、用户请求、错误格式、各种 ID | **模型动作（AnalysisAction）、观察结果（Observation）、最终报告（AnalysisReport）还没定义** |
| UserInteraction | 能把“运行”和“查看”请求交给 Kernel | 命令行入口 `apps/cli` 只有 1 行，还不能真正在终端里用 |
| Workflow | 能创建一次运行，并从 AgentToolPool 查好 5 个定义（Agent、模型、工具、提示词、动作格式） | **Agent 循环一行都没有**：不会调模型、不会解析动作、不会停止、不会出报告 |
| Kernel | 能检查请求格式；能把“上下文”请求转给 ContextEngine；能把其他请求转给执行器；超时检查 | **调用模型还没实现**；取消（CANCEL）暂不支持 |
| Executor（`apps/executor`） | 安全读文件：拒绝绝对路径、`..`、符号链接越界，有大小和超时限制，测试齐全 | 只能读**整个文件**，不能指定行范围 |
| ContextEngine | 一个简单版：逐个文件数关键词出现次数，把整个文件塞进结果 | 规格里的 ORIENT、SEARCH、ASSEMBLE 基本都还没做 |
| AgentToolPool | 内置了 Agent、模型、工具、提示词、动作格式的定义与版本号 | 提示词的**实际内容**还没写 |
| 基础设施 | 本地存档、文件存储、进程内转发、模块启动顺序，都有最小实现和测试 | 基本够 M1 用 |

**一句话总结：** “管道”已经铺好，“水”还没通。M1 剩下的主要工作，就是把模型接上、把循环写出来、把上下文和评测做好。

## 2 三个人 M1 分别做什么

### 2.1 Cary：Workflow（外加 UserInteraction 和 AgentToolPool 的最小实现）

**大白话：** 他负责写“项目经理”，也就是 Agent 循环本身。

具体要做的：

1. **定义模型的动作格式（AnalysisAction）**：模型每一轮只能从几种动作里选一个，比如搜索、读文件、给出最终答案；提案里还建议加上“向用户澄清”和“无法确定”。
2. **写 Agent 循环**：组装输入 → 调模型 → 解析动作 → 执行 → 记录观察 → 下一轮。
3. **处理模型出错**：模型输出不是合法的动作格式怎么办（一般是提示它重试，最多几次）；连续做同样的动作、原地打转怎么发现。
4. **控制预算和停止**：最多 24 步、12 次模型调用、12 万 token、30 分钟（代码里已有这组默认值），到了就停，并说明为什么停。
5. **最终验收与报告**：检查每条结论都有出处，生成分析报告（AnalysisReport）。
6. **写好提示词内容**（AgentToolPool 里）和命令行入口（CLI）。

**做完是什么样：** 在终端输入一个问题，能看到 Agent 一步步搜索、读代码，最后输出一份带出处的报告。

**他需要别人先给的：** Kernel 能调通模型（田园）；ContextEngine 能组装输入、执行搜索（你）。在拿到这些之前，他可以先用“假的”Kernel 和 ContextEngine（fake）把循环写出来。

### 2.2 田园：Kernel（和 Executor）

**大白话：** 他负责写“管理员兼执行员”：所有动作都要经过他这一关，并由他真正去执行。

具体要做的：

1. **接入模型**：通过 Vercel AI SDK 调用 DeepSeek，把返回结果校验成合法的动作格式；把模型 SDK 的各种报错转换成统一的错误分类；记录 token 用量（包括缓存命中了多少）。
2. **读文件支持行范围**：现在只能读整个文件，要改成可以只读第 30–90 行。这对控制上下文大小很重要。
3. **拒绝一切“写”的请求**：写文件、执行命令、跑测试，M1 全部返回“不支持”。
4. **每一步都记审计**：谁申请的、做了什么、结果如何、花了多久。
5. **保证仓库不被修改**：运行前后检查仓库版本没变。
6. 按提案建议，M1 的 Kernel 只保留上面这些核心；用户请求的准入和运行状态展示，可以交给时间更多的 Cary。

**做完是什么样：** Workflow 交给他一张“调模型”或“读文件”的申请单，他能安全执行并返回回执；任何越界请求都会被拦下，并给出明确的错误原因。

**他需要别人先给的：** 模型动作的格式（Cary 定义），他才知道要把模型输出校验成什么样。

**需要注意的现实情况：** 田园每周只有约 12 小时，还要上操作系统实践课。M1 的 Kernel 任务要控制在这个量以内。模型接入可能是他最花时间的一块。

### 2.3 meti（你）：ContextEngine + 评测

**大白话：** 你负责写“资料员”（决定模型每一轮看到什么），同时负责“考官”（证明 Agent 在变好）。

具体要做的（详见 `ContextEngineSpec.md` 第 9 节）：

1. **第 1 周**：写合约变更提案；实现路径安全和文件过滤；接入 rg；SEARCH 最小版；准备 F1–F5 五个测试任务；做好不花 token 的检索评测。
2. **第 2 周**：代码分块、打分排序、去重；ORIENT 仓库概览；ASSEMBLE 最小版。
3. **第 3 周**：长观察截断、历史压缩；token 估算校准；端到端评测（每个任务跑 3 次）。
4. **第 4 周**：各功能的开关对照实验；回归集；评测报告。

**做完是什么样：** 有一份带数据的评测报告，能说出“仓库概览让成功率提高了多少”“压缩让成本降低了多少”。

**你需要别人先给的：** Workflow 要提供步骤记录（StepRecord）和状态事实（StatusFacts）的格式；Kernel 的读文件要支持行范围。这两件事周日都要定。

## 3 三个人之间谁等谁

```text
                 ┌── 周日会议：定下所有接口 ──┐
                 ▼                           ▼
   Cary：动作格式、步骤记录格式      meti：上下文请求/结果格式
                 │                           │
      ┌──────────┴──────────┐                │
      ▼                     ▼                ▼
田园：按动作格式校验     Cary：用 fake 写循环   meti：用 fixture 写检索
     模型输出                                  （完全不依赖别人）
      │                     │                │
      └──────── 第 2 周末：把三部分接起来，跑通第一个真实任务 ────────┘
```

**关键点：**

- **接口一旦定下，三个人都可以立刻开工。** 每个人先用“假的”对方模块（fake）做测试，不用等别人写完。这就是 M1AchievePlan 里说的“Workflow 负责人不等待真实 Kernel/ContextEngine”。
- **你的检索部分完全不依赖别人**，可以最先开工。只要有测试仓库和 rg，SEARCH 和检索评测就能做。
- **真正的“接线”在第 2 周末**：三部分第一次连起来，用真实模型跑一个任务。这时候一定会暴露各种问题，要预留时间。

## 4 M1 之后每个人做什么（大白话版路线图）

以下按 M1 修改提案里调整后的路线写。团队如果不同意提案，M2 会按原计划加入数据库和 DBOS。

| 里程碑 | 产品变成什么样 | Cary（Workflow） | 田园（Kernel） | meti（ContextEngine + 评测） |
|---|---|---|---|---|
| **M1** | 只读分析助手：能读懂陌生仓库，交出带出处的报告 | Agent 循环、预算、报告 | 模型接入、安全读文件、拒绝写入 | 概览、搜索、组装、压缩、评测 |
| **M2** | 能改代码的助手：修 bug、跑测试、交出改动（diff） | 循环加入“修改 → 测试 → 失败再改” | 写文件和执行命令（需要用户确认）、在 Docker 里执行、git worktree 隔离 | 文件改动后旧内容失效；把测试报错纳入观察；接入 SWE-bench 子集评测 |
| **M3** | 多个 Agent 分工：规划 Agent 拆任务，多个 Worker 并行，最后合并 | 任务图、并行调度、结果合并；任务树第一次真正用上 | 多个 Worker 的资源和并发控制 | 子 Agent 返回摘要的格式；把“上级目标、兄弟任务”写进子 Agent 的提示词；单 Agent 与多 Agent 的对比评测 |
| **M4** | 能暂停、恢复、审批 | 保存和恢复运行状态 | 高风险动作的人工审批、更强的隔离 | 恢复后重建上下文 |
| **M5** | 完整平台（多用户、Web 界面等） | 按需 | 按需 | 向量检索、长期记忆（数据证明需要时） |

**现实提醒：** 按三个人现在的投入，M3 能做完就很好了。M4、M5 更多是“长期设想”，不必现在就为它们花时间。

## 5 你可以怎么帮到另外两个人

这也是你在团队里提升存在感、加深理解的好办法：

1. **帮 Cary 写 Agent 循环的测试用例。** 你最清楚 ContextEngine 需要循环提供什么（每一步的动作、观察、状态），从使用者的角度写测试，能帮他把接口想清楚。
2. **帮田园搭评测环境。** 他接好模型以后，你的端到端评测能第一时间告诉他：模型输出格式出错的频率、token 用量、缓存命中率。这些数据直接反映他那块的质量。
3. **你的评测报告就是全队的成绩单。** 最后简历上写的“成功率从 X% 提到 Y%”，来自你的评测体系。
